`mpCharacterHeadMenuHandler` GETOPTIONCOUNT returns `mpGetNumHeads2()`
(the TOTAL head count -- legacy variant with `param2==1` for the second

both carousel rows). Our renderer uses a single head dropdown with
`mpGetNumHeads2()` options, matching the flat index space that
`mpchrSetHeadByIndex` understands.

`mpCharacterBodyMenuHandler` GETOPTIONCOUNT returns `mpGetNumBodies()`.

**Display names**: There is no `mpGetHeadName()` symbol. The agent-create
screen (`pdgui_menu_agentcreate.cpp:179`) builds display names from
`catalogMpHeadId(idx)` via a `formatCatalogId()` helper. We replicate the
same pattern (declare `catalogMpHeadId` extern, format the returned ID
string into "Dark Combat" / "Mr Blonde" etc.). Bodies have
`mpGetBodyName((u8)idx)` which returns the localized name string directly
-- we use that as-is.

only via `mpchrSetHeadByIndex` / `mpchrSetBodyByIndex` inside the legacy
`menuhandlerMpSimulantHead/Body` handlers.

## Dialog-level handler fallthrough

`menudialogMpSimulants`, `menudialogMpSimulant`, and `menudialog0017ccfc`
are all **dialog-level** handlers -- they receive `MENUOP_OPEN` / `MENUOP_TICK`
from the menu runtime regardless of whether the dialog is hot-swapped to
our C++ renderer. We do NOT invoke them from C++. Their side effects
(reset slotcount, auto-pop on delete, refresh model preview) fire through
the normal runtime path. This matches how S202 cheats.cpp preserved
`cheatMenuHandleDialog` OPEN/CLOSE side effects automatically.

## Intentional simplifications

1. **No 3D character model preview in Simulant Character screen**. Legacy
   uses `MENUOP_11` to drive `g_Menus[].menumodel.newparams` so the dialog
   renders a live character render to the right of the carousels. Our
   ImGui replacement shows two dropdowns (Head + Body) and a "Back"
   button, no preview. The render-to-texture portrait system exists in
   `pdguiCharPreviewRequest` but wiring it up is scope creep for Batch 6
   (Batch 11 player-setup will likely need the same thing -- better to
   do it once there than to partly-implement here).

2. **Flat profile list with inline group headers** in Add/Change Simulant.
   Legacy renders as a grouped list with separate "Normal Simulants" /
   "Special Simulants" headers. Our ImGui replacement uses the same
   `GETOPTGROUPCOUNT` / `GETOPTGROUPTEXT` / `GETGROUPSTARTINDEX` calls to
   find the split point and inserts a non-selectable group-header row
   above each group. Content parity, no collapse widget.

3. **No marquee animation for simulant description**. Legacy uses a
   scrolling marquee (MENUITEMTYPE_MARQUEE) with
   `mpMenuTextSimulantDescription`. Our replacement shows the same string
   as static wrapped text below the profile list. Visual animation lost;
   information content preserved. Matches the Batch 4 cheats unlock-
   tooltip precedent.

4. **Copy Simulant spelling**: legacy Edit-Simulant items[4] is
   `MENUITEMFLAG_LITERAL_TEXT` with hardcoded string `"Copy Simulant\n"`.
   We use the same literal.

5. **Edit-Simulant title is the bot name**. We call the function pointer
   `mpMenuTitleEditSimulant(nullptr)` via shadow-cast -- safe because the
   function does not dereference its dialogdef argument. Matches legacy
   exactly.

None of these drop a legacy handler, option bit, or backing-store write.
All are UX-level surface changes.

## Mid-batch integration pivot (per Mike's mid-task guidance)

After the initial build was green on both targets, Mike routed guidance:

> Bot/simulant setup should be integrated into the room design
> (pdgui_menu_room.cpp) rather than living as a standalone modal screen.
> Keep pdgui_menu_botsetup.cpp as the owner of the renderers, but
> integrate them into pdgui_menu_room.cpp as an inline panel / tab /
> expandable section rather than a pushed modal.  Legacy dialog symbols
> stay declared/defined for link compatibility.  Zero function loss.

### Situation before guidance

1. `pdgui_menu_botsetup.cpp` registers 5 modal renderers for the legacy
   `g_MpSimulantsMenuDialog` / `g_MpAddSimulantMenuDialog` /
   `g_MpChangeSimulantMenuDialog` / `g_MpEditSimulantMenuDialog` /
   `g_MpSimulantCharacterMenuDialog` dialogs.  These hot-swap the legacy
   Combat Simulator push path to ImGui modals.  All backing-store writes
   route through the legacy C handlers in setup.c via the s204 shadow
   pattern.  Zero function loss for the legacy path.
2. `pdgui_menu_room.cpp` already has a rich per-room bot UI using
   `g_MatchConfig.slots[]` (room-native matchslot data model, NOT the
   legacy `g_BotConfigsArray[]` data model).  Room.cpp covers difficulty
   / type / character selection / weapon slot / accuracy+reaction
   traits inline in the room screen via a Bots section in the player
   panel plus a per-slot "Bot Settings" modal with advanced traits.

So room.cpp's bot integration ALREADY exists -- but for the modern
matchslot model, not the legacy `g_BotConfigsArray` model.  The two
coexist because the Combat Simulator legacy entry point (which pushes
`g_MpSimulantsMenuDialog`) is still reachable from the main menu tree.

### Integration approach

1. Keep `pdgui_menu_botsetup.cpp` as owner of the renderers (per Mike's
   guidance -- modularity, don't throw away the work).
2. Extract the five renderers' body-drawing logic into inline content
   helpers: `pdguiBotSetupDrawSimulantsBody` / `DrawAddChangeBody` /
   `DrawEditBody` / `DrawCharacterBody`.  Each takes an `outClose`
   parameter so the caller (modal wrapper or room.cpp panel) can close
   the surrounding window on user action.
3. The existing `renderMpSimulants` etc. become thin modal wrappers
   that call the inline helpers inside a modal frame.  This satisfies
   the legacy push path (for backwards compat / zero function loss if
   a Combat Simulator menu ever pushes these dialogs).
4. A new header `port/include/pdgui_menu_botsetup.h` declares the
   inline helpers with `extern "C"` linkage so `pdgui_menu_room.cpp`
   can include it.
5. `pdgui_menu_room.cpp` adds a new expandable section titled
   "Simulant Profiles" in the right-hand player panel (below the
   existing Bot section).  When expanded it calls
   `pdguiBotSetupDrawSimulantsBody` inline.  This gives room-inline
   access to the legacy `g_BotConfigsArray` flow alongside the existing
   matchslot flow.  It is additive -- no existing room.cpp code is
   removed or restructured.

### Why additive instead of replacing room.cpp's matchslot bot UI

Room.cpp's matchslot flow and the legacy `g_BotConfigsArray` flow are
backed by DIFFERENT data structures:

- `g_MatchConfig.slots[]` -- per-room live match config with body_id /
  head_id catalog strings, botDifficulty / botType enums, accuracy /
  reaction traits.  Used by room.cpp.
- `g_BotConfigsArray[]` -- 32-slot bot profile pool referenced by
  legacy menu dialogs, with mpbodynum / mpheadnum integer indices,
  difficulty u8, and the `g_BotProfiles[]` template system.

Unifying them into a single data model is a much larger refactor that
would retire half of setup.c and affect save-file compatibility.  That
is out of scope for Batch 6.  Instead we make BOTH flows reachable
from room.cpp and let them coexist -- the matchslot flow is the
primary/modern path, the legacy flow is the fallback/compatibility
path.  This preserves zero function loss for BOTH models and satisfies
"integrated into the room design" for the legacy dialogs Batch 6
targets.
