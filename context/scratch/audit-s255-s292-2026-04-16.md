## 2. Critical Issues

### C-1: Nine-Slice Chrome — Integer Overflow in TGA Writer + Pixel Loop

**File**: `port/fast3d/pdgui_menu_moddinghub.cpp:1444`

```c
for (s32 i = 0; i < w * h; i++) {
```

`w * h` is computed as `s32 * s32` (32-bit signed). For the scaled output case (scale slider goes to 400%), an image of 4096x4096 scaled 4x produces `s_ChromeOutW=16384, s_ChromeOutH=16384`. The product `16384 * 16384 = 268,435,456` overflows `s32` (max 2,147,483,647 — wait, that fits). But with an 8K input at 400%: `32768 * 32768 = 1,073,741,824` — still fits s32, but the per-pixel `fwrite` loop would write 4 GB of data. More immediately: the `size_t bytes = pxCount * 4u` at line 1527 for `32768*32768*4 = 4,294,967,296` — this overflows 32-bit `size_t` on 32-bit builds. Since this is a 64-bit Windows build, `size_t` is 64-bit, so the allocation technically works, but `malloc(4 GB)` will fail.

**Real-world impact**: A user importing a large image (4K+) and pushing scale sliders up can trigger multi-GB allocations that fail silently (the `realloc` fail returns early without error message), or succeed and produce enormous TGA files. The TGA header uses 16-bit width/height fields (lines 1436-1439), so output exceeding 65535px in either dimension produces a corrupt file.

**Fix**: Cap `s_ChromeOutW/H` to a sane maximum (e.g., 4096 or 8192), validate before allocation, show status error when the cap is hit.

### C-2: Nine-Slice Chrome — No Maximum Image Size Guard

**File**: `port/fast3d/pdgui_menu_moddinghub.cpp:1625-1648`

`chromeToolLoadImage()` passes the stb_image result directly to `glTexImage2D` with no size cap. A user selecting a 16K×16K screenshot (common from high-res displays) would allocate `16384*16384*4 = 1 GB` of VRAM and system RAM. Most GPUs have a `GL_MAX_TEXTURE_SIZE` limit (often 16384), but the allocation itself could cause an OOM crash or GL error that isn't checked.

**Fix**: After `stbi_load`, check `w*h > MAX_CHROME_PIXELS` (e.g., `8192*8192 = 67M pixels`). Reject with status message.

### C-4: Nine-Slice Chrome — mod.json Name Field Not JSON-Escaped

**File**: `port/fast3d/pdgui_menu_moddinghub.cpp:1727`

```c
"  \"name\": \"%s\",\n"
...
slug, s_ChromeModName,
```

`s_ChromeModName` is a user-editable text field (up to 96 chars). If the user types a name containing double quotes, backslashes, or control characters, the generated JSON will be malformed. The mod registry would fail to parse the file, silently dropping the mod.

### C-5: Nine-Slice Chrome — realloc Failure Leaves Dimension/Buffer Mismatch

**File**: `port/fast3d/pdgui_menu_moddinghub.cpp:1521-1534`

`s_ChromeOutW`/`s_ChromeOutH` are updated at lines 1521-1524 BEFORE the allocation at lines 1528-1534. If `realloc` fails, the function returns early, but `s_ChromeOutW`/`s_ChromeOutH` now describe the **new** (larger) dimensions while `s_ChromePreviewPixels` still holds the **old** (smaller) buffer. The next access using the new dimensions (e.g., during save at line 1705, or the pixel loop at line 1544) will read/write out of bounds — a potential crash or memory corruption.

**Fix**: Defer updating `s_ChromeOutW`/`s_ChromeOutH` until after the allocation succeeds. Or restore them on failure.

### C-6: `matchConfigAddBot` Hardcoded Human Count

**File**: `port/src/net/matchsetup.c:438`

```c

```

The `1` hardcodes a single human. In multiplayer with 2-8 humans, this ceiling is too high — it would allow `MATCH_MAX_SLOTS - 1` bots instead of `MATCH_MAX_SLOTS - actualHumans`. ## 3. Significant Concerns

### S-1: Nine-Slice Chrome — Resolution-Independence Gap (Mike's Flagged Issue)

**Core problem**: Inset values (`s_ChromeInsetL/R/T/B`) are pixel-absolute integers tied to the imported image's resolution. When a user imports a 4K image and sets insets to 1024px (25% of image), those values mean something completely different if they import a 256px image. The saved `mod.json` records `src_inset` in pixels from the saved output dimensions, but there's no concept of proportional insets.

**Critical detail found in save path** (`pdgui_menu_moddinghub.cpp:1755-1756`): Both `src_inset` and `dst_corner_px` in the saved JSON are written with **identical values** — both use `s_ChromeInsetT/B/L/R`. These are conceptually different: `src_inset` defines where to slice the source texture, while `dst_corner_px` defines how large the corners render on screen. By making them equal, corners always render at the source pixel size regardless of display resolution. A 2048px source with 512px insets renders 512px corners — enormous at 1080p, reasonable at 4K. A 128px source with 32px insets renders tiny corners at any resolution. This is the root cause of Mike's concern.

**Current behavior**:
- On load, insets default to `w/4` and `h/4` (line 1651-1654) — proportional to the loaded image
- Slider bounds clamp to output dimensions (line 1589+)
- Save writes absolute pixel values to `mod.json`
- No border-scale control exists

**What goes wrong**: A user creates chrome from a 512x512 image with 128px insets (25% borders). Another user imports a 2048x2048 image — the default insets are 512px, and the visual proportions are correct. But if they load the first user's mod, the insets are baked at 128px which is now only 6.25% of the new dimensions.

**Proposed design** (see Section 4 for full proposal).

### S-2: Middle-Click Back Bridge Conflicts with Skin Editor Canvas Pan

**File**: `port/fast3d/pdgui_backend.cpp:337-343` vs `port/fast3d/pdgui_skin_editor.cpp:454`

The middle-click back bridge (S276) injects `ImGuiKey_Escape` on middle mouse button down. But the Skin Editor uses `ImGui::IsMouseDragging(ImGuiMouseButton_Middle)` for canvas panning. When the user starts a middle-click drag on the skin canvas:
1. Middle-button-down triggers `io.AddKeyEvent(ImGuiKey_Escape, true)` in `pdguiDriveImGuiNav`
2. This Escape event closes the skin editor or its parent dialog before the drag gesture completes
3. The pan is interrupted by the cancel action

This is a confirmed input conflict. Middle-click panning in the Skin Editor is broken by the S276 universal back bridge.

**Fix**: Gate the middle-click→Escape injection on `!ImGui::IsMouseDragging(ImGuiMouseButton_Middle)`, or exempt the Skin Editor tool from the bridge when it has canvas focus.

### S-3: Shared `s_PdmsOwnsMenuCtx` Flag Across 4 Dialogs

**File**: `port/fast3d/pdgui_menu_mpsettings.cpp:305`

All four MP settings dialogs (Handicap, SelectTunes, Soundtrack, TeamNames) share one static `s_PdmsOwnsMenuCtx` flag. If dialog A pushes `g_CtxImGuiMenu` and sets the flag true, then the user navigates to stacked dialog B, B's `IsWindowAppearing` finds the context already active and sets the flag false. When B closes, it sees `s_PdmsOwnsMenuCtx == false` and does NOT pop the input context — leaking it on the stack. This causes input context stack corruption when navigating between stacked dialogs (e.g., Soundtrack → SelectTunes).

**Fix**: Use per-dialog ownership tracking instead of a single shared flag.

### S-4: Close Button Hover Check Not Clipped to Window

**File**: `port/fast3d/pdgui_style.cpp:537`

`IsMouseHoveringRect` is called with `false` (not clipped to current window). If a modal popup is on top of another dialog, clicking in the X-button region of the BACKGROUND dialog fires Escape on the wrong dialog. Since PD dialogs use custom title bars drawn via the draw list (not ImGui's built-in), ImGui doesn't manage focus for this custom button.

**Fix**: Add `ImGui::IsWindowFocused()` check before processing the close-button click, or pass `true` to `IsMouseHoveringRect` for window clipping.

### S-5: Skin Editor Downrez Preview Buffer Not Resized on Character Change

**File**: `port/fast3d/pdgui_skin_editor.cpp:1329-1332`

`s_DownrezPreview` is allocated once based on canvas dimensions. If the user switches characters (different texture size) while the downrez dialog is open, the buffer size may not match the new `cw * ch * 4`. The `skinQuantize` call at line 1335 writes `cw*ch*4` bytes into the old buffer — a potential heap buffer overwrite.

**Fix**: Track the allocated dimensions and realloc when they change.

### S-6: Chrome Style Rescan Leaks GL Textures

**File**: `port/fast3d/pdgui_theme.cpp:1304-1317`

`pdguiThemeRescanChromeStyles()` calls `s_chromeStylesClear()` which only zeros the count — it does not delete the GL textures uploaded during the previous scan. The textures remain in `s_ThemeTexCache` with valid GL IDs. On repeated rescans (e.g., user repeatedly opens settings, or toggles mods), old GL textures for removed/replaced mods leak GPU memory.

### S-7: Nine-Slice Chrome — Preview Buffer Never Shrinks

**File**: `port/fast3d/pdgui_menu_moddinghub.cpp:1528-1535`

The preview buffer uses `realloc` which can grow but never explicitly shrinks. If the user starts with a large image and scale, then reduces scale, `realloc` to a smaller size is valid C but the allocator may keep the larger block. More critically, if `realloc` fails (on the grow path), the function silently returns without updating the preview or showing an error, leaving stale preview data displayed.

### S-3: `matchConfigChooseBotTeam()` Only Handles 2 Teams

**File**: `port/src/net/matchsetup.c:411-428`

```c
s32 counts[2] = {0, 0};
...
if (team < 2) { counts[team]++; }
...
```

If PD2 supports 3+ team modes (and it does — the original had up to 8 teams), this code only balances across teams 0 and 1. All bots would pile onto teams 0-1, leaving teams 2-7 empty. For the current most-common case (2 teams), this works correctly.

### S-4: Dev Window v2 `--no-verify` Fallback Scope

**Files**: `devtools/dev-window-v2/dev-window-v2.ps1:1373-1374`, `devtools/release.ps1:133-134`

### S-6: Chrome Style Registry Thread Safety

**File**: `port/fast3d/pdgui_theme.cpp:1283-1307`

`pdguiThemeRegisterChromeModDir()` and `pdguiThemeRescanChromeStyles()` modify `s_ChromeStyles[]` and call into the GL texture/nineslice registration pipeline. Both are called from the ImGui render thread (main thread) during frame render. Since PD2 is single-threaded for rendering, there's no race condition per se. However, `pdguiThemeRescanChromeStyles()` calls `s_chromeStylesClear()` which destroys the style array, and if a nineslice draw call is in flight during the same frame (e.g., a style is being rendered when rescan is triggered), the texture ID could become invalid.

**Mitigation**: In practice, the rescan is triggered by button clicks in the Modding Hub which is a separate frame from normal chrome rendering. But there's no structural guard.

### S-7: Skin Editor Capture — Largest-Area Heuristic May Choose Wrong Texture

**File**: `port/fast3d/gfx_pc.cpp` (S278 change)

The skin capture source selection was changed from "first imported texture" to "collect all candidates, choose largest-area texture." This is better, but the heuristic can still fail: if a character model has a large shared-atlas texture (e.g., a 512x512 weapon/accessory texture) alongside the actual 256x256 body texture, the wrong one gets captured.

**Impact**: Skin Editor base capture could produce wrong-content base layers for some character models.

### S-8: `stageTableReset()` Called During In-Place Apply — Potential Use-After-Free

**File**: `port/src/modmgr.c:1780` → `modmgrUnloadAllMods()` → `stageTableReset()`

`modmgrApplyChanges()` calls `modmgrUnloadAllMods()` which calls `stageTableReset()`. But the apply path is designed for in-place operation ("no stage restart" — line 1795). If `stageTableReset()` zeroes or reallocates the stage table, and the player is in a menu that caches pointers to stage table entries (e.g., the arena selector in the Room screen), those pointers become dangling. The `modmgrReload()` path is safe because it immediately calls `mainChangeToStage(MODMGR_STAGE_TITLE)` which reloads everything, but `modmgrApplyChanges()` stays in-place.

**Fix**: Either skip `stageTableReset()` in the in-place apply path, or ensure all stage-table consumers re-resolve their pointers after apply.

### S-9: Nineslice Registry Never Cleared on Apply — Accumulation

**File**: `port/fast3d/pdgui_nineslice.cpp` (fixed-size `s_Registry[]`)

`pdguiNinesliceRegister()` adds entries to a capped array. The mod apply path never calls any nineslice clear function. Over repeated apply cycles with different chrome mods, the registry fills up (capped at `PDGUI_MAX_NINESLICE_ENTRIES`) and eventually refuses new registrations silently. Disabled chrome mods leave stale nineslice definitions that can't be overwritten.

**Fix**: Add `pdguiNinesliceClearMods()` to the apply path, or at minimum clear non-base entries before re-registration.

### S-10: Two Copies of `parseAudioCategoryValue` with Subtle Differences

Nearly identical implementations with differences in whitespace handling and numeric cast (`(u8)value[0]` vs `*value`). Both work in practice because upstream trimming handles whitespace, but the duplication is a maintenance hazard — a bug fix in one copy won't propagate to the other.

### S-11: modmgrApplyChanges Missing Chrome Style Rescan

**File**: `port/src/modmgr.c:1788-1796`

`modmgrApplyChanges()` calls `pdguiThemeRescanMods()` (for `theme.json` visual themes) but does NOT call `pdguiThemeRescanChromeStyles()` (for chrome nine-slice mods). ### S-9: Nine-Slice Chrome — Trim Sliders Not Cross-Clamped

**File**: `port/fast3d/pdgui_menu_moddinghub.cpp:1873-1876`

Each trim slider (Left/Right/Top/Bottom) independently ranges from 0 to `ImgW-1` (or `ImgH-1`). Combined `TrimL + TrimR` can equal `2 * (ImgW - 1)`, far exceeding the image width. The preview function clamps `cropW` to minimum 1 (line 1489) preventing a crash, but users get degenerate 1-pixel crops with no feedback that the trim pair is over-committed.

### S-10: Nine-Slice Chrome — glTexImage2D Called Every Slider Tick

**File**: `port/fast3d/pdgui_menu_moddinghub.cpp:1584`

`chromeToolUpdatePreviewTexture()` calls `glTexImage2D` (full GPU texture reallocation + upload) every time any slider changes. For a 2048x2048 preview this is 16 MB per slider tick. Should use `glTexSubImage2D` when dimensions haven't changed and only `glTexImage2D` when they have.

### S-11: Nine-Slice Chrome — Original Texture Wastes VRAM

**File**: `port/fast3d/pdgui_menu_moddinghub.cpp:1648, 1955`

The full-resolution imported image is uploaded as `s_ChromeTex` via `glTexImage2D`. For a 4K image this consumes 33 MB of VRAM. But `s_ChromeTex` is only used as a fallback when `s_ChromePreviewTex` is not available (line 1955: `s_ChromePreviewTex ? s_ChromePreviewTex : s_ChromeTex`). Since `chromeToolUpdatePreviewTexture()` is called immediately after load (line 1660), the preview texture is always available. The original occupies VRAM for no reason.

### S-12: SVC_ROOM_SETTINGS Doesn't Clear Stale Bot Slots on Count Decrease

**File**: `port/src/net/netmsg.c:6124-6136`

When `numBots` decreases (host removes bots), `numSlots` is set to `1 + clampedBots`, but slots beyond `clampedBots` are never zeroed. The loop at line 6128 only initializes `SLOT_EMPTY` slots up to `clampedBots`. Previous `SLOT_BOT` entries at higher indices retain stale data. While `numSlots` should prevent most code from iterating into them, any path that scans the full `MATCH_MAX_SLOTS` array (rather than stopping at `numSlots`) could pick up ghost bots. The slot memory is never cleared to `SLOT_EMPTY`.

**Fix**: After the initialization loop, explicitly zero `slots[1+clampedBots..numSlots_old-1].type = SLOT_EMPTY`.

### S-13: Client/Host Team Assignment Strategy Mismatch

**File**: `port/src/net/netmsg.c:6132-6133` vs `port/src/net/matchsetup.c:411-429`

The host uses `matchConfigChooseBotTeam()` (balance-counting: count occupants per team, assign to least-full). The client-side `SVC_ROOM_SETTINGS` rebuild uses positional alternation: `team = (i-1) & 1`. These strategies produce different team assignments for the same slot configuration.

For example, if the host's player is on team 0 with 3 bots: `matchConfigChooseBotTeam` distributes 1-2-1, but the client alternation produces 0-1-0-1. Additionally, the alternation ignores the local player's actual team — slot 0's team is not considered.

**Fix**: Either have the host send per-bot team assignments on the wire, or have both sides use the same algorithm.

### S-14: `scenario_id` Not Synced in SVC_ROOM_SETTINGS

**File**: `port/src/net/netmsg.c:6115`

`SVC_ROOM_SETTINGS` carries `scenario` as a `u8` integer but does NOT carry `scenario_id` (the PRIMARY catalog string per constraints.md). The read path updates `g_MatchConfig.scenario` (deprecated integer) but leaves `scenario_id` stale. Since `scenario_id` is documented as the authoritative identity, a client-side scenario save after receiving this message would record the wrong game mode.

### S-15: Odd Bot Count in Team Mode

**File**: `port/src/net/matchsetup.c:428`

```c
return counts[0] <= counts[1] ? 0 : 1;
```

With an odd number of bots (e.g., 7), team 0 gets 4 bots and team 1 gets 3. The `<=` means team 0 always gets the extra bot. This is fine for initial assignment, but if bots are removed and re-added, the count check doesn't consider the removed bot's team — it rebalances from scratch across all remaining slots, which is actually correct behavior.

## 4. Nine-Slice Chrome: Current State + Proposed Design

### Current State

The Nine-Slice Chrome tool (S288-S290) provides:
- Image import via file browser + stb_image (PNG/JPG/BMP/TGA)
- Transform pipeline: trim edges → center-cut → scale → optional desaturation
- Live ruler overlay preview showing slice positions
- Assembled frame preview via `pdguiNinesliceDrawEx`
- Save as mod: writes `ui_chrome_frame.tga` + `mod.json` → immediate activation

**What works well**: The transform pipeline is well-structured with proper clamp guards at each stage. The preview system gives immediate visual feedback. Save+activate cycle is seamless.

**What doesn't work**: 
1. No resolution cap on imported images (can OOM)
2. Insets are pixel-absolute (resolution-dependent)
3. No border-scale concept
4. TGA format limited to 65535px per dimension
5. Large images + high scale = multi-GB allocations

### Proposed Design: Border Scale + Interior Rectangle

**Goal**: Allow users to import any resolution source image and produce a chrome mod that looks correct regardless of the source resolution.

**Approach**: Add two controls:

1. **Border Scale** (`s_ChromeBorderScale`, float, default 1.0):
   - Multiplier on the final inset values written to `mod.json`
   - `dst_corner_px = (int)(inset * borderScale)`
   - Allows "thicker" or "thinner" borders from the same source
   - UI: slider 0.25x–4.0x with visual preview

2. **Interior Rectangle** (`s_ChromeInteriorL/T/R/B`, proportional 0.0–1.0):
   - Defines the "useful content area" as a fraction of the output image
   - Default: auto-derived from insets (`insetL/outW`, etc.)
   - Override mode: manual sliders for each edge
   - Purpose: when importing a non-standard-ratio image, user can define where the content goes

3. **Resolution Normalization on Import**:
   - After stb_image load, if either dimension > 2048, downsample to fit in 2048x2048
   - This caps VRAM usage at 16 MB and keeps TGA writes reasonable
   - Inform user: "Image downsampled from 4096x4096 to 2048x2048 for chrome authoring"

4. **Proportional Inset Mode** (optional toggle):
   - Store insets as percentages (0-50%) instead of pixels
   - On save, resolve to pixel values based on output dimensions
   - This makes insets resolution-independent by construction

5. **Resizable Panel Preview** (enhance existing frame preview):
   - Add width/height sliders for the frame preview pane (e.g., 100px-800px each)
   - Simulates real in-game panel sizes so users can see how the chrome renders at actual use dimensions
   - The existing `pdguiNinesliceDrawEx` already supports arbitrary destination rect — just expose it

**Implementation priority**: (1) Resolution cap on import + output dimension cap, (2) separate `dst_corner_px` from `src_inset` with border-scale slider, (3) proportional inset mode, (4) interior rectangle override, (5) resizable panel preview.

## 5. Dev Window v2: Failure Analysis vs Dev Window v1

### Key Architectural Difference

Dev Window v1 (`devtools/_dev-window.ps1`) is a monolithic ~2300-line script with synchronous build flow. Dev Window v2 (`devtools/dev-window-v2/dev-window-v2.ps1`) is a WPF-based GUI with async build queue, git sync, release integration, and DPI scaling.

### Known Fixed Issues (S255-S273)

| Session | Issue | Fix |
|---------|-------|-----|
| S255 | No Pull/Push buttons, DPI text blurry | Added Pull/Push, DPI-aware init |
| S256 | Tool buttons stretched tall, VERSION clipped | Layout fixes |
| S257 | Git sync before build missing | Added `Invoke-GitSyncBeforeBuild` |
| S259 | Stale `index.lock` blocks sync | Lock cleanup with retry |
| S261 | `python3` not on subprocess PATH | Explicit `-DPD_PYTHON_EXECUTABLE` |
| S269-S273 | Lock path format mismatch (MSYS/Windows/WSL) | Multi-path cleanup + same-git-exe policy |
| S287 | Hook failure blocks commit, missing Build dir | `--no-verify` fallback + `mkdir Build` |

### Remaining Divergences That Could Cause Failures (Ranked by Likelihood)

**1. PATH Pollution from `Sync-UserMachinePath` (MOST LIKELY FAILURE CAUSE)**

V2 (`dev-window-v2.ps1:25-33`) calls `Sync-UserMachinePath` which prepends BOTH Machine and User PATH entries to `$env:Path`. This runs AFTER `_build-env-prelude.ps1` set up the correct PATH. If the Machine PATH contains `C:\devkitPro\msys2\usr\bin` or another MSYS2/Cygwin installation, those entries get placed BEFORE `C:\msys64\mingw64\bin` — shadowing the correct cmake/gcc/ninja.

V1 (`_dev-window.ps1:18`) uses a simple, reliable hardcoded prepend: `$env:PATH = "C:\msys64\mingw64\bin;C:\msys64\usr\bin;" + $env:PATH`. No pollution.

**This is the root cause of the Cygwin-cmake bug we fixed today, and it will recur for any tool that exists in multiple MSYS installations.**

**2. Blocking Git Sync Freezes UI + Aborts Build on Push Failure**

V2's `Invoke-GitSyncBeforeBuild` runs SYNCHRONOUSLY on the WPF dispatcher thread. The entire UI freezes during `git add`, `commit`, `push`. If `git push` hangs (network issue, credential prompt), Dev Window becomes permanently unresponsive with no cancel mechanism. If push fails, V2 ABORTS the entire build.

V1 runs git operations as async build steps. If push fails, the build continues. Push failure is non-fatal — cmd.exe ends with `& exit 0`.

**3. Release Pipeline: `-File` vs `-Command` Invocation**

V2 invokes `release.ps1` with `-File` while V1 uses `-Command`. Key differences:
- V2 passes `-SkipPush:$false` but with `-File`, the `:$false` syntax is parsed as a literal string, not a PowerShell boolean. The switch may be misinterpreted.
- V1 passes `-NonInteractive`; V2 does not. If release.ps1 triggers a credential prompt, V2's subprocess hangs.
- V1 merges all output streams with `*>&1`; V2 doesn't — `Write-Host` output from release.ps1 may not be captured by V2's async line reader, making the Log tab appear empty during release.

**4. Incremental Release Build Instead of Clean**

V1 always does a clean build for releases (`forceClean=$true`). V2 does incremental (`$false`). Stale object files from a previous broken build can link into the release binary.

**5. Missing Stable Branch Merge Logic**

V1 has full stable-branch merge logic (checkout stable, merge dev, push stable, return to dev). V2 has none — the "Stable" release option just builds and calls release.ps1 without the branch merge step.

**6. Generator Difference**: V1 uses `Unix Makefiles` with `make.exe`; V2 uses `Ninja`. Ninja is faster and correct (matches `build-headless.ps1`), but if Ninja isn't found or the wrong one is found (Cygwin), V2 fails where V1 might succeed because `make.exe` is more universally available.

**7. Async build error propagation**: V2 runs builds in a background runspace. If the runspace throws an unhandled exception (as seen in multiple sessions — "PowerShell runspace exception"), the error doesn't propagate to the UI cleanly. V1 runs synchronously and errors are visible immediately.

### Recommended Fixes (Priority Order)

1. **Remove `Sync-UserMachinePath`** or move it BEFORE `_build-env-prelude.ps1` so the prelude's prepend wins. Better: hard-code the PATH exactly like V1 does.
2. **Make git sync non-blocking**: Run in a background runspace with timeout. Don't abort build on push failure.
3. **Switch release invocation to `-Command`** to match V1's proven approach. Pass `-NonInteractive`.
4. **Add `forceClean=$true`** for release builds.
5. **Port stable-branch merge logic** from V1.
