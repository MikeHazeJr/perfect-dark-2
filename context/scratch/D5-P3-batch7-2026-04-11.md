### 3.3 Audit conclusions

1. **No new shadow/cache copy was introduced.** Every Batch 7 ImGui
   writer routes its MENUOP_SET through a legacy C handler via the s205
   call-through. Those handlers touch exactly the same globals the
   legacy renderer's menuitem dispatch would have touched — meaning the
   host match-start (`mpStartMatch` + `mpConfigureQuickTeamSimulants` +
   `mpConfigureQuickTeamPlayers`), the network serializer
   (`netmsgSvcStageStartWrite`), the client receive path
   (`netmsgSvcStageReceive`), and the endscreen all see identical state
   to a pure-legacy dialog interaction.

2. **Modern room-lobby path is untouched.** `port/fast3d/pdgui_menu_room.cpp`
   writes to `g_MatchConfig` (a distinct PC-port authoritative struct),
   and `port/src/net/matchsetup.c::matchStart()` copies `g_MatchConfig`
   → `g_MpSetup` before calling `mpStartMatch`. The Batch 7 dialogs are
   NOT reachable from `room.cpp` at all (grep confirmed no references),
   so there is no risk of interleaving the two paths.

3. **Quick-team state fields (`g_Vars.mpquickteam`, `mpquickteamnumsims`,
   `unk0004a0`, `mpsimdifficulty`, `mpplayerteams[]`) have no parallel
   `g_MatchConfig` equivalent.** This is intentional and pre-existing:
   the modern room lobby manages bot slots and teams through its own
   `struct matchslot slots[]` array, bypassing the quick-team abstraction
   entirely. If a user ever reached a Batch 7 hub while the room lobby
   was also active, the quick-team writes would be harmless because
   `matchStart()` overwrites `g_MpSetup.options` / stagenum / scenario /
   weapons with `g_MatchConfig` before `mpStartMatch` runs — meaning the
   only surviving quick-team state would be the bot counts and team
   assignments that `mpConfigureQuickTeamSimulants` applies to the
   `g_Vars.mpquickteam != NONE` branch. `g_Vars.mpquickteam` defaults to
   `NONE` and is reset by `menudialogCombatSimulator` MENUOP_TICK every
   frame the CS dialog is current, so stale quick-team state cannot leak
   into a subsequent non-QT match.

4. **Pre-existing (out of scope) hazard**: if a user edited match
   config through legacy Batch 7 dialogs AND then started via room.cpp,
   `matchStart()`'s g_MatchConfig → g_MpSetup copy would clobber the
   legacy edit. This was already the case before Batch 7 — the ImGui
   wrappers do not make it worse. Documented here for future awareness;
   not a Batch 7 bug.

5. **Network match-end path reads the same fields**: `endscreen.c` does
   not reference `g_MpSetup.*` directly. It reads `g_Vars.playerstats[]`
   / `g_BotConfigsArray[]` which were populated at match-start and
   updated during the match by `bot.c` / `chr.c` / scenario tick code.
   So any field that makes it into `g_BotConfigsArray` or
   `g_PlayerConfigsArray` at match-start time will reach endscreen.
   Verified clean for all 13 rows above.

### 3.4 What changed vs. Batch 6

Batch 6 had no network-audit requirement because its dialogs (Bot/
Simulant Setup) only wrote to the `g_BotConfigsArray` pool, which has
always been the leaf authoritative bot list — no ambiguity. Batch 7's
renderers write to a mix of `g_MpSetup.options`, `g_Vars.mp*`, and
`g_PlayerConfigsArray`, which is why Mike called for the audit. The
audit confirmed all writes hit the same paths the legacy renderer did.

## 6. Integration pattern notes

### 6.1 `hubPushRow` helper

Both the Advanced Setup hub and the Player Setup hub need selectable
rows that show a label on the left and dynamic text (scenario/arena
name, player name, "Save Player" / "Save Copy of Player") on the right.
ImGui's `Selectable` with trailing text is fiddly, so I built a small
`hubPushRow(label, target, rightSideText)` helper that draws a
full-width Selectable with a manual two-column text overlay via
`GetWindowDrawList()->AddText`. This keeps the render code compact and
uniform, and avoids inventing a new public layout primitive.

A parallel `hubHandlerRow(label, fn, param, rightSideText)` delegates
to a legacy handler's MENUOP_SET branch instead of pushing a dialog
directly — used for `menuhandlerMpOpenOptions` (pushes scenario-options
based on current `g_MpSetup.scenario`), `menuhandlerMpSaveSettings`
(pushes save-setup dialog based on `g_MpCurrentSetup`), and similar
indirection.

### 6.2 Default arguments in C++

Both hub row helpers use C++ default parameters (`rightSideText = nullptr`,
`param = 0`). This compiles fine in the C++ translation unit and
significantly cleans up the Advanced Setup hub body which would
otherwise need two explicit `nullptr`s per row. Standard C++ — no
compiler warning.

### 6.3 File-local window-frame clone

`ma_BeginStandardWindow` / `ma_CloseCurrentDialog` / `ma_BackPressed` are
byte-for-byte clones of the Batch 5 mpsetup.cpp helpers with an `ma_`
prefix. They could be extracted to a shared header, but doing so would
require pulling the WindowFrame struct out of file scope and re-plumbing
all four Batch 4-6 cpp files, which is out of scope for Batch 7. Same
decision Batch 6 made for botsetup.cpp — keep the clones until a clear
consolidation pass.

### 6.4 s205 shadow struct

Cloned from s203 (mpsetup.cpp) / s204 (botsetup.cpp). ABI-compatible
with `handlerdata` / `menuitem` from `src/include/types.h:3342..3417`.
Bumping the suffix one step per batch makes it easy to grep for which
cpp owns which shadow, and the independent definition means no header
changes are needed. The helpers under the shadow (`dd_Get*` / `dd_Set`
/ `dd_IsHidden` / `plain_Set`) are a superset of what we need — only
the dropdown + plain-SET helpers are used in Batch 7, but keeping the
full set makes future edits trivial.
