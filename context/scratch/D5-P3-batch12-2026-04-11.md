## Integration philosophy

Per Mike's direction ("same integration philosophy … enhance the room flow,
don't disrupt it") and the Batches 3–11 precedent:

- **s207 shadow-struct call-through** for any legacy item handler we invoke from
  C++ (tunes LIST, multiple-tunes CHECKBOX). Full MENUOP_* opcode block seeded
  at top of the new section to avoid the Batch 4 mid-flight gotcha.
- **Inline UX where it makes sense** — Team Names replaces the legacy
  KEYBOARD drill-down (`g_MpChangeTeamNameMenuDialog`) with an inline
  `ImGui::InputText` per row. Zero-function-loss preserved by routing the
  input through a new `pdguiMpsTeamNameSet` bridge accessor that mirrors the
  exact write semantics of `mpTeamNameMenuHandler::MENUOP_SETTEXT` (11-char
  cap, `\n` terminator at end, MODFILE_MPSETUP dirty flag). Room.cpp is
  untouched.
- **Soundtrack modal stays modal** — it's pushed from the MP stuff hub
  (already a Batch 7 ImGui renderer) and from the MP pause control hub
  (Batch 8). No inlining; just replace with a cleaner ImGui modal.
- **Select Tunes modal stays modal** — reached only by Soundtrack → Select
  Tune(s) push, so it lives as a child dialog.
- **Challenges root reuses existing renderer** — `g_MpChallengesMenuDialog`
  functionally equivalent to `g_MpChallengeListOrDetailsMenuDialog`. Both
  present the same list and the same Accept semantics. Adding a single
  registration to point the new dialog at the existing `renderChallenges`
  is the minimum correct extension.

## Network match start/end wiring audit

Mike's explicit requirement: verify every field writer → backing global →
match-start reader → match-end reader. No shadow/cached copy introduced.

### Setup

- **`g_BossFile`** — per-player persistent "boss" file that stores multiplayer
  settings (team names, track selection, soundtrack mode, locktype). Loaded
  from disk at boot, saved to disk via `saveBossFile()` when any handler sets
  `g_Vars.modifiedfiles |= MODFILE_MPSETUP`. The boss file is **strictly
  local** — each client machine loads its own boss file from its own save.
  There is **no wire field** for teamnames/tracknum/multipletracknums in the
  protocol v32 message set (`grep -r teamnames\|tracknum port/src/net/`
  returns nothing).
- **Challenges** — writer is `challengeSetCurrentBySlot(slot)` in
  `src/game/challenge.c` which writes into `g_MpSetup` (scenario, stagenum,
  weapons, bot profiles, score/time limits). `g_MpSetup` is the established
  MP match config whose fields already propagate via
  `netServerStageStart` / `SVC_STAGE_START` / `SVC_LOBBY_STATE` on match
  start. No batch-specific net surface.

### Summary

**9/9 fields accounted for.** 8 are **N/A (local-only)** — music tracks, team
names, and challenge lock are per-client display/state that never crosses the
wire. 1 is **WIRED** — challenge match start uses the established
`g_MpSetup` → `SVC_STAGE_START` flow and reuses the existing Batch 0
`matchStartFromChallenge` helper.

**Zero shadow/cached copies introduced.** Team name inline edits write
directly to `g_BossFile.teamnames[]` via the bridge accessor, same address
the legacy `mpTeamNameMenuHandler::MENUOP_SETTEXT` writes. No divergence.

**Room flow untouched.** None of the 4 dialogs inline into `room.cpp`'s
`renderPlayerPanel` because:
- Tunes/Soundtrack are ambient music config — no natural fit on the room screen.
- Team Names are only meaningful when teams are enabled (per-scenario config).
  Adding them to room.cpp as a collapsing header would duplicate the existing
  Pause → Team Rankings view (Batch 8). Keeping them as a modal from
  MP Stuff → Team Names (setup.c:5832) preserves the legacy flow.
- Challenges root is reached from the MP root menu via its own selectable
  (setup.c:6425) — it's a top-level navigation, not a per-player panel item.

**Note on SET bypass for challenges**: The legacy `mpChallengesListMenuHandler::MENUOP_SET` pushes a confirm dialog (either `g_MpConfirmChallengeViaListOrDetailsMenuDialog` or `g_MpConfirmChallengeMenuDialog` depending on `item->param`), which then pushes either `challengeSetCurrentBySlot + menuPopDialog` (advanced-setup path) or `challengeSetCurrentBySlot + func0f0f820c(&g_MpQuickGoMenuDialog, 3)` (root-menu path). The existing Batch 0 renderer bypasses BOTH confirm paths and directly calls `matchStartFromChallenge(slot)` which does `challengeSetCurrentBySlot + mpStartMatch`. This is a deliberate Batch 0 UX simplification: PC users get "pick and play" instead of "pick → confirm → quickgo → start". Batch 12 preserves the same behavior for `g_MpChallengesMenuDialog` because the zero-function-loss test is about the LEGACY LOGIC being preserved (challenge config → `g_MpSetup` → match start), not the legacy DIALOG SEQUENCE. All the intermediate confirm/quickgo dialogs are still compiled and reachable from other paths; they're just bypassed for the direct challenge-start UX.
