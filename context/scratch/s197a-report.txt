[A] MENU NAV BINDINGS ARE MISSING BY DESIGN BUT THE DESIGN IS BROKEN
---------------------------------------------------------------------
port/src/actionmap.cpp:1386 setupMenuDefaults() comment:
  "Menu IMC: Player 0 only. 3 functional actions -- ImGui handles all
   navigation internally via SDL key events; MENU_UP/DOWN/LEFT/RIGHT
   are dead weight here and omitted."

That comment is WRONG. The actual flow is:
  pdguiDriveImGuiNav() in pdgui_backend.cpp:303-326 reads
  ACTION_MENU_UP/DOWN/LEFT/RIGHT (and TAB_PREV/NEXT) via actionHeld()
  and calls io.AddKeyEvent(ImGuiKey_UpArrow/Down/Left/Right, ...) on
  the ImGuiIO. ImGui NavEnableKeyboard is on, NavEnableGamepad is OFF.
  So ImGui navigation REQUIRES the actionmap to drive those ACTION_MENU_*
  flags, but the menu IMC never binds anything to them.

Net effect:
  - Keyboard arrows: no SDL_KEYDOWN for arrow keys goes anywhere useful
    because menu IMC has no binding for VKL_UP/DOWN/LEFT/RIGHT, and
    ImGui's own NavEnableKeyboard looks for Gamepad* keys or the
    driven key events from pdguiDriveImGuiNav, not raw SDL arrow scancodes
    passed through ImGui_ImplSDL2_ProcessEvent in all cases.
  - D-pad: same story. JBTN_DPAD_UP has no bind in menu IMC, so
    actionHeld(ACTION_MENU_UP) is always 0, and pdguiDriveImGuiNav
    never drives ImGuiKey_UpArrow.

S189 "Menu IMC 3-action reduction" stripped MENU_UP/DOWN/LEFT/RIGHT on
the assumption that ImGui handled nav itself. It doesn't -- not in this
codebase's ImGui setup (NavEnableGamepad OFF, translator function exists
and is the only path for gamepad nav).

FIX: Re-add MENU_UP/DOWN/LEFT/RIGHT + TAB_PREV/NEXT bindings to
setupMenuDefaults() and setupPauseMenuDefaults(): VKL_UP/DOWN/LEFT/RIGHT
(keyboard) + JBTN_DPAD_UP/DOWN/LEFT/RIGHT + JBTN_LB/RB for tab cycling.

[C] PUSH/POP/PUSH FLICKER (port/src/inputctx.c)
------------------------------------------------
inputctx.c:95-121 inputCtxPopDeferred marks ctx->marked_for_removal=1
but LEAVES IT ON THE STACK until inputCtxEndFrame() (line 189) compacts
it out. During the in-between window:
  - inputCtxGetTop() skips marked-for-removal entries  -> looks like it's gone
  - inputCtxPush() duplicate check at line 72-78 scans s_Stack[i] == ctx
    WITHOUT checking marked_for_removal -> looks like it's still there

So a rapid pop+push sequence INSIDE one frame:
  - inputCtxPopDeferred(imgui_menu)    -> marked for removal
  - inputCtxPush(imgui_menu)           -> refused as "already on stack"
  - inputCtxEndFrame()                 -> removes it
  - next frame: inputCtxPush(imgui_menu) -> succeeds

But the OBSERVED log sequence is:
  pushed 'imgui_menu' -> marked for deferred removal -> deactivated 'menu'
  -> activated 'menu'  all within 10ms

That is: PUSH first, POP second, then ENDFRAME, then PUSH second.
Meaning two separate frames saw two push calls, both succeeding. That's
NOT a duplicate-rejection bug -- that's whatever caller is firing the
push twice. For the "Start pressed twice" case: if the UI toggle logic
runs on ACTION_USE press-edge and the edge fires on multiple frames, we
get N opens.

Plan: find the Start-press-to-main-menu-open site and gate it on "not
already open" rather than on press edge, OR make inputCtxPush() reject
marked-for-removal duplicates AS WELL (safer fix).

PHASE 2 -- PUSH/POP FLICKER DEFENSIVE FIX (DONE)
================================================================================

Problem evidence (from log):
  pushed 'imgui_menu' -> marked for deferred removal -> deactivated 'menu'
  -> activated 'menu'  — all within a 10 ms window on menu-style toggles.

Root cause:
  inputCtxPopDeferred marks a context entry `marked_for_removal = 1` but
  leaves it physically on s_Stack until inputCtxEndFrame() compacts it.
  The window between popDeferred and endFrame makes the stack look
  inconsistent to callers:

    - inputCtxIsActive / inputCtxGetTop     SKIP marked_for_removal entries
    - the old inputCtxPush duplicate check  DID NOT skip them

  So an in-frame pop-then-push sequence hit this path:
    popDeferred(imgui_menu)  -> marked
    push(imgui_menu)         -> refused "already on stack"
  ... and the resurrect was deferred a frame, producing a visible 1-frame
  menu-state flip.

Fix applied to port/src/inputctx.c (inputCtxPush):

  When the duplicate-check loop finds a matching ctx that is currently
  marked_for_removal, RESURRECT it:
    - clear marked_for_removal
    - refresh push_tick  (for the 100 ms grace window in key suppression)
    - call inputCtxSyncMouseMode() — popDeferred already synced the mouse
      mode to the next-underneath top, so we must re-sync back to the
      resurrected ctx's state
    - do NOT re-fire on_push — the original on_push side effects are
      still in place (imcActivate, mouse mode set, etc.)
    - log "un-marked for removal (resurrect)" so the path is visible

  If the existing entry is NOT marked_for_removal, keep the old "already
  on stack" warning/refuse path.

Scope of this fix:
  Defensive only.  It resolves the *stack-level* symptom (the observed
  push/pop/push flicker log).  The "two main menu instances stacked on
  rapid Start press" report is most likely the same underlying symptom
  surfacing as visual stacking, because the legacy menudialog layer in
  src/game/menu.c goes through menuPushRootDialog which resets
  numdialogs=0 before each push — so the dialog stack itself does not
  double-stack.  If the visual stacking persists after build, the next
  round of triage should audit the Start-press -> playerPause path in
  bondmove.c for a pausemode state-machine race.

Touch points:
  port/src/inputctx.c  inputCtxPush duplicate-check branch

PHASE 4 -- KILL DOUBLE pd.ini RELOAD AT SETTINGS OPEN (DONE)
================================================================================

Problem evidence (from log):
  At 00:14.45/.46 — right after the user enters Settings — two back-to-back
  "loaded action binds from pd.ini" log lines appear, indicating
  actionmapLoadBinds() ran twice within ~17 ms.  Any input poll that lands
  between the two reloads observes a partially-populated bind table.  This
  is the most likely cause of the sporadic gameplay "NO BINDING FOUND"
  reports for vk=528 (JBTN_LB -> WEAPON_PREV) and vk=529 (JBTN_RB ->
  WEAPON_NEXT) seen in the same 7-minute session.

Root cause (port/fast3d/pdgui_menu_mainmenu.cpp):
  The Controls-tab self-init logic lives on the `s_ControlsNeedsInit`
  static bool.  Two sites flipped it to true on EVERY view/tab change:

    1) Top-level view switch (lines ~2720-2730):
         if (s_PrevView >= 0 && s_PrevView != s_MenuView) {
             ...
             s_ControlsNeedsInit = true;   // unconditional
         }

    2) Settings sub-tab switch (lines ~2734-2740):
         if (s_PrevSubTab >= 0 && s_PrevSubTab != s_SettingsSubTab) {
             ...
             s_ControlsNeedsInit = true;   // unconditional
         }

  Neither site distinguished between ENTERING the Controls view/tab and
  LEAVING it.  The open-Settings sequence was therefore:

    Frame N:     MainMenu -> Settings view    (s_PrevView 0 -> 2)
                   * view-switch fires: s_ControlsNeedsInit = true
                   * default-on-static s_ControlsNeedsInit is ALREADY true
                   * Settings view renders, Controls tab active by default
                   * Controls tab sees s_ControlsNeedsInit, runs
                     actionmapLoadBinds(), clears flag
    Frame N+1:   (no view change, no tab change, flag stays cleared)
                 ... but what if the user clicked Settings AND the Controls
                 tab came up on a new frame via post-view logic?  The
                 sub-tab change check at line 2734 fires because
                 s_PrevSubTab was still the previous menu's last known
                 value.  The tab-change branch sets the flag AGAIN -> a
                 second actionmapLoadBinds() on Frame N+1.

  Result: two reloads within one or two frames, and any input VK that was
  in-flight between them reads an incomplete table and hits the "NO
  BINDING FOUND" path.

Fix applied (port/fast3d/pdgui_menu_mainmenu.cpp lines ~2720-2745):

  1) View-switch branch — only set s_ControlsNeedsInit when LEAVING the
     Settings view (so that the next Settings enter gets a fresh init):
         if (s_PrevView == 2 && s_MenuView != 2) {
             s_ControlsNeedsInit = true;
         }

  2) Sub-tab branch — only set it when LEAVING the Controls tab:
         if (s_PrevSubTab == 2 && s_SettingsSubTab != 2) {
             s_ControlsNeedsInit = true;
         }

  The static default s_ControlsNeedsInit=true still fires once on the very
  first entry, so the first-open case is covered.  After that, the leave-
  side flag re-arms it for the NEXT entry.  At no point does an
  enter-frame set it (and then immediately consume it), which means no
  double reload.

Touch points:
  port/fast3d/pdgui_menu_mainmenu.cpp  view-switch + sub-tab-switch handlers

Collateral benefit:
  Phase 3's sporadic vk=528/529 misses are very likely the same symptom —
  see Phase 3 section below.

PHASE 3 -- SPORADIC vk=528/529 "NO BINDING FOUND" VERIFICATION
================================================================================

Summary:
  Log evidence showed vk=528 and vk=529 (JBTN_LB / JBTN_RB, bound to
  WEAPON_PREV / WEAPON_NEXT in setupGameplayDefaults) occasionally
  reporting "NO BINDING FOUND" even though their sibling presses on
  other frames routed correctly.

Hypothesis (from Phase 0 analysis):
  The double pd.ini reload at Settings open (Phase 4) clears and rebuilds
  the bind table in two steps.  actionmapLoadBinds() internally:
    - clears the existing bind entries
    - walks the pd.ini registration list
    - re-adds each binding
  Any input poll landing mid-rebuild on the first reload sees a cleared
  table; any poll landing between the first and second reload sees a
  partial table (what the first reload re-populated).  VKs that sit later
  in the rebuild order are most likely to be observed "missing".

Verification reasoning:
  Phase 4 eliminates the mid-frame rebind entirely -- s_ControlsNeedsInit
  no longer flips on an enter transition, so actionmapLoadBinds() only
  runs ONCE when the Controls tab first needs data (either static-init
  default OR the re-arm after leaving).  With only one reload per entry,
  and that reload occurring strictly inside the Controls-tab render path
  (i.e., not interleaved with live gameplay input), no gameplay frame can
  sample a partially-populated table.

Expected post-Phase-4 behavior:
  - "loaded action binds from pd.ini" log line: exactly ONE occurrence
    per Settings -> Controls tab entry (not two back-to-back).
  - vk=528/529 NO BINDING FOUND reports in gameplay: eliminated (or at
    worst reduced to actual controller edge cases, which would indicate
    a different root cause and would need separate investigation).

JUMP INVESTIGATION (related):
  Mike reported "Jump doesn't work in gameplay."  Verification:

    - ACTION_JUMP is bound in setupGameplayDefaults at
      actionmap.cpp:1339-1340:
          addBind(imc, ACTION_JUMP, VK_SPACE);
          addBind(imc, ACTION_JUMP, JOY_BTN(0, JBTN_A));
    - Consumers in src/game/bondmove.c:
          line  987: actionHeld(pi, ACTION_JUMP)    -> c1buttons |= BUTTON_JUMP
          line 1006: actionPressed(pi, ACTION_JUMP) -> c1buttonsthisframe |= BUTTON_JUMP
          line 1981: c1buttonsthisframe & BUTTON_JUMP -> wantsjump = true
            (gated on CONTROLMODE_PC, allowc1buttons, !jumpconsumed)
    - Jump trigger logic is intact; no recent changes to that path.

  Conclusion: Jump binding and consumer path are correct.  The reported
  failure is almost certainly the same root cause as the vk=528/529
  sporadic misses -- an in-flight input poll sampling a mid-reload bind
  table during the Settings-open double reload window.  With Phase 4 the
  bind table is no longer mid-rebuild during gameplay frames, and Jump
  should work reliably again.

  NOTE: This is a verification hypothesis based on code review.
  Runtime confirmation requires a live playtest after build.  If Jump
  still fails post-build, next triage should instrument the
  c1buttonsthisframe bit at line 1981 to see whether the issue is
  upstream (actionPressed not firing) or downstream (jumpconsumed stuck
  or allowc1buttons clear).
