# B-78 Fix — Chat Rate Limiting (2026-04-11)

## What changed

File: `port/src/net/netmsg.c` (+10 lines, -2 lines)

### 1. Added `CHAT_MSG_MAX_LEN 255u` constant (line 74)

The existing rate limiter (5 msg / 2s per client) capped message frequency but not
message size. `netbufReadStr` allows up to 65534-char strings. Even at 5 msg/2s, a
malicious client could push 5 × 64KB = ~320KB/s per attacker into the rebroadcast
path, amplified to every connected peer.

Added `CHAT_MSG_MAX_LEN 255u` to the rate-limiter constants block.

### 2. Length check in `netmsgClcChatRead` (before rate-limit check)

```c
if (strlen(msg) > CHAT_MSG_MAX_LEN) {
    sysLogPrintf(LOG_WARNING, "NET: chat message too long from client %u — dropped", srccl->id);
    return src->error;
}
```

Oversized messages are dropped before they touch the rate-limiter ring buffer.
Server logs a WARNING with the client ID for operator visibility.

### 3. Removed dead `char tmp[1024]` from `netmsgSvcChatRead` (B-84)

Client-side chat handler had an unused 1KB stack variable from an earlier draft.
Removed — the handler only needs the `netbufReadStr` return value.

## Why the rate limiter alone wasn't enough

Rate limit: 5 msg / 2s = 2.5 msg/s max per attacker.
Without size cap: 2.5 × 64KB = 160KB/s per attacker, amplified to N peers.
With size cap: 2.5 × 255B = ~637B/s per attacker. Amplification is negligible.

## What was NOT changed

- The ring-buffer rate limiter logic itself — correct as written.
- `s_ChatRate` reset on disconnect: not done (requires touching net.c, out of scope).
  New client in a recycled slot inherits old timestamps, may be blocked up to 2s —
  acceptable false positive for a security guard, self-heals after the window expires.
- Protocol version: unchanged (255-char limit is a server policy, not a wire change).
