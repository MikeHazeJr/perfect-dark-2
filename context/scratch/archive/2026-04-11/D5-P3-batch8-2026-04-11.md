### 3.3 Audit conclusions

1. **No new shadow/cache copy was introduced.** Every Batch 8 ImGui
   writer routes its MENUOP_SET through a legacy C handler via the
   s206 call-through.  Those handlers touch exactly the same globals
   the legacy renderer's menuitem dispatch would have touched -- the
   host match-start (`mpStartMatch` + `mpConfigureQuickTeam*`), the
   network serializer (`netmsgClcSettingsWrite`, `netmsgSvcStageStartWrite`),
   the client receive path (`netmsgSvcStageReceive`), and the endscreen
   all see identical state to a pure-legacy dialog interaction.

2. **The one network-propagating write (team switch) uses the same
   path as the legacy in-game dropdown**: `g_NetLocalClient->settings.team`
   -> `g_NetLocalClient->config->base.team` -> `netClientSettingsChanged()`
   -> `CLC_SETTINGS` packet.  Server authoritatively updates its copy,
   re-broadcasts.  This is a mid-match write; no match-start reader is
   involved because the match is already running.

3. **Display options are per-player local preferences and never
   serialized on the wire.**  `scenarios.c` and `radar.c` read
   `g_PlayerConfigsArray[g_MpPlayerNum].base.displayoptions` each
   frame, so a mid-match checkbox toggle takes effect on the next
   render.  The field IS persisted to the player file via the save
   buffer, so a user who changes display options during a match AND
   saves their player afterwards will have the new settings persist to
   their next session -- matching legacy exactly.

4. **`g_MpSelectedPlayersForStats` is local view state**, not match
   state -- writing to it has no network effect.  It's an 8-byte
   per-player array indexed by `g_MpPlayerNum` (0..3 for split-screen,
   always 0 on PC) that records which other player the current viewer
   wants the kill matrix to show.

5. **Inventory equip writes** (`bgunEquipWeapon2`) use the exact same
   path the player already uses during normal gameplay when they
   press "Next Weapon" or scroll the wheel.  The existing netplay
   weapon-state broadcast (carried as part of the client's per-tick
   state snapshot) propagates the change to other clients.  Zero
   protocol change.

6. **Modern room-lobby path is untouched.**  `port/fast3d/pdgui_menu_room.cpp`
   writes to `g_MatchConfig` via the SETTINGS struct flow.  Batch 8
   dialogs are only reachable during a LIVE MATCH, after
   `matchStart()` has already copied `g_MatchConfig` → `g_MpSetup`.
   The two paths do not interleave.

7. **`mainEndStage()` path for End Game is unchanged**: the push to
   `g_MpEndGameMenuDialog` still calls through to the legacy
   `menuhandlerMpEndGame` which already handles both solo/local
   (`mainEndStage()`) and client-netplay (`netDisconnect()`) cases.

8. **Pre-existing (out of scope) hazard**: the legacy in-match Team
   dropdown was `static` at the C level but functionally identical to
   the non-static `menuhandlerPlayerTeam` pre-match dropdown -- they
   both write team assignments but to DIFFERENT backing globals
   (in-match = `g_NetLocalClient->settings.team`, pre-match =
   `g_Vars.mpplayerteams[player]`).  The pre-match path is Batch 7's
   concern; the in-match path is Batch 8's.  There is no cross-traffic
   because the pre-match field is only read by
   `mpConfigureQuickTeamPlayers` at setup time and never again during
   the live match.

### 3.4 Why Batch 8 was lighter than Batch 7

Batch 7's surface area spanned 11 dialogs writing to ~13 distinct
fields (quick-team mode, scenario override, per-player teams, sim
counts, sim difficulty, lock type, save flags, etc.), all of which
feed the match-start path.  Batch 8 has only 1 network-propagating
write (the in-match team switch) and everything else is either
read-only display or local player preference.  The audit surface is
correspondingly smaller, but the **philosophy and methodology** --
trace every writer to its backing global, verify the match-start and
match-end readers see the same state as legacy, confirm no new shadow
copy -- is identical.

## 6. Integration pattern notes

### 6.1 Standalone-file approach (following Batch 7 template)

Per Mike's confirmed direction: enhance the existing room / pause
flow, do not break it.  Batch 7 established that a new standalone
`pdgui_menu_*.cpp` file + a single line in `pdgui_menus.h` is the
right shape when the batch's dialogs are a cohesive navigation
surface (not inline additions to `room.cpp`'s matchslot layout).

Batch 8's 6 dialogs are a LIVE-MATCH pause menu -- they don't touch
the room lobby at all.  They fire when the player presses PAUSE
during a running match.  So the "enhance room flow" concern does
not apply here directly; what applies is "do not break the live
match".  The standalone file pattern is perfect for this: hot-swap
registration + no edits to other ImGui files + no modification of
the legacy dialog defs themselves.

### 6.2 `pdgui_menu_mpingame.cpp` is reserved for overlays

There's a pre-existing file with a similar name
(`pdgui_menu_mpingame.cpp`, 323 lines) that owns the in-match kill
ticker overlay + legacy endscreen dialog suppression.  It is NOT a
pause-menu file and must not be polluted with pause-dialog renderers.
Batch 8 lives in `pdgui_menu_mppause.cpp` for clean separation.  The
`pdguiMpIngameRegister()` function (in the overlay file) and the
`pdguiMenuMpPauseRegister()` function (new, Batch 8) are both called
from `pdguiMenusRegisterAll()`.

### 6.3 Bridge accessor for `g_BossFile.teamnames`

Rather than cloning `struct bossfile` locally, Batch 8 introduces a
single new bridge function `pdguiMppGetTeamName(u32 team)` in
`port/fast3d/pdgui_bridge.c` (which is C and has the real types.h
in scope).  Keeps the C++ renderer file struct-layout-free for this
one field.  The `mpchrconfig_mpp` / `ranking_mpp` clones are kept
for the ranking API because `mpGetPlayerRankings` / `mpGetTeamRankings`
return pointers to `struct mpchrconfig` -- adding bridge wrappers
for those would be 8-10 accessors (name, team, placement,
killcounts[], numdeaths, numpoints, etc.) which is more invasive
than a layout-compatible local struct clone.  Consistent with the
existing pattern in `pdgui_menu_pausemenu.cpp` +
`pdgui_menu_mpingame.cpp`.

### 6.4 C++ default arguments

`hubPushRow` and `hubHandlerRow` use C++ default parameters
(`rightSideText = nullptr`, `param = 0`).  Same pattern as Batch 7.
Compiles fine in the C++ translation unit.

### 6.5 s206 shadow struct

Cloned from s205 (`pdgui_menu_mpadvanced.cpp`) with the s20X suffix
bumped by one.  ABI-compatible with `handlerdata` / `menuitem` from
`src/include/types.h:3342..3417`.  The independent definition means
no header changes are needed.  The helpers under the shadow
(`dd_Get*` / `dd_Set` / `dd_IsHidden` / `plain_Set` / `list_Get*` /
`list_Set` / `cb_Get` / `cb_Set`) are a superset of the ones used by
Batch 7 because Batch 8 has more variety of item types (list,
checkbox, dropdown, plain SET).

### 6.6 `static` removal in ingame.c

Two C handlers (`menuhandlerNetTeamSwitch`,
`menuhandlerNetPauseControls`) were file-local `static` in ingame.c.
The C language has no reason to keep them file-local -- they're only
used in one menuitem array, but that was an artifact of how the
legacy menu system worked (item arrays are addressed by their
enclosing file's static scope).  Exposing the symbols is a 2-word
edit with zero semantic change; there are no name collisions because
the symbols are nowhere else in the codebase (grepped).

Batch 7 did the same kind of expansion implicitly: many of the
