Per Mike's standing rule ("Ensure any network play properly passes menu info into the relevant match start / end procedures"), every state field the Batch 10 renderers touch was traced end-to-end. Summary: 12 of 12 dialogs are LOCAL-ONLY; none propagate over the wire.

| Bio List / Profile | `g_ChrBioSlot` | `g_ChrBioSlot` (data.h) | None | LOCAL-ONLY — bios are CI-visited SP content; no stat counter or wire field |
| DT List / Details | `g_DtSlot`, `dtBegin/dtEnd` sets up `g_DeviceTrainingData` | `g_DtSlot` (data.h), `g_DeviceTrainingData` (`data.h`) | None | LOCAL-ONLY — device training is SP-only, `dtBegin/dtEnd` only affect local player state |

## Model Preview Pipeline (Batch 0 consumption)

Batch 10 uses all three preview kinds wired in Batch 0:

- **CHARACTER**: `pdguiModelPreviewDraw(head_id, body_id, x, y, w, h, opts)` — used by `renderBioProfile`. Catalog IDs resolved via the new `pdguiTrBioGetCurrentChrCatalogIds` bridge helper (bodynum → mpbodynum → catalog ID + default paired head).
- **WEAPON**: `drawFilenumPreview(PDGUI_PREVIEW_WEAPON, filenum, ...)` — used by `renderDtDetails` and `renderHtDetails`. Filenum resolved via `pdguiTrDtCurrentWeaponFilenum` / `pdguiTrHtCurrentWeaponFilenum`, both of which call `weaponGetFileNum` on the current slot's weapon num.
- **VEHICLE**: `drawFilenumPreview(PDGUI_PREVIEW_VEHICLE, filenum, ...)` — used by `renderHangarVehicleHolograph`. Filenum comes from the bridge-mirrored `biovehicleitem[]` table (FILE_PDROPSHIP / FILE_PHOVERCRATE1 / FILE_PHOVBIKE / FILE_PHOOVERBOT / FILE_PDD_HOVERCOPTER / FILE_CCHICROB / FILE_PA51INTERCEPTOR / FILE_PELVIS_SAUCER / FILE_PSK_SHUTTLE).

`drawFilenumPreview` is a file-local helper in `pdgui_menu_training.cpp` that wraps the `pdguiCharPreviewRequestFilenum` → `pdguiCharPreviewGetTextureId` → `dl->AddImage` loop, mirroring the visual style of `pdguiModelPreviewDraw` (background frame, border, placeholder silhouette, label slot, idle rotation). It does not live in `pdgui_model_preview.cpp` to avoid churn in the shared module; if a future batch needs the same filenum-keyed API from another file, we can promote it.

The existing `pdguiCharPreviewRequestEx` / `pdguiCharPreviewRequestFilenum` paths in `pdgui_charpreview.c` already support WEAPON (renders via MENUMODELTYPE_HUDPIECE) and VEHICLE/PROP (renders via MENUMODELTYPE_DEFAULT). No changes needed to `pdgui_charpreview.c` or `pdgui_model_preview.cpp` — the Batch 0 infrastructure was complete.

## Controller Diagram Decision

The legacy `g_SoloMissionControlStyleMenuDialog` layout uses a `MENUITEMTYPE_CONTROLLER` item that renders a texture of the N64 controller with overlaid button labels pertinent to the selected control mode. Per Mike's standing direction and the plan's "ImGui diagram (no 3D needed)" guidance, the Batch 10 renderer replaces this with a text panel that lists the actual button → action mapping for the hovered mode.

Each of the 9 control modes has a short 5-7 line text block describing:
- Left stick role (Move / Look / Strafe)
- C buttons role (Move / Look / Turn)
- A/B button roles (Jump/Accept, Crouch/Cancel)
- Z/R trigger roles (Fire, Aim)
- Start (Pause menu)

For modes 2.1-2.4 (dual-controller), we annotate "dead on PC" since the port already removed 2P splitscreen (constraint `No local multiplayer` added 2026-04-10). The Ext (PC) entry describes the WASD+mouse keyboard routing that the action-map system provides.

This is information-equivalent to the legacy texture diagram (which showed a static N64 controller with labels) but adapted to the PC keyboard/gamepad input layer and readable in any language's font.

## MENUOP_* Opcodes

Not used in this batch because every renderer delegates via concrete bridge accessors (`pdguiTr*`, `pdguiCd*`) rather than through the shadow-struct call-through pattern (s207/s208). The shadow-struct pattern is beneficial when the legacy handler is a switch statement with many MENUOP_* branches and the ImGui renderer wants to reuse all of them. The Batch 10 legacy handlers (`frWeaponListMenuHandler`, `ciOfficeInformationMenuHandler`, `dtDeviceListMenuHandler`, `htHoloListMenuHandler`, `ciHangarInformationMenuHandler`, `menuhandlerControlStyleImpl`, `menuhandlerMpControlCheckbox`, `menuhandlerMpAimControl`) are mostly simple 3-5 branch handlers where each branch maps cleanly to a single bridge accessor call. Direct accessors are lighter and easier to audit.
