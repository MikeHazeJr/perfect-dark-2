PHASE 2 — 1080p SCALING BASELINE FLIP
=============================================================================

Rationale
  context/designs/d5-full-menu-overhaul.md is the authoritative design
  spec.  Its UI Scaling section specifies 1080p as the reference
  resolution and writes every pixel constant (heading 36, body 24,
  small label 16, button height 64, etc.) against that baseline.  The
  implementation in pdgui_scaling.h was carrying a 720p baseline from
  before the spec was written, so every literal in menu code was
  implicitly "N at 720p" while the doc wrote "N at 1080p" for the same
  conceptual value.  S192 Batch 0 flagged this as deferred item D-3.

Approach
  1. Flip pdgui_scaling.h scale factor to displayH / 1080.0f.
  2. Rewrite all pdguiScale() literal arguments x1.5 so that product
     `literal * scaleFactor` produces the same pixel at every
     resolution.  This is a pure source-code rename of the reference
     resolution — visual output is identical before and after.

Reference values (from d5-full-menu-overhaul.md, 1080p column)
  Menu heading           36
  Body text / items      24
  Small UI labels        16
  Button height          64
  Min focus/click target 48
  Window padding         16
  Item spacing            8
  Scrollbar width        14

Baseline constants changed — pdgui_scaling.h
  pdguiScaleFactor()    displayH/720.0f          -> displayH/1080.0f
  pdguiMenuWidth cap    1200.0f  * scaleFactor   -> 1800.0f * scaleFactor
  pdguiBaseFontSize     16.0f  (small-label 720) -> 24.0f  (body-text 1080)
  PDGUI_REF_WIDTH       (new macro)              -> 1920.0f
  PDGUI_REF_HEIGHT      (new macro)              -> 1080.0f

Baseline constants changed — pdgui_layout.cpp (action bar metrics)

  PDGUI_AB_BODY_MIN_PX       60 -> 90

Baseline constants changed — pdgui_backend.cpp (safe area fallback)

  Raw fallback height  720.0f -> 1080.0f

Architectural choice

  Rather than scatter new per-dialog renderers across three files, the
  delivery upgrades the existing typed dialog renderer in
  pdgui_menu_warning.cpp so every DANGER/DEFAULT/SUCCESS dialog gets
  the Batch 1 improvements automatically — scrim, literal-text label
  fix, slider support — and then adds a dedicated PC placeholder
  renderer for the four filemgr pak-era dialogs whose MENUITEMTYPE_LIST
  items the generic renderer cannot handle.

  This is architecturally cleaner than the plan's "one new renderer per
  dialog" suggestion: the upgrade benefits every type-fallback dialog
  (not just the seven), and each Batch 1 dialog still gets an explicit
  hotswap registration so ownership is visible in the hotswap log.

Key upgrades to pdgui_menu_warning.cpp

  1. #include "pdgui_layout.h" — brings in the S192 docked action bar +
     popup scrim primitives.

  2. Popup scrim primitive adopted:
       pdguiPopupDarkenBehind(0.55f);
     called at the top of renderTypedDialog().  Replaces the scattered
     ad-hoc GetBackgroundDrawList rectangles that were never quite
     consistent.  Every typed modal now has a matching dimmed
     background behind it.

  3. Literal text label support (fixes g_ExitGameMenuDialog regression):
     BEFORE:
       getItemLabel() unconditionally called langSafe((s32)param2),
       which interpreted the raw C-string pointer bits of
       g_ExitGameMenuItems[0]'s label ("Are you sure you want to
       exit?") as a lang index -> crash or empty text.
     AFTER:
       getItemLabel() checks MENUITEMFLAG_LITERAL_TEXT (0x08000000)
       first and returns the raw pointer as a const char*.  Every
       legacy dialog with a literal-text LABEL now renders correctly.

  4. Slider item support (enables g_PdModeSettingsMenuDialog):
     New MENUITEMTYPE_SLIDER case in the item iteration loop.  Calls
     the item handler with MENUOP_GETSLIDER / MENUOP_GETSLIDERLABEL to
     fetch the current u32 value and a label string, renders an
     ImGui::SliderInt(0, 255), writes back on change via MENUOP_SET,
     and plays PDGUI_SND_SUBFOCUS on value-change edges.

  5. renderFilemgrPcPlaceholder() — dedicated new renderer (~120 lines)
     for the four pak-era filemgr dialogs that use MENUITEMTYPE_LIST
     items.  On PC those list items are never populated (no controller
     paks), so the dialog would render as an empty list under the
     generic fallback.  The placeholder:
       - Scrim-darkens the background
       - Draws a PD-authentic dialog frame with title from getDialogTitle
       - Body text explains that PC agent management goes through
         Agent Select, and that saves live in saves/agent_<name>.json
       - Docks a single OK button using pdguiBeginActionBar /
         pdguiActionBarButton
       - Dismisses on Escape / B button
     This is a safety net: the dialogs are unreachable in the normal
     PC flow, but if fringe code paths ever push one, the player sees
     a clean informational card instead of a broken list.

  6. Explicit Batch 1 hotswap registrations:
     pdguiMenuWarningRegister() now explicitly registers all seven
     Batch 1 dialogs so the hotswap log clearly shows who owns each.
     Previously they would fall through the type-based fallback
     anonymously.

Deferred items (Phase 3)

  D3-1. Per-handler sound cues on slider drag (continuous feedback)
        SND_SUBFOCUS fires on every step; some designs want SND_TICK
        at lower volume.  Not specified in d5, kept simple.

  D3-2. Keyboard up/down arrow to tab between selectables in the
        docked action bar is provided by ImGui's default nav; the
        custom focus highlight ring is not drawn in the type fallback.
        The type fallback uses ImGui::Button, not pdguiActionBarButton.
        This keeps the generic renderer simple and avoids the "who
        owns focus state" problem.  The S192 pdguiActionBarButton
        primitive is still used by the new renderFilemgrPcPlaceholder.

  D3-3. Filemgr Delete / Copy / Operations as actual list pickers.
        Intentionally not implemented — the N64 controller pak saves
        do not exist on PC.  The PC placeholder points the player at
        the correct PC equivalent (Agent Select).  The real filemgr
        dialogs remain unreachable from the normal PC flow; this
        delivery is a safety net, not a port.
