Phase 4.1 — Extend pdgui_menu_warning.cpp typed-dialog primitive

Added item types and ops to the shadow declarations so the switch in
renderTypedDialog can handle Cheats items natively:
  - MENUITEMTYPE_CHECKBOX (0x09)
  - MENUITEMTYPE_MARQUEE  (0x17)
  - MENUOP_GETOPTIONCOUNT (1)
  - MENUOP_GETOPTIONTEXT  (3)
  - MENUOP_GETSELECTEDINDEX (7)
  - MENUOP_GET            (8)
  - MENUOP_CHECKDISABLED (12)

Added shadow structs for checkbox/dropdown handlerdata:
  - handlerdata_checkbox { u32 value; }
  - handlerdata_dropdown { uintptr_t value; uintptr_t unk04; }

getItemLabel() extended to implement the legacy menuResolveText() contract
from src/game/menu.c:490:
  - param2 < 0x5a00         -> lang text ID, call langSafe()
  - param2 == 0             -> empty string
  - param2 >= 0x5a00        -> function pointer char*(*)(struct menuitem *)
    — this is the case cheats.c uses for `cheatGetNameIfUnlocked`.

Without this fix the Cheats screens would render every cheat as garbage
text because langSafe() would interpret the function pointer bits as a
lang index.

Phase 4.2 — CHECKBOX case in renderTypedDialog

  - getItemLabel() provides the dynamic label.
  - MENUOP_GET reads the current state (cheatCheckboxMenuHandler returns
    the value directly as the function's return code; we fall back to
    data->checkbox.value if the handler doesn't return).
  - MENUOP_CHECKDISABLED reads the locked-cheat state; disabled items
    render via ImGui::BeginDisabled()/EndDisabled() so locked cheats are
    visible but uninteractable.
  - Toggle plays PDGUI_SND_TOGGLEON / PDGUI_SND_TOGGLEOFF per state flip.
  - MENUOP_SET writes the new value via data->checkbox.value.
  - PushID on the item pointer gives each checkbox a stable unique ID.

Phase 4.3 — DROPDOWN case in renderTypedDialog

  - Enumerates options via MENUOP_GETOPTIONCOUNT (count in dropdown.value)
    and MENUOP_GETOPTIONTEXT (text returned as function code OR via
    dropdown.unk04 depending on the handler).
  - Reads current index via MENUOP_GETSELECTEDINDEX.
  - Renders as ImGui::BeginCombo with one Selectable per option.
  - On change, writes the new index via MENUOP_SET with dropdown.value,
    plays PDGUI_SND_SUBFOCUS audio cue.
  - Fallback "Option N" label if the handler returns empty text.

Phase 4.4 — MARQUEE case in renderTypedDialog

  - Legacy marquee items are scrolling text banners (e.g., "Cheat Available").
  - ImGui has no native marquee; render as centered dimmed text.
  - getItemLabel() resolves the callback form (the cheat marquee uses
    `cheatGetMarquee` which returns the currently-applicable banner text).

Phase 4.5 — Explicit hotswap registrations

Added 9 Cheats dialogs to pdguiMenuWarningRegister() with renderDefaultDialog
(or renderDangerDialog for the warning/confirm dialogs).  Registrations are
idempotent and live alongside the existing Batch 1 explicit registrations.

Announced start: S195 Phase 3

Rationale for bundling: Batches 8, 11, and 12 all consist of legacy PD
dialogs that use only the typed-dialog item primitives (LABEL / SEPARATOR /
SELECTABLE / CHECKBOX / DROPDOWN / MARQUEE / KEYBOARD / SLIDER) plus one
or two complex item types (LIST / PLAYERSTATS / RANKING).  The Batch 4
extension of renderTypedDialog already covers every simple item type.
Complex item types render as visible `[label]` placeholders — a clean

STOPPING DECISION
=============================================================================

After Batches 3, 4, 8, 11, 12 landed and built green, next candidate is
one of:

  - Batch 5 — MP Setup Core (Arena/Weapon/Scenario/Limits, ~14 screens)
  - Batch 6 — Bot Simulant Setup (5 screens)
  - Batch 7 — MP Advanced/Quick paths (11 screens)
  - Batch 10 — Training NULL-FN (12 screens, needs 3D preview and LIST)

Weighing factors for the stopping decision:

  1. Context pressure — we have executed 5 batches in this session plus
     foundational audit work.  Quality at each gate has been verified.
     Context is still sufficient, but the remaining batches all require
     significantly more code per dialog, not just registrations.

  2. Remaining batches need primitives not yet extended:
     - Batch 5 scenario options are CHECKBOX / DROPDOWN heavy and might
       work with the Batch 4 extension, but arena/weapon pickers are
       LIST-heavy.  Not a pure registration pass.
     - Batch 6 bot setup uses CAROUSEL + LIST + CHARACTER preview — needs
       more primitive extensions.
     - Batch 7 is mostly navigation hubs — could be registrations, but
       each one has its own data model tied to setup.c machinery.
     - Batch 10 needs the Batch 0 model preview pipeline to be wired into
       a NULL-renderer replacement strategy for every TRAINING dialog.

  3. LIST primitive extension — adding MENUITEMTYPE_LIST to the typed
     dialog would unlock ~20 additional dialogs across multiple batches
     in one focused extension pass.  This is the next highest-leverage
     investment and should be the first item of the NEXT session, not a
     rushed addition at the end of this one.  Writing LIST without a
     clean audit of the LIST items it needs to support (data model,
     scroll, group categorization, focus tracking, custom-render hook)
     risks regression.

  4. Quality over volume — Mike's standing order is "volume delivered
     under the same quality bar".  Tacking more batches onto this session
     with rushed LIST support or half-implemented primitives would break
     the quality bar.

Decision: STOP at a clean boundary.  Batches 3, 4, 8, 11, 12 landed with
clean merges, green builds, and documented deferred items.  Batch 5 and
onwards are the right starting point for S196.
