# Deep Project Audit Report -- Perfect Dark 2

> **Scope**: Full audit on `dev` branch at commit `5c059f65`. Worktrees explicitly
> disregarded per scheduled-task instruction. Findings target the live `dev` tree
> only. Skill: `super-audit` (scheduled run, 2026-06-12).

## 1) Inferred Project Goal & Intended Outcomes

### Inferred Purpose

Perfect Dark 2 is a fan re-engineering of Rare's *Perfect Dark* (N64, 2000),
descended from `n64decomp` -> `fgsfdsfgs/perfect_dark` `port-net` ->
`jonaeru/perfect_dark` `allinone-latest`, and now substantially rewritten with
PD2-native pillars:

- A **Catalog** as the single authoritative store for every asset family
  (weapons, bodies, heads, arenas, scenarios, models, meshes, materials,
  textures, audio, fonts, lang, animations, props, projectiles, entities,
  vehicles, songs, gamemodes, botprofiles, themes, hud, ui, missions, effects).
- An **equal-footing content pipeline** where mod and native assets traverse
  the same loader, resolver, network, and renderer paths (`.pdmod` -> catalog
  registration -> stage manifest -> live render, with the same hot-registration
  pipeline reached by both file-system scan and friend-network distribution).
- A first-class **modding pipeline** with public typed archives (`.pdarena`,
  `.pdweapon`, `.pdmesh`, `.pdscenario`, ...), strict packager
  (`modpackPdmodFromFolder`), validators (`asset_native_source_guard.py`,
  `verify_pdxxx_modder_workflow.py`), and a release-validated `.pdmod`
  transport.
- **The Grid** -- a UDP/Ed25519-signed cross-peer share layer
  (`social_share.c`, port 27109) carrying mod manifests, profile stats,
  listening-room playlists, and mod-request handoff to `file_transfer.c`.
- A **client online mode** with ENet listen-host (`g_NetDedicated == 0`),
  6-tier P2P escalation (`p2p.c`: LAN/DIRECT/STUN/UPnP/ICE/TURN), connect-code
  sentences (no raw IP in UI), and a single-local-player constraint.
- A **game-agnostic dedicated server** target (`pd-server.exe`). **NOTE: per
  S486 (2026-04-27) and feedback memory `feedback_no_pd_server_build`, this
  target is deprecated and not part of routine verification.** The intended
  game-agnostic plugin ABI (`pd-server-plugin-abi.md`) is still on file as a
  deferred design.

### Likely Player & Contributor Types

- PD / GoldenEye N64 veterans
- Speedrunners and competitive challenge-mode players
- Modders (asset authors using DCC GLTF/OBJ/WAV/MIDI workflows)
- Casual online / LAN groups (4-8 humans + bots)
- Single contributor (Mike) shipping the live engine; sub-agents and worktree
  sessions author code, Mike compiles and tests via `build-session.ps1`
- No active dedicated-server operators (target deprecated)

### Core Workflows / Gameplay Loops (Inferred)

1. Solo Combat Sim + 21-stage solo campaign.
2. Listen-host MP: leader picks scenario/arena/weapons -> ready gate -> stage.
3. Co-op / Counter-Op campaign with `SVC_BOT_AUTHORITY` delegation.
4. Mod authoring: edit public typed archive -> pack `.pdmod` -> share via
   Grid -> peer pulls via `file_transfer.c` -> installed-disabled with
   enable-prompt -> live render through catalog.
5. Friend network: presence + share aggregator + listening room + transfer.

### Upstream Lineage Observations

- **`n64decomp` inheritance** is concentrated in `src/game/`, `src/lib/`,
  `src/include/`. Identifiers `s32/u8/f32`, `g_Vars`, `chrdata`, decompiled
  funcs (`func0f069b4c`), and the `MAX_PLAYERS == 8` ceiling all originate
  there. The catalog rewrites have not removed the legacy slot tables but have
  reframed them as private migration debt (see `constants.md`).
- **`port-net` inheritance** is concentrated in `port/src/net/`. The 8-player
  ENet ceiling has been lifted to `NET_MAX_CLIENTS == 32` and the participant
  pool to `PARTICIPANT_DEFAULT_CAPACITY == 32`, but **the wire still carries a
  single `u64` active-slot mask**, hard-capping any future expansion at 64
  slots. Many `SVC_*/CLC_*` handlers iterate `for (i = 0; i < MAX_PLAYERS;
  i++)` rather than the participant pool, which is the *N64-era player-count
  loop* signature.
- **`allinone` inheritance** has been almost entirely retired in the catalog
  rewrite: `g_ModNum`, `g_ModBodies[]`, `g_ModHeads[]`, `g_ModArenas[]`,
  `modconfig.txt`, monolithic mod swap, and shadow asset arrays are gone
  (constraints.md 2026-03-24 entries). The component-based modding pipeline
  (`mod.json`, `.pdmod`) is fully PD2-native.
- **Catalog system, Grid, modding pipeline, connect codes, swarm sync, ready
  gate, file-transfer enable-prompt, P2P 6-tier orchestrator, identity cookie,
  RCON admin, persistent bans, room passwords, session catalog wire IDs** are
  all PD2-authored.

### Pillar Observations

- **Catalog SOT**: Strongly enforced in `src/game/`. `g_HeadsAndBodies[]`
  direct dereference outside the catalog layer is gone (only in
  `assetcatalog.c`/`assetcatalog_api.c`/`modelcatalog.c`). Asset references
  on wire/save/manifest are catalog ID strings. Private integer bridges
  (`MODELNUM_*`, `bodynum`, `headnum`, `filenum`) exist only as
  catalog-internal slot allocators -- per `constraints.md` 2026-06-08 these
  are explicitly migration debt, not identity.
- **Mod-native Parity**: `assetcatalog_load.c` walks both bundled and
  non-bundled (mod) entries through the same lifecycle and registers mod
  overrides in the reverse index alongside bundled records. The `is_mod`
  / `bundled` distinction survives at the load-source level (where it has to
  -- the file path differs), but downstream consumers (render, manifest,
  match) are symmetric. **However**, several legacy fallback paths exist
  where `e->bundled` triggers ROM-provider fast-path while mods always take
  the file-provider path; these have not yet been unified.
- **Modding Pipeline**: `modpack_pdmod.c` packager + `modmgrValidateArchiveFile`
  + `modmgrInstallArchiveFile` + `verify_pdxxx_modder_workflow.py` is the
  authored chain. Deterministic per the current evidence (sha256 round-trip
  tests pass per 2026-06-11 session-log). Bytes-in/bytes-out pdmod packaging
  is verified.
- **Grid Trust**: `social_share.c` signs every outbound UDP frame with Ed25519,
  enforces friend-handle TOFU lock, rate-limits inbound, and bounds payload
  reads. `socialFriendByHandle` + `socialBlockIsHandle` + `rateLimitAllow` are
  required prior to dispatch. Strong design.
- **Online-mode Boundary**: Listen vs dedicated split is clear at
  `g_NetDedicated`. Distinct CLC_AUTH paths skip ROM/mod checks on dedicated.
  `g_NetLocalClient == NULL` discipline is observed in connect handler with
  defence-in-depth (B-327 fix).
- **Dedicated-server Boundary (game-agnostic)**: **Critically incomplete**.
  `server_stubs.c` (518 lines) stubs the entire PD2 game tree into the
  server binary; PD2-specific globals (`g_MpSetup`, `g_PlayerConfigsArray`,
  `g_BotConfigsArray`, `g_MissionConfig`, `g_MatchConfig`) and PD2 game
  message handlers are compiled directly into `pd-server`. There is no
  plugin ABI; the "game-agnostic dedicated server" pillar exists in design
  doc form (`pd-server-plugin-abi.md`) but not in code. Per shipping decision
  S486 this is intentionally deferred but it means the pillar as written in
  the audit prompt is not represented in the live source.
- **Scaling**: Mixed. The PC port has lifted player count from 4 to 8 and bot
  count to 32, but `MAX_PLAYERS == 8` is hardcoded, the wire active-slot
  mask is `u64` (cap 64), `u8 player_mask` bit-encodings throughout cap at
  8, and ~70 `for (i = 0; i < MAX_PLAYERS; i++)` loops in `src/game/` are
  visual N64-shape player-count loops even where the symbol is present.

### Assumptions / Unknowns

- Live behaviour of the c3849 Wave 7 weapon-graph runtime (`Debug.WeaponGraphRuntime`)
  default-OFF -- not under test in this static pass.
- Live B-801 source-only fatal-cutover safety: gated on Mike's playtest call,
  not verifiable here.
- pd-server binary trust boundary: not exercised by routine smoke (target
  deprecated) so any boundary regressions could survive unnoticed until a
  future plugin-ABI implementation date.
- The 6-tier P2P orchestrator under real NAT: only one-tier sanity covered
  in static scan; live trial would need to validate STUN/UPnP/ICE/TURN cascade.
- IPv6 hosting: the connect-code system encodes IPv4 only; if STUN returns
  an IPv6 mapped address, that hosting path appears unexpressible to a peer.

## 2) Design Intent & Gameplay / Multiplayer Fit Review

### System & Workflow Validation Findings

#### Critical Issues

- **Dedicated-server boundary discipline pillar unrepresented in code**
  - Severity: Critical
  - Confidence: Confirmed
  - Location: `port/src/server_stubs.c` (entire file, 518 lines);
    `port/src/server_main.c:243` (`g_NetDedicated = 1`);
    deferred design at `context/designs/connectivity/pd-server-plugin-abi.md`
  - Lineage: Authored-in-PD2 (legacy `port-net` foundation; PD2 added the
    aspirational plugin pillar but did not yet implement it)
  - Pillar Impact: Dedicated-server Boundary
  - Defect Class: Trust-Boundary
  - Intended Outcome (per audit prompt): A PD2-agnostic dedicated-server core
    with PD2 game semantics behind a per-game plugin / ABI boundary, capable
    of hosting other games and isolating multi-tenant sessions.
  - Current Behavior: `pd-server` is a `g_NetDedicated == 1` build of the
    whole PD2 game tree, with every game global stubbed by `server_stubs.c`
    (`g_MpSetup`, `g_BotConfigsArray`, `g_PlayerConfigsArray`, `g_MatchConfig`,
    `g_MissionConfig`, `g_ChrSlots`, `g_ObjectiveStatuses`, ...). PD2-specific
    message handlers (`netmsg.c`, `matchsetup.c`, `mplayer/participant.c`) are
    compiled directly into the server. There is no plugin boundary, no
    per-game ABI, no multi-tenant isolation, and no game-agnostic core.
  - Gap / Failure Mode: The dedicated-server pillar exists as design but not
    as architecture. Per S486 (2026-04-27, see `constraints.md`) the shipping
    scope was narrowed to listen-host, so this gap is *deliberately deferred*,
    but the audit-prompt pillar is materially absent.
  - Why It Matters: Future plugin-ABI work cannot extract PD2 semantics
    cleanly without significant refactoring of `netmsg.c`, the participant
    pool, the catalog lifecycle, and the manifest pipeline -- all of which
    have grown PD2-specific assumptions in the deferral period.
  - Risk If Not Fixed: When plugin-ABI work resumes, the server core will
    need rework not just for ABI definition but for full extraction of PD2
    semantics that have continued to accrete. Estimated cost grows with each
    new wire-protocol bump (v44 -> v50 already added MP-specific opcodes).
  - Recommendation: If pillar remains genuinely deferred, capture explicit
    "frozen surface" notes in `pillars/server.md` so new wire/manifest work
    avoids tightening PD2 coupling on the server side. If pillar is to be
    rescued, fork the work now: identify the actual game-agnostic primitive
    set (auth + rooms + bans + RCON + transport + manifest distribution),
    move `netmsg.c` PD2 handlers behind a `pd2_plugin_*` table, and stop
    compiling `participant.c` and `mplayer.h` into the server build.
  - Cross-System Changes Required: Yes (server build target, netmsg.c,
    participant.c, manifest, RCON, banlist, identity cookie)
  - Blocks Intended Outcome?: Yes (for the game-agnostic pillar)

#### High Priority Findings

- **MAX_PLAYERS == 8 is a hard cap that propagates through wire, masks, save,
  UI, and hand-rolled player loops**
  - Severity: High
  - Confidence: Confirmed
  - Location: `src/include/constants.h:44` (`#define MAX_PLAYERS 8`);
    duplicate at `port/include/pdgui_constants.h:20`;
    `PLAYERCOUNT()` macro at `src/include/constants.h:103-112` branches on
    `MAX_PLAYERS` value with hand-coded `?:` chains capped at 8;
    `playerCutsceneActiveMask` at `src/game/player.c:330` (`for (i = 0; i <
    MAX_PLAYERS && i < 8; i++)` plus `u8 mask`);
    `netpreservedplayer.killcounts[MAX_MPCHRS]` packs s16 by index;
    `s_ReadyGate.expected_mask`/`ready_mask`/`declined_mask` are `u32`
    (`port/src/net/netmsg.c:300-303`);
    SVC_STAGE_START active-slot `u64 active_mask` at `port/src/net/netmsg.c:1550`
  - Lineage: Inherited-from-n64decomp (`MAX_PLAYERS` constant);
    Authored-in-PD2 (the wire mask widenings)
  - Pillar Impact: Scaling Ceiling
  - Defect Class: Scaling
  - Intended Outcome: P2P session size scales with host compute / bandwidth;
    dedicated-server scales with server capacity.
  - Current Behavior: The PC port has widened `NET_MAX_CLIENTS` to 32,
    `MAX_BOTS` to 32, `MAX_MPCHRS` to 40, but `MAX_PLAYERS` remains 8 with
    bitmask widths and visual-shape loops that cap at exactly that value.
    `playerSetCutsceneActiveMask(u8 player_mask, ...)` accepts an 8-bit mask
    that cannot represent slot 8+ at all -- silent truncation if MAX_PLAYERS
    is raised. The wire `u64 active_mask` caps at exactly 64 participant
    slots, which is below the published goal of "scale to host capacity."
    The hand-unrolled `PLAYERCOUNT()` would have to be re-templated by hand
    every time MAX_PLAYERS changes. `for (i = 0; i < 4; i++)` and
    `for (i = 0; i < 8; i++)` patterns appear in `src/game/player.c:610,617,
    704,5967` and many call sites where the literal is not a symbolic
    constant -- those would silently underflow on a count increase.
  - Gap / Failure Mode: A bump from 8 to (say) 12 requires touching the
    `PLAYERCOUNT()` macro chain by hand, replacing every `u8 player_mask`
    with at least `u16`, widening the cutscene mask plumbing, expanding the
    ready-gate masks to u64, and auditing every fixed-literal player loop.
    Many of these would be silent corruption rather than build breaks.
  - Why It Matters: The audit prompt explicitly says fixed N64-era ceilings
    are findings in PD2 even when current code works. The current code
    works at 8, but every step toward "host-bound scaling" requires
    coordinated multi-site work and the architecture does not centralize
    these.
  - Risk If Not Fixed: The published architectural intent ("scale with host
    compute") cannot be realized without coordinated cross-system work, and
    the ceiling is hidden inside bit widths rather than expressed as a
    single constant.
  - Recommendation: (a) Add a comment in `constants.h` documenting which
    derivatives must change in lockstep if MAX_PLAYERS is raised; (b)
    promote all `u8 player_mask` to a typedef (`player_mask_t`) sized to
    fit `MAX_PLAYERS` so bit-width changes are mechanical; (c) replace
    visual `for (i = 0; i < 4; ++)` / `for (i = 0; i < 8; ++)` loops in
    `src/game/player.c` with symbolic loops; (d) audit
    `s_ReadyGate.*_mask` widening when the time comes; (e) plan a
    wire-protocol bump (`u64` -> repeated-block) for active slots if a
    future cap above 64 is ever pursued.
  - Cross-System Changes Required: Yes
  - Blocks Intended Outcome?: Partially (current outcomes work; growth
    outcome blocked)

- **Connect-code "no raw IP" is privacy theater, not a privacy boundary**
  - Severity: High
  - Confidence: Confirmed
  - Location: `port/src/connectcode.c:28-275` (4 dictionaries of 256 entries
    each, in plain ASCII in the binary);
    `constraints.md` line for "No raw IP in any UI surface";
    every UI call site (`pdgui_lobby.cpp:262,357`, `pdgui_menu_lobby.cpp`,
    `video.c:176-181`, `server_main.c:496`)
  - Lineage: Authored-in-PD2
  - Pillar Impact: Online-mode Boundary
  - Defect Class: Trust-Boundary
  - Intended Outcome: "No UI element may display or accept a raw IP address."
    The constraint frames connect codes as a privacy improvement over raw
    IPs.
  - Current Behavior: Connect codes are a deterministic, reversible
    `IPv4(+port) -> 4-or-6 sentence` encoding via a fully-public dictionary
    that ships in the open-source binary. Anyone who has the dictionary
    (which is everyone who can read the source or run `strings` on the
    binary) can convert a code to an IP in O(1). The four dictionaries are
    256 entries each, and the binary is open source.
  - Gap / Failure Mode: The constraint *as worded* implies confidentiality
    ("never shown" / "must never be exposed"). The mechanism only achieves
    visual obfuscation in casual contexts (screenshots, livestreams), not
    confidentiality from a motivated adversary.
  - Why It Matters: PD2 audit's threat model includes IP exposure as a
    griefing / harassment vector. Treating obfuscation as confidentiality
    can lead future contributors to skip stronger mitigations (e.g., relay
    via dedicated server, opaque session tokens via signaling service).
  - Risk If Not Fixed: A player who shares a "fun connect code" on a stream
    has just publicly disclosed their IP to anyone who reads the source.
    No code changes; UI continues to "protect" IPs that are trivially
    recoverable.
  - Recommendation: (a) Update the constraint wording from
    "privacy/protection" to "obfuscation against casual readers"; (b)
    document this limitation in user-facing share-screen text ("anyone who
    can read the game source can recover the IP from this code"); (c) for
    real confidentiality, plan a signaling-service / relay tier in a future
    iteration of the connectivity pillar.
  - Cross-System Changes Required: No (documentation update); future relay
    work would touch P2P + UI + identity
  - Blocks Intended Outcome?: Partially (claims protection that does not
    exist)

- **Save migration framework registers zero migrations despite SAVE_VERSION
  having moved from 1 to 2**
  - Severity: High
  - Confidence: Confirmed
  - Location: `port/src/savemigrate.c:245-278`
    (`saveMigrateInit` body); `port/include/savefile.h:41`
    (`#define SAVE_VERSION 2`); `port/src/savefile.c:225-241` (load path)
  - Lineage: Authored-in-PD2
  - Pillar Impact: None (save invariant)
  - Defect Class: None
  - Intended Outcome: A registered migration ladder upgrades pre-v2 saves
    to the current SAVE_VERSION as part of load.
  - Current Behavior: The framework exists and is wired into the loader,
    but `saveMigrateInit()` registers nothing. The file header comment
    still says "Currently SAVE_VERSION = 1, so no migrations are registered
    yet" -- stale; `SAVE_VERSION` is 2 in the live header. Loader path
    logs `SAVE: version older than current SAVE_VERSION` but the unknown-
    key skip is the *only* migration mechanism for v1 -> v2.
  - Gap / Failure Mode: Players whose saves were written under v1 (string

  - Why It Matters: The intent of the framework -- explicit, registered,

  - Risk If Not Fixed: A real v1 save in the wild could silently load with

  - Recommendation: (a) Replace the stale comment to match SAVE_VERSION==2;

  - Cross-System Changes Required: No
  - Blocks Intended Outcome?: Partially (only affects v1 -> v2 carry-over)

#### Medium Priority Findings

- **PLAYERCOUNT() macro hand-unrolls per MAX_PLAYERS value with chained ?:**
  - Severity: Medium
  - Confidence: Confirmed
  - Location: `src/include/constants.h:102-112`
  - Lineage: Inherited-from-n64decomp (`MAX_PLAYERS == 4` branch is the
    original-shape; `MAX_PLAYERS > 4` branch was added during the PC
    expansion)
  - Pillar Impact: Scaling Ceiling
  - What We Found: The macro chains `?:` operators eight deep, one per

  - Why It Matters: Visual N64-shape, brittle to change, doesn't centralize

  - Recommendation: Replace with `mpGetActivePlayerCount()` (already exists

- **Hand-rolled `for (i = 0; i < 4; i++)` and `for (i = 0; i < 8; i++)`
  loops in `src/game/player.c` use raw literals as player-count surrogate**
  - Severity: Medium
  - Confidence: Confirmed
  - Location: `src/game/player.c:610,617,704,5967,5968`;
    `src/game/mplayer/mpspawn_orchestrate.c:431`;
    `src/game/chr.c:3402`;
    `src/game/chraction.c:15533,15592`
  - Lineage: Inherited-from-n64decomp
  - Pillar Impact: Scaling Ceiling
  - Defect Class: Lineage-Shape
  - What We Found: At least 9 player-count loops use raw `4` or `8` instead
    of `MAX_PLAYERS` or `MAX_LOCAL_PLAYERS`. The audit prompt explicitly
    flags this signature: "N64-era player-count loops -- for (i = 0; i < 4;
    i++) where the 4 means 'max players,' regardless of what the symbolic
    constant evaluates to elsewhere." Some of these may not be player
    iterators (e.g., 4x4 matrix loops), but at least the `player.c:610-617`
    and `player.c:704` patterns sit inside player-loop bodies.
  - Why It Matters: A future MAX_PLAYERS increase would not touch these.
    They would silently iterate up to the old N64 cap.
  - Recommendation: Convert each verified player-loop site to
    `MAX_PLAYERS` / `MAX_LOCAL_PLAYERS`. Document non-player `4`/`8`
    constants with a comment so the next sweep does not re-flag them.

- **Hardcoded STUN servers leak host external IP to third parties (Google,
  Cloudflare)**
  - Severity: Medium
  - Confidence: Confirmed
  - Location: `port/src/net/netstun.c:71-76`
    (`stun.l.google.com:19302`, `stun1.l.google.com:19302`,
    `stun.cloudflare.com:3478`)
  - Lineage: Authored-in-PD2
  - Pillar Impact: Online-mode Boundary
  - Defect Class: Trust-Boundary
  - What We Found: Hosts performing NAT discovery transmit a STUN binding
    request to Google/Cloudflare, which reveal source IP/port to those
    third parties. The list is not configurable in `pd.ini`.
  - Why It Matters: PD2's threat model includes IP exposure. Sending every
    host's external-IP discovery to Google is a privacy claim users may
    not expect, and a centralization point for a community-run game.
  - Risk If Not Fixed: All PD2 hosts are surveilled by these third parties;
    if either fails, NAT discovery fails community-wide.
  - Recommendation: (a) Document the third-party dependency in
    `pillars/connectivity.md`; (b) make the list overridable in `pd.ini`
    (operators can choose alternative STUN providers); (c) consider
    adding a community-run STUN as a third option.

- **Wire-decoded session-catalog count bounded for memory but not CPU**
  - Severity: Medium
  - Confidence: Confirmed
  - Location: `port/src/net/sessioncatalog.c:115-191`
    (`sessionCatalogReceive`)
  - Lineage: Authored-in-PD2
  - Pillar Impact: None
  - Defect Class: None
  - What We Found: The receiver reads `wire_count` (a 16-bit field), clamps
    `count` to `SESSION_CATALOG_MAX_ENTRIES`, then iterates `i < wire_count`
    -- continuing to drain entries from the netbuf even after the
    write-side cap is hit. A malicious server (or a buggy one) could send
    `wire_count == 65535` and force 65k string-read iterations.
  - Why It Matters: CPU amplification under malicious input. Not memory-
    unsafe, but a server with hostile peers (or a peer compromise) could
    burn CPU on this path.
  - Recommendation: After clamping `count`, also set
    `wire_count = count` so the read loop bounds match the write loop.
    Log a warning at the clamp.

- **`netDistribClientHandleCatalogInfo` allocates `calloc(count, 64)` from a
  16-bit wire field without an upper bound**
  - Severity: Medium
  - Confidence: Probable
  - Location: `port/src/net/netdistrib.c:782-823`
  - Lineage: Authored-in-PD2
  - Pillar Impact: Catalog SOT
  - Defect Class: Trust-Boundary
  - What We Found: `count` is read elsewhere as a u16 batch count.
    `calloc(count, sizeof(*missing_ids))` allocates `count * 64` bytes;
    upper bound `65535 * 64 == ~4 MB` per call. Catalog batches occur on
    a per-batch cadence so a hostile server could repeatedly push these.
  - Why It Matters: Memory amplification under hostile-server scenarios.
    Listen hosts (the shipping target) trust their leader, but a
    compromised lobby leader could exploit this against peers.
  - Recommendation: Cap `count` at a sane batch size (e.g., 4096) and
    drop the batch if it exceeds. Also cap repeated batches by
    `total_count` upper bound.

- **`netmsgSvcCatalogInfoWrite` and the v50 batched catalog-info path widen
  the trust surface without an explicit malformed-input fuzz test**
  - Severity: Medium
  - Confidence: Probable (no live fuzz harness observed)
  - Location: `net.h:12-50` (v50 protocol change rationale);
    `port/src/net/netdistrib.c:782-980`
  - Pillar Impact: Catalog SOT
  - What We Found: The wire format grew batched length-prefixed catalog
    entries to support large mod packs. Each new batched/length-prefixed
    format adds another input-validation surface; without a fuzz harness
    these grow over time.
  - Recommendation: Add a fuzz harness (libFuzzer / AFL) over
    `netmsgSvc*Read` paths -- at minimum SVC_CATALOG_INFO,
    SVC_SESSION_CATALOG, SVC_STAGE_START, SVC_DISTRIB_BEGIN, SVC_DISTRIB_CHUNK.

#### Low Priority Findings

- **`mpsetupSerialize/Deserialize` writes structs via `fwrite(&s,
  sizeof(s), 1, fp)` -- portable only on identical endian / packing**
  - Severity: Low
  - Confidence: Confirmed
  - Location: `port/src/mpsetups.c:362-390`
  - Lineage: Authored-in-PD2
  - Pillar Impact: None (PC-only target)
  - Defect Class: Layout
  - What We Found: Direct field-by-field `fwrite` of the version/header
    and opaque `setups[i].bytes` blocks. Currently fine for x86_64 LE; if
    a future port target ever shifts endianness or padding rules, these
    saves would silently corrupt.
  - Recommendation: Explicit byte-order on `version`/`numsetups`/etc.
    Mark in `constraints.md` that this format is intentionally LE-only.

- **`extractArchive` accepts `path_len` and `dlen` only up to the file end,
  but no per-file size cap**
  - Severity: Low
  - Confidence: Confirmed
  - Location: `port/src/net/netdistrib.c:687-776`
  - Lineage: Authored-in-PD2
  - Pillar Impact: Modding Pipeline
  - Defect Class: Supply-Chain
  - What We Found: A single inner file of the PDCA archive could be
    `archive_bytes - small_header` size (capped at 256 MB by the outer
    `archive_bytes` cap). The `..` path traversal block is good; the
    drive-prefix protection on Windows is implicitly handled by
    `_fullpath` containment. Per-file size cap is implicit (sum bound) not
    explicit.
  - Recommendation: Add a per-file size cap (e.g., 64 MB) inside
    `extractArchive` so a single oversized inner file is rejected before
    being written to disk.

- **PDCA archive header is written via `memcpy(buf, &magic, 4)` /
  `memcpy(buf, &file_count, 2)` without an explicit byte-swap; reader
  uses `PD_LE16/PD_LE32` macros**
  - Severity: Low
  - Confidence: Confirmed
  - Location: `port/src/net/netdistrib.c:307-308,344` (writer);
    `port/src/net/netdistrib.c:691-701` (reader)
  - Lineage: Authored-in-PD2
  - Pillar Impact: Modding Pipeline
  - Defect Class: Layout
  - What We Found: Writer side trusts host LE; reader compensates with
    PD_LE macros. Symmetric on x86_64 LE, but if the writer ran on a BE
    host the archive would not round-trip.
  - Recommendation: Make the writer match the reader's explicit endian
    contract -- byte-swap in the writer too.

- **STUN transaction ID uses `rand()` rather than a cryptographic RNG**
  - Severity: Low
  - Confidence: Confirmed
  - Location: `port/src/net/netstun.c:118-133`
  - Lineage: Authored-in-PD2
  - Pillar Impact: Online-mode Boundary
  - Defect Class: None
  - What We Found: 12-byte transaction ID is built from `rand() & 0xFF`.
    For STUN tx-IDs this is correlation only, not security-critical, but
    `rand()` is a weak PRNG.
  - Recommendation: Use `SDL_GetPerformanceCounter` mixed with a running
    hash (the same idiom as `netServerIssueCookie`). No urgency.

### Missing / Incomplete Features Blocking Success

## 4) Security, Trust & Privacy Review

### Critical Issues

- (none distinct from Section 2 / 3 Critical)

### High Priority Findings

- **Trust gate for received `.pdmod` archives queues an enable prompt but
  always installs the file to disk first**
  - Severity: High
  - Confidence: Confirmed
  - Area: Security
  - Location: `port/src/file_transfer.c:552-580`
    (`fileTransferInstallReceivedMod`)
  - Lineage: Authored-in-PD2
  - Pillar Impact: Modding Pipeline / Grid Trust
  - What We Found: Received mods are validated by `modmgrValidateArchiveFile`
    (which checks root mod.json + rejects `.bin` / `.tsv` public payloads +
    walks typed nested archives), then `modmgrInstallArchiveFile` writes
    the archive to disk under `mods/installed/`. For non-friends,
    `enable_now == 0` so the mod is installed-disabled with an enable
    prompt, but the disk artifact persists.
  - Why It Matters: A friend (or someone spoofing a friend handle until the
    TOFU bind fires) can drop a `.pdmod` onto the user's disk through the
    share channel. The disk write itself is reachable before any user
    consent in the "non-friend" path -- the user only consents to *enabling*
    the mod, not to receiving and storing it.
  - Risk If Not Fixed: Storage abuse (filling inbox with `.pdmod` files),
    name-collision attacks (mod_id reuse to mask future installs),
    accidental pickup if user later clicks "enable all" sweep.
  - Recommendation: (a) For non-friend or untrusted-source pushes, hold the
    archive in a quarantine area (`social/inbox/quarantine/`) until the
    user accepts; (b) reject duplicate mod_id installs from non-friends;
    (c) cap inbox / quarantine size per peer.

- **`v46` mandatory SHA-256 enforces compressed-archive integrity, but no
  signature -- any peer with control of the catalog-info path can ship an
  arbitrary `.pdmod` to a client**
  - Severity: High
  - Confidence: Probable
  - Area: Security
  - Location: `port/src/net/netdistrib.c:864-947`
    (`distribStartReceive`); `2511-2525` (digest verify)
  - Lineage: Authored-in-PD2
  - Pillar Impact: Modding Pipeline (supply chain)
  - What We Found: SHA-256 protects against in-transit corruption /
    mismatched payloads, but the digest comes from the same server that
    sends the data. A compromised listen-host or malicious leader can
    issue a digest matching their own malicious archive.
  - Why It Matters: The PD2 modding-pipeline pillar calls out "supply-chain
    integrity" as a target. SHA-256 satisfies transport integrity but not
    source authentication.
  - Risk If Not Fixed: A malicious listen-host can ship arbitrary mod
    payloads to clients who only "trust" the room they joined. Path
    traversal and per-file size are bounded, but a deliberately crafted
    mod could still ship hostile scripted assets or attempt
    deserialization-time bugs (asset INI parser, GLTF importer, etc.).
  - Recommendation: Sign mods with the author's Ed25519 key (already
    present for social_share), bind mod_id -> author handle, and verify
    signature on receive. Add a Catalog field for `author_pubkey` (or
    keep TOFU per mod_id), and refuse mods whose author key doesn't
    match the previous record.

- **Persistent ban list is per-IP only and the IP is extracted from the
  ENet peer address string**
  - Severity: High
  - Confidence: Confirmed
  - Area: Security
  - Location: `port/src/server_bans.c:*` (entire file);
    `port/src/net/netmsg.c:8555-8584` (extract IP for ban from ENet peer)
  - Lineage: Authored-in-PD2
  - Pillar Impact: Online-mode Boundary
  - What We Found: Bans are keyed by bare IP string. A peer behind CGNAT
    or dynamic IP rotates trivially; bans are evaded by reboot. Conversely,
    a shared-IP household has one banned peer ban out the rest.
  - Why It Matters: PD2's threat model includes griefing. Per-IP ban is
    the weakest tier of enforcement available.
  - Recommendation: Layer identity-cookie bans on top of IP bans. A
    repeated-offender pattern (same cookie reconnecting) can stick even
    across IP changes; legitimate household members are not collaterally
    banned.

#### Medium Priority Findings

- **`SVC_GPUSWARM_STATE` (v48, 0x6c) carries position+velocity for the
  whole bot pool 10 Hz, quantized to 20 B / bot -- amplifies host send to

  - Severity: Medium
  - Confidence: Probable
  - Area: Security
  - Location: `port/include/net/net.h:34-49` (rationale);

- **The `g_NetLocalBotAuthority` flag and `SVC_BOT_AUTHORITY` mechanism

## 5) Cross-Cutting Risks & Architecture Concerns

- **Scaling-ceiling lattice is encoded in bit widths, not constants.** The
  player-count cap is *declared* as `MAX_PLAYERS == 8` but *enforced* by
  `u8 player_mask` (cutscene path), `u32 ready_mask` (ready gate; cap 32),
  `u64 active_mask` (wire; cap 64), `s16 killcounts[MAX_MPCHRS]` (preserved
  scores). Each cap is reached by a different ceiling. Future scaling
  cannot proceed by raising the constant alone. -> Document the lattice;
  consider a `pillars/scaling-ceilings.md` map.

- **Mod-vs-native fallback symmetry is not complete.** Catalog override
  path (`assetcatalog_load.c`) is symmetric for the file-provider case,
  but bundled assets still take a ROM-provider fast path while mods always
  take the file-provider path. The audit prompt's "you couldn't tell"
  property is achieved at most code layers but not in the bundled-vs-
  override branching of the loader. -> Audit each `if (!e->bundled ||
  e->source.primary.provider == fileProvider())` site for fast-path
  divergence and consider unifying behind a `catalogLoadTypedAsset` path
  that does not branch on source provider.

- **Trust model for received mods is "received first, consent second"**
  rather than "consent first, receive second." Section 4 High flagged the
  install-disabled artifact persistence. The same logic applies to the
  receive UDP socket itself: the share aggregator binds port 27109 by
  default and accepts inbound from any signed friend. There is no per-
  friend transfer cap, so a friend can fill local disk with `.pdmod`
  archives slowly. -> Add per-friend transfer quota / inbox quota / cap
  on quarantine size.

- **Wire-protocol changelog as header comment.** v50 protocol comment is
  the symptom; the cross-cutting concern is that every behaviour change
  cascades through the same monolithic `net.h` header. New work should
  document protocol changes in `pillars/save-wire-format.md` with a
  per-version bounds-proof; the header should carry only the live version
  + a pointer.

- **Coupling between `g_NetDedicated` branches in game-side code.** Several
  places (`netmsgClcAuthRead`, `netServerEvConnect`, slot allocation, ROM
  check skip, identity name resolution) test `g_NetDedicated`. This is
  the boundary between "is the program a listen-host?" and "is it a
  dedicated server?" -- the place where a future game-agnostic core would
  emerge. The current sprinkle is correct but means the boundary is
  encoded in conditionals rather than in module structure. -> When plugin
  ABI work resumes, this is the seam to cut along.

- **Two CLAUDE.md files duplicate the same project briefing**
  (`Perfect-Dark-2/CLAUDE.md` and `perfect_dark-mike/CLAUDE.md`).
  Stale-content drift risk is high; either reduce to a single source with
  the other as a thin pointer, or set up a `pre-commit` hook that fails
  on drift.

- **Connect-code and dictionary integrity** -- a typo in any of the four
  256-entry dictionaries silently shifts IPs. There is no checked-in
  test for dictionary uniqueness. -> Add a static assertion or unit test.

- **Save-format migration ladder is a registry of zero entries** -- the
  framework exists, but the registration is documentation only. The
  intended invariant ("every save passes through the migration ladder")
  is implicitly satisfied only by zero-need; a real v1->v2 migration is
  unverified.

- **Header-side bookkeeping vs. pillar-doc bookkeeping.** Several
  constants and explanations live in two places (e.g., NET_PROTOCOL_VER
  in `net.h` and `pillars/save-wire-format.md`; MPSETUP_VERSION in
  `mpsetups.h` and `constraints.md`). Discipline requires both updates;
  drift was already observed in `port/CLAUDE.md` ("Protocol version: 17"
  vs. live 50). -> Add a tools/check_doc_drift.py to fail CI when these
  drift.

### Top Scaling Ceilings Identified

- `MAX_PLAYERS == 8` (`src/include/constants.h:44`) -> CPU + UI + memory.
  All downstream caps derive.
- Cutscene mask `u8 player_mask` (`src/game/player.c:325-348`) -> silent
  truncation if MAX_PLAYERS > 8.
- Ready-gate `u32 mask` (`port/src/net/netmsg.c:300-303`) -> caps at 32
  participants.
- Wire `u64 active_mask` (`port/src/net/netmsg.c:1550`) -> caps at 64.
- `NET_MAX_CLIENTS == 32` (`port/include/net/net.h:218`) -> independent
  cap; tied to ready-gate u32.
- `PLAYERCOUNT()` macro chained `?:` (`src/include/constants.h:103-112`)
  -> requires hand-edit to grow.
- ~70 `for (i = 0; i < MAX_PLAYERS; i++)` loops in `src/game/` -> CPU
  scales linearly; some are O(N^2) for player-vs-player iteration.

### Top Data-Layout Integrity Breaches (Phase 2.5)

- **None Critical observed.** The codebase has visibly internalized the
  `Vec3 12 vs 16 byte` lesson from prior incident: `struct coord` is a
  clean 3-float, no padding, used consistently with `sizeof(struct coord)`.
  Bitmask widths around player count are *intentional* scaling caps, not
  data-layout breaches.
- **Low**: `mpsetupSerialize` and `extractArchive` PDCA header write
  assume host LE without explicit byte-swap on the writer side. Reader
  uses `PD_LE*` macros. Persisted format is implicitly LE-only.
- **Low**: `chrdata.headnum` was widened from `s8` to `s16` per session
  log 2026-06-11 (custom head slot 152). Test pin added. Past breach
  closed, but worth a propagation check that no other `headnum` /
  `bodynum` field still uses `s8` somewhere downstream.
- **Low**: `net_hash u32` backfill survives in `session_catalog_entry_t`
  / `sessionCatalogGetIdByHash` despite the 2026-04-02 constraint
  retiring net_hash from wire.
