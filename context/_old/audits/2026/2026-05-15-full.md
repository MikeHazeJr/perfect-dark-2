## 1) Inferred Project Goal & Intended Outcomes

### Inferred Purpose
Perfect Dark 2 is a community fork of `fgsfdsfgs/perfect_dark` (`port-net`) re-engineered into a modding-first, P2P-multiplayer, social-Grid-aware game with a deterministic asset Catalog and a game-agnostic dedicated server (aspirational; deferred per S486). The current ship target is in-client online connectivity (listen-host). The primary architectural arc this week is the **Smoke Verify Gate** -- a CI-style assertion engine built on top of a JSON-driven harness that can drive the live client through scripted scenarios, capturing log assertions and producing a 0/1 verdict. This closes the long-running gap where the only way to regress class-of-bug fixes was Mike's manual playtest.

### Likely Player & Contributor Types
- PD / GoldenEye veterans and speedrunners (manual play, replays).
- Modders authoring `.pdmod` archives (Maps, Weapons, UI Chrome, Skins, Audio).
- Community hosts running listen-mode servers.
- Future dedicated-server operators (deferred).
- AI sessions and Mike collaborating; the smoke gate is explicitly a contributor-class tool that any new pull request can extend.

### Core Workflows / Gameplay Loops (Inferred)
1. **First-launch BYOR**: client extracts ROM, walks catalog, 13 per-asset emitters populate `data/<romid>/<kind>/`, walker registers them, loader pool finalises typed payload, game proceeds to title.
2. Listen-host: P2P 6-tier NAT traversal -> ENet auth (v46) -> manifest exchange -> match start.
3. Mod author: `.pdmod` archive built locally -> SHA-256 distribution via `SVC_DISTRIB_*` -> hot-register in catalog.
4. **NEW: contributor smoke run** -- `PerfectDark.exe --smoke tests/<x>.json` (or `tools/smoke-verify/run.ps1 -Test <name>`) drives a scripted scenario, asserts on log markers, exits 0/1.
5. Dedicated server (NEW smoke coverage this week): `PerfectDarkServer.exe --headless --port N --maxclients K` boots to "Entering main loop" with bans + admin state initialised.

## 2) Design Intent & Gameplay / Multiplayer Fit Review

### System & Workflow Validation Findings

#### Critical Issues

##### D-1) Smoke harness compiled unconditionally into shipping binary; `--smoke <path>` is an unprotected action-injection surface
- Severity: **Critical** (release-binary attack surface)
- Confidence: Confirmed
- Location: [port/src/smoke_harness.c:731-777](../../port/src/smoke_harness.c) (`smokeHarnessInit`), [port/include/smoke_harness.h:46](../../port/include/smoke_harness.h), `CMakeLists.txt` `file(GLOB_RECURSE port/src/*.c)` auto-discovers `smoke_harness.c` into the `pd` target
- Lineage: Authored-in-PD2 (c115, 2026-05-11 + 2026-05-14)
- Pillar Impact: Online-mode Boundary (potential), Modding Pipeline (potential)
- Defect Class: Trust-Boundary
- Intended Outcome: The smoke harness is a contributor / CI tool. It should not be reachable from a shipping release.
- Current Behavior (from code evidence): Any user who passes `--smoke <path>` to a shipping `PerfectDark.exe` activates the harness:
  - `smokeHarnessInit` opens the path via `fopen(path, "rb")` with no traversal protection (line 375).
  - The JSON tokenizer (~480 lines) parses test definitions and seeds `s_State.events[]` with up to 512 events.
  - `smokeHarnessTick()` runs every frame and dispatches keyboard, mouse, and `actionmapInjectStateForSmoke` events (focus-independent action-map mutation) -- see [port/src/actionmap.cpp:3212-3254](../../port/src/actionmap.cpp).
  - On press, `actionmapInjectStateForSmoke` calls `cheatRecord((InputAction)action)` (line 3241) for all non-axis actions. A scripted test JSON can therefore drive the cheat buffer through any sequence (the same buffer that unlocks cheats via real input).
  - `smokeHarnessExit(code, reason)` calls `exit(code)` directly (line 908) -- see D-2.
- Gap / Failure Mode:
  - **Local cheat unlock via scripted input**: a player writes a JSON sequence matching `g_CheatTable` entries (`right, right, down, down, ...` etc.) and runs `PerfectDark.exe --smoke cheats.json`. The cheat unlocks deterministically without ever needing to learn the sequence or input it. This is local-only (no online advantage; server is authoritative for damage/score), so it is a fairness concern rather than a security exploit.
  - **Joined-session input flooding**: if `--smoke` is combined with online play, the harness can sustain a higher input-edge rate than a human can. The server's input-rate limit (if any) and per-action throttles are the only defense. The harness's `actionmapInjectStateForSmoke` writes directly into `s_State[player][action]` bypassing any per-press SDL focus or window-context check -- input that ImGui would otherwise drop still mutates the action map.
  - **JSON parser attack surface**: ~480 lines of hand-rolled tokenizer in the shipping binary. Not a known CVE class today, but a hand-rolled parser handling arbitrary user-supplied input violates least-attack-surface discipline.
  - **Path traversal**: `fopen(path, "rb")` on argv-derived path. Adversarial input is implausible (the user already controls argv), but the lack of any guard is sloppy.
- Why It Matters: The project already establishes a `PD_DEV_BUILD` gate for similar developer-only surfaces. [port/src/actionmap.cpp:400](../../port/src/actionmap.cpp) gates `ACTION_TESTSCEN_CYCLE_COUNT` under `PD_DEV_BUILD` and [port/src/pdsched.c:358-360](../../port/src/pdsched.c) gates its handler under the same flag. The smoke harness's existence in shipping binaries violates the discipline pattern already in use elsewhere.
- Risk If Not Fixed: Subtle: most release players will never know `--smoke` exists. But the project ships free / community / open-source: a single shared JSON of cheat sequences would distribute easily, and the harness's per-frame action injection bypass would be a noisier-than-real cheat vector.
- Recommendation: Gate the entire `smoke_harness.c` (or at minimum `smokeHarnessInit/Tick/Exit` and `actionmapInjectStateForSmoke` / `actionmapResolveByName`) behind `#if defined(PD_DEV_BUILD)`. The CMakeLists addition can be a `target_compile_definitions(pd PRIVATE PD_DEV_BUILD)` on a `-DPD_DEV_BUILD=ON` toggle. Release builds compile out the harness entirely; dev / smoke builds include it. The runner's `runtime_strategy=harness` continues to work against dev builds; the `runtime_strategy=timeout-kill` strategy works against any build.
- Cross-System Changes Required: No (single CMake toggle, conditional `#include` in `main.c`).
- Blocks Intended Outcome?: No (functionally; but breaks architectural discipline).

##### D-2) `smokeHarnessExit()` calls `exit()` directly, bypassing the registered `cleanup()` -- persisted state not flushed on smoke-driven exits
- Severity: **Critical** (silent state loss on every smoke run; potential save-format / pd.ini corruption)
- Confidence: Confirmed
- Location: [port/src/smoke_harness.c:883-909](../../port/src/smoke_harness.c) (`smokeHarnessExit` -> `exit(code)`), [port/src/main.c:401-433](../../port/src/main.c) (`cleanup()` registered)
- Lineage: Authored-in-PD2 (c115)
- Pillar Impact: Save / wire format
- Defect Class: Trust-Boundary (between harness and lifecycle)
- Intended Outcome: All exit paths run `cleanup()` -- which calls `actionmapSaveBinds()`, `configSave(CONFIG_PATH)`, `statsShutdown()`, `netDisconnect()`, `mempPCFreeAll()`, `SDL_Quit()`. State persists; sockets close; UPnP HTTP delete runs.
- Current Behavior (from code evidence): `smokeHarnessExit` calls `fflush(NULL)` then `exit(code)`. `cleanup()` is NOT registered with `atexit()` in the current `main.c` -- it is called from the explicit `return` of `main()` path. `exit()` does NOT run that path. Specifically:
  - `configSave(CONFIG_PATH)` does not run -> any pd.ini mutation during the smoke run is lost (acceptable for tests, but harness's `sysLogSetChannelMask(s_State.channel_mask)` at line 761 does not actually mutate pd.ini, so this is benign).
  - `actionmapSaveBinds()` does not run -> any binding changes are lost (benign for tests).
  - `netDisconnect()` does not run -> if a smoke test reached the lobby or match state with active ENet peers, those peers see a connection-drop rather than a clean disconnect. The server's preserved-player slot reservation will hold the slot for the timeout period.
  - `mempPCFreeAll()` does not run -> heap memory is leaked at process exit (the OS reclaims it; benign).
  - `SDL_Quit()` does not run -> SDL audio device + window may remain in a half-initialised state for a brief moment; should auto-clear on process exit but is non-deterministic.
- Gap / Failure Mode: Smoke tests that reach an online/listen-host state see noisy / leaked-state shutdowns. Future tests that mutate pd.ini (e.g. testing config-load paths) will silently lose mutations. This violates the principle that exit paths are uniform.
- Why It Matters: As the smoke gate expands to cover more state-mutating paths (D13 update flow, save-migrate, ban list, ready gate), the unfair shutdown will start producing false positives -- a passing assertion on the live frame but a corrupted artifact left over.
- Risk If Not Fixed: Inconsistent test outcomes as coverage grows; potential save-state corruption if a save-migrate smoke test is added before this is fixed.
- Recommendation: Either (a) register `cleanup()` via `atexit(cleanup)` in `main()` so `exit()` runs it (preferred -- one-line change); or (b) have `smokeHarnessExit` call `cleanup()` before `exit(code)` (couples the harness to a forward declaration). Option (a) is the structural fix.
- Cross-System Changes Required: No (single line in `main.c`).
- Blocks Intended Outcome?: Partially (test fidelity).

- Confidence: Confirmed
- Location: [port/src/main.c:925-929](../../port/src/main.c)
- Lineage: Authored-in-PD2 (c115)

##### D-4) `bootApplyDebugSpawnAt` accepts a raw integer for `room` and narrows silently to `RoomNum (s16)` -- no input validation
- Severity: High (developer-facing fast-path with silent truncation)
- Confidence: Confirmed
- Location: [port/src/main.c:701](../../port/src/main.c) (`g_BootSpawnAtRoom = (s32)strtol(tokR, NULL, 0);`), [port/src/main.c:853](../../port/src/main.c) (`rooms[0] = (RoomNum)g_BootSpawnAtRoom;`)
- Lineage: Authored-in-PD2 (c115, 2026-05-14)
- Pillar Impact: None
- Defect Class: Layout (type narrowing without validation)
- Intended Outcome: `--debug-spawn-at x,y,z,room` teleports the player to a specific room. Out-of-range input should fail loudly.
- Current Behavior: `strtol` returns an `s32`; `RoomNum` is `s16`. Values >= 32768 truncate. `--debug-spawn-at 0,0,0,99999` becomes `room=33359 mod 65536 = ...` after the implementation-defined narrowing.
- Gap / Failure Mode: Smoke test author passes an arbitrary integer thinking they got the room they asked for; the actual `chrMoveToPos` runs against a different room. The teleport fails or sends the player to garbage geometry.
- Why It Matters: Silent truncation in dev-facing CLI surfaces is a workflow-correctness footgun; the harness should fail-fast on malformed input.
- Risk If Not Fixed: Smoke tests that use spawn-at with large room indices produce non-deterministic results.
- Recommendation: Bounds-check `g_BootSpawnAtRoom` against the stage's `g_Vars.roomcount` (or at minimum against `INT16_MAX` / `INT16_MIN`) at the `bootDebugSpawnAtTick` entry. Emit `LOG_WARNING` and clear the latch on failure.
- Cross-System Changes Required: No (single function).
- Blocks Intended Outcome?: Partially (test fidelity).

##### D-5) `actionmapInjectStateForSmoke` writes the cheat buffer on every scripted press -- smoke tests can inadvertently unlock cheats
- Severity: High (test-fidelity + privacy violation)
- Confidence: Confirmed
- Location: [port/src/actionmap.cpp:3237-3243](../../port/src/actionmap.cpp), [port/src/actionmap.cpp:551-556](../../port/src/actionmap.cpp) (`cheatRecord`)
- Lineage: Authored-in-PD2 (c115)
- Pillar Impact: None directly; affects test reproducibility
- Defect Class: Trust-Boundary
- Intended Outcome: The smoke harness drives input through the action map for fidelity; the side effects of real input (cheat sequence detection, hold-vis-grace) are typically wanted.
- Current Behavior: On press, `actionmapInjectStateForSmoke` calls `cheatRecord((InputAction)action)` for every non-axis action. The 32-slot ring buffer is updated and `cheatCheckSequences` runs on the next tick.
- Gap / Failure Mode: A smoke test that incidentally fires a sequence matching one of `g_Cheats[]` entries will activate that cheat. Save state for that profile then carries the unlock. If a smoke test uses the user's actual install (via `-Install`), the user's save acquires unlocks they did not intend.
- Why It Matters: Smoke runs should be hermetic. Cheat-as-side-effect violates that.
- Risk If Not Fixed: Future smoke tests that exercise menu nav (which involves many ACTION_USE / ACTION_MENU_CANCEL presses) may incidentally fire cheats and corrupt the install's unlock state.
- Recommendation: Gate the `cheatRecord` call inside `actionmapInjectStateForSmoke` on `if (!smokeHarnessIsActive())` (no-op since smoke is the caller), or more precisely add a `cheats_enabled` flag to the smoke harness state (default off) that the JSON can opt-into when explicitly testing cheat behavior. Either way, default smoke runs should not mutate the cheat buffer.
- Cross-System Changes Required: No (single function).
- Blocks Intended Outcome?: Partially (test hermeticity).

##### D-6) `--launch-mp-room` seeds `g_MatchConfig` without crediting host-ownership state -- bypasses lobby leader auth
- Severity: Medium (online-mode boundary; latent)
- Confidence: Probable
- Location: [port/src/main.c:607-653](../../port/src/main.c)
- Lineage: Authored-in-PD2 (c115)
- Pillar Impact: Online-mode Boundary, Trust-Boundary
- Defect Class: Trust-Boundary
- Intended Outcome: The smoke fast-path seeds local match state for a solo CS / pre-host state.
- Current Behavior: `bootApplyLaunchMpRoom` writes `g_MatchConfig.stage_id`, `scenario_id`, then loops `matchConfigAddBot(...)` up to `g_BootLaunchMpBotCount`. Then arms `g_PostExitMainMenuView = 0` and routes through `STAGE_CITRAINING`. No host-credential, no leader-claim, no room-ID assignment. The state mutation is local-only and bypasses the normal listen-host flow.
- Gap / Failure Mode: Today, fine for solo CS smoke. If `--no-net` is NOT also passed and the user starts listening for joins (via subsequent menu nav), the locally-seeded `g_MatchConfig` would broadcast as authoritative without ever running through `lobbyIsLocalLeader()` -- the leader-claim path is the design constraint per [constraints.md](../constraints.md). - Why It Matters: The trust-boundary discipline holds today because `--launch-mp-room` is only used with `--no-net`; the smoke tests using it all set `--no-net`. But the dependency is implicit; future test authors may not know.
- Risk If Not Fixed: Latent. If a future smoke test exercises `--launch-mp-room` WITHOUT `--no-net`, the locally-seeded match config bypasses leader-auth on the first broadcast.
- Recommendation: Add a constraint check in `bootApplyLaunchMpRoom`: if `!g_BootNoNet`, log `LOG_WARNING` and abort the seed. Or document the requirement explicitly in the smoke-verify README.
- Cross-System Changes Required: No.
- Blocks Intended Outcome?: No today.

##### D-7) c131 (`SkipIntro=1` boot black-screen deadlock) hints at a wider class of cutscene-end-gate dependencies
- Severity: Medium (propagation class)
- Confidence: Probable
- Location: [src/game/menutick.c:351](../../src/game/menutick.c) (file-select gate `tickmode != TICKMODE_CUTSCENE`), c131 fix at commit `3529116f`
- Lineage: Inherited-from-port + Authored-in-PD2 (the SkipIntro flag + the CI fly-in interaction is port-era)
- Pillar Impact: Menus / UI / UX
- Defect Class: Trust-Boundary (between boot-mode and tickmode state machine)

The new c115 fast-paths (`--launch-mission`, `--launch-mp-room`, `--launch-scenario`, `--main-menu`) all touch similar pre-mainProc state. Are any of them creating new stuck-cutscene paths?

For each, identify every gate downstream that reads tickmode / TICKMODE_CUTSCENE / similar state and verify the boot path drives that state transition. Multi-session lane; design ref: [context/designs/in-flight/](../designs/in-flight/) family.
- Cross-System Changes Required: Yes.
- Blocks Intended Outcome?: No today (c131 patched the immediate symptom).

##### D-8) `runtime_strategy=timeout-kill` (new c115) kills the dedicated-server process without graceful shutdown -- in-flight peers receive no DISCONNECT_SHUTDOWN
- Severity: Medium (test fidelity for server-pillar smoke)
- Confidence: Confirmed
- Location: [tools/smoke-verify/run.ps1:303-312](../../tools/smoke-verify/run.ps1) (strategy doc), [tools/smoke-verify/tests/dedicated_server_boot_smoke.json:18](../../tools/smoke-verify/tests/dedicated_server_boot_smoke.json) (uses this strategy)
- Lineage: Authored-in-PD2 (c115)
- Pillar Impact: Server / hosting, Online-mode Boundary
- Defect Class: Trust-Boundary
- Intended Outcome: Server smoke tests boot the daemon to a known state and tear it down cleanly.
- Current Behavior: The runner launches with `boot_args` only, sleeps `timeout_seconds`, then calls `Kill` on the process. Today's `dedicated_server_boot_smoke.json` test has no clients connect, so there are no peers to disconnect. But the pattern is generalizable -- future tests will simulate clients connecting and the timeout-kill will leave them hanging.
- Gap / Failure Mode: Future smoke tests that exercise the server's listen-host + client-join + then teardown will produce noisy peer-disconnect logs in the client's recorded log and may cause client smoke runs to assertion-fail on residual state.
- Why It Matters: Server test fidelity depends on either (a) full graceful shutdown or (b) explicit "disconnect-on-kill" tracking so the test can assert on the right markers.
- Risk If Not Fixed: Server-pillar smoke coverage tops out at single-process boot tests; multi-process client-server flows are noisier than they need to be.
- Recommendation: Add a `--graceful-shutdown` CLI flag to pd-server that, when SIGTERM (or equivalent on Windows: Ctrl+C via `Stop-Process -Force:$false` -- which is what `Kill` does on Windows -- followed by a soft handler) is received, runs `netDisconnect()` on all peers and exits. Or add a `--shutdown-after-ms <N>` CLI flag that arms a one-shot shutdown timer inside the server's main loop, matching the harness model for clients.
- Cross-System Changes Required: Yes (server CLI + main loop).
- Blocks Intended Outcome?: No today (single-process tests work); blocks future multi-process server smoke.

##### D-9) `bootResolveStageIdToNum` silently falls through hex-parse failure to catalog resolve

##### D-10) Smoke harness JSON parser does not validate UTF-8 boundaries; uses `strncpy` with silent truncation on overflow
- Severity: Low
- Confidence: Confirmed
- Location: [port/src/smoke_harness.c:246-252](../../port/src/smoke_harness.c) (`j_tok_copy_str`)
- Lineage: Authored-in-PD2 (c115)
- Pillar Impact: None
- Intended Outcome: Test JSONs have ASCII identifiers; this is robust by construction.
- Current Behavior: `j_tok_copy_str` does `memcpy(dst, t->start, n); dst[n] = '\0';` with `n` clamped to `dstsz - 1`. If the source string is longer than the destination, the truncation is silent. A multi-byte UTF-8 char split mid-byte would produce malformed output.
- Gap / Failure Mode: Test files with extended characters in scenario names or action names produce wrong values.
- Why It Matters: Tests are authored in ASCII today; not a real issue.
- Risk If Not Fixed: None today.
- Recommendation: Add `LOG_WARNING` when truncation actually fires (compare `t->len` to `dstsz`). Cheap; documents the invariant.

##### S-2) `--smoke <path>` accepts arbitrary filesystem paths via `fopen` -- no traversal protection
- Severity: High (local-only; latent)

- Area: Security

##### S-3) Smoke harness embeds ~480-line hand-rolled JSON parser in shipping binary
- Severity: High (attack surface principle; latent)
- Confidence: Confirmed
- Area: Security
- Location: [port/src/smoke_harness.c:152-282](../../port/src/smoke_harness.c) (tokenizer + value-skipper)
- Lineage: Authored-in-PD2 (c115)
- Pillar Impact: None
- What We Found: The parser is hand-written. It correctly handles `{}`, `[]`, strings with backslash-escape, numbers (including 0x-hex), `true`/`false`/`null`, and `//` comments. Bounds: caps file at 2 MB, events at 512.
- Quick safety review: the tokenizer increments `p->pos` without explicit bounds checking against the source buffer end -- it relies on the source being null-terminated (`buf[n] = '\0'` after `fread`) to terminate scanning. The terminator IS written (line 396), so this is safe under the current `smokeReadFile` discipline. If a future caller bypasses `smokeReadFile` and parses from a buffer without a trailing nul, the parser would walk off the end.
- Why It Matters: An invariant ("source must be null-terminated") is implicit, not enforced. The string scanner at line 204 (`while (*p->pos && *p->pos != '"')`) terminates on either, so it's defensive against unterminated strings. The number scanner at line 220 (`while (*p->pos >= '0' && *p->pos <= '9')`) terminates on the null byte. Skip-value at line 261 reads via `j_next` which has the same protection. So the parser is safe IF the source is null-terminated.
- Risk If Not Fixed: Today, none -- `smokeReadFile` is the only entry. Latent if a future code path adds an alternate entry without enforcing the invariant.
- Recommendation: (a) Add a comment block at the top of the parser documenting the null-termination invariant. (b) Long-term, if the harness ships in release: extract the JSON parser into a small shared module with explicit length-bounded API and unit tests.

## 5) Cross-Cutting Risks & Architecture Concerns

**A-1. PD_DEV_BUILD gating discipline is inconsistent.** The codebase already gates `ACTION_TESTSCEN_CYCLE_COUNT` and its dispatcher under `PD_DEV_BUILD` ([port/src/actionmap.cpp:400](../../port/src/actionmap.cpp), [port/src/pdsched.c:360](../../port/src/pdsched.c)). But the smoke harness, CLI fast-paths (`--launch-mission`, `--launch-mp-room`, `--launch-scenario`, `--debug-mount-bike`, `--debug-spawn-at`, `--no-net`, `--main-menu`), and the action-injection primitive (`actionmapInjectStateForSmoke`) are unconditional. Recommendation: define a single project-wide rule for "developer-only CLI surface" and apply it. The simplest version: all c115 surfaces gate under `PD_DEV_BUILD` together. Multi-file change but mechanically straightforward.

**A-2. Exit-path uniformity is not enforced.** `cleanup()` runs from `main()` return, not from `atexit()`. Any code path that calls `exit()` (smoke harness, `sysFatalError` paths in some legacy code, `crashHandler` in extreme cases) bypasses it. Recommendation: register `cleanup()` via `atexit()` in `main()` and audit existing callers for double-shutdown safety.

**A-3. Smoke gate's input model has two-layer bypass risk.** The harness writes directly to the action-map state, bypassing both SDL focus (good for test reliability) AND the input-context stack (incidentally bypasses menu-consumption discipline). Real input flows: SDL -> action-map fire -> input-context layer-stack -> consumer-or-leak-to-lower. Smoke flow: action-map state directly mutated, bypassing both ends. Result: tests can pass for the wrong reason when menu-vs-gameplay arbitration matters. Recommendation: investigate routing injection through the input-context stack at the press edge (S-6).

**A-4. New c115 fast-paths share trust-boundary state with the listen-host flow.** `--launch-mp-room` writes `g_MatchConfig` directly; the same struct is normally populated by the leader-claim path. If a future smoke test combines `--launch-mp-room` (no `--no-net`) with auto-host, the locally-seeded state would bypass leader auth. Recommendation: D-6's `if (!g_BootNoNet) abort` check.

**A-5. Documentation drift is wider than just `port/CLAUDE.md`.** Q-1 surfaces the v17 vs v46 drift. A grep for `protocol version` / `protocol v\d+` across docs would likely find more. Recommendation: when bumping `NET_PROTOCOL_VER`, also grep-update all docs that name a specific version.
