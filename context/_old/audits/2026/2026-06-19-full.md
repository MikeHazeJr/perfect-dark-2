#### High Priority Findings

- **Modmgr/file_transfer refactor consolidated install logic but did NOT
  address any of the 06-12 High security findings**
  - Severity: High
  - Confidence: Confirmed
  - Location: `port/src/file_transfer.c` (shrank by 206L);
    `port/src/modmgr.c` (`modmgrInstallArchiveFile` lines 3308-3380);
    `port/include/modmgr.h` (new public API at lines 147-157);
    `port/fast3d/pdgui_menu_moddinghub.cpp` (-421L; UI deprecation)
  - Lineage: Authored-in-PD2
  - Pillar Impact: Modding Pipeline, Grid Trust
  - Defect Class: Trust-Boundary, Supply-Chain
  - Intended Outcome: Received mods are quarantined for non-friends before
    disk write, mod_id collisions from a hostile peer are rejected,
    per-peer transfer quota caps inbox abuse.
  - Current Behavior: The five-file refactor (file_transfer.c -206L,
    modmgr.c +341L, netdistrib.c +334L, pdgui_menu_moddinghub.cpp -421L)
    is a clean consolidation but inherits all three 06-12 High findings
    *verbatim*. The new `modmgrInstallArchiveFile()` writes both friend
    and non-friend mods to `mods/installed/`; only the `enable_now` flag
    differs. No quarantine subdirectory. No mod_id collision check
    (path-match only at line 3345). No per-peer accumulated-size cap.
  - Gap / Failure Mode: A peer (or someone spoofing a friend handle before
    TOFU binds) can fill the user's disk with `.pdmod` files,
    overwrite/shadow a trusted mod by mod_id collision, or stage a hostile
    archive for a later "enable all" sweep. SHA-256 covers transport
    integrity but not source authentication or storage hygiene.
  - Why It Matters: The 06-12 audit explicitly flagged each of these as
    blocker-class for the modding pipeline / Grid trust pillars. A refactor
    pass was a natural moment to address them; it did not.
  - Risk If Not Fixed: Identical to 06-12 -- storage abuse, mod_id shadow
    attacks, accidental pickup. The refactor *changed* the surface so any
    future fix has to land in modmgr.c instead of file_transfer.c.
  - Recommendation: Implement the three 06-12 mitigations in the new
    flow: (a) quarantine subdirectory for `enable_now == 0`; (b) mod_id
    collision rejection on install when source is not the user's local
    folder; (c) per-peer cumulative-size cap on file_transfer receive.
  - Cross-System Changes Required: Yes (file_transfer + modmgr + Grid
    UX -- the user needs an "accept this mod from <peer>" prompt for the
    quarantine path)
  - Blocks Intended Outcome?: Partially (current functional behavior works;
    the trust property the pillar declares does not)

- **`matchslot.headnum` / `matchslot.bodynum` still typed `u8` after the
  custom-slot expansion went past 152**
  - Severity: High
  - Confidence: Confirmed
  - Location: `port/include/net/matchsetup.h` (deprecated-marked u8 fields);
    `src/include/types.h` (`chrdata.headnum` widened to s16 in c3844)
  - Lineage: Authored-in-PD2 (legacy from before private-slot allocator)
  - Pillar Impact: Catalog SOT
  - Defect Class: Layout
  - Intended Outcome: All head/body slot fields are wide enough to address
    the private custom-slot range that allocates beyond 152.
  - Current Behavior: `struct chrdata.headnum` is now `s16`. But
    `struct matchslot.headnum` / `.bodynum` remain `u8` (marked
    "DEPRECATED: integer g_MpHeads[] index") and the canonical match-slot
    identity is now `body_id` / `head_id` (catalog ID strings). The
    deprecated fields are not the live identity, but they survive in the
    struct layout and any code that still reads them silently truncates
    slot 152+ to bits 0-7 (i.e. slot 152 reads as 0x18 = 24).
  - Gap / Failure Mode: A new wire consumer or save-format reader that
    forgets the migration and reaches for `matchslot.headnum` will silently
    truncate custom-slot values. The "deprecated" comment is a hand-shake
    against future drift, not an enforcement.
  - Why It Matters: The 06-12 audit warned that data-layout defects from
    type-width migrations are exactly the class PD2 has already seen
    (Vec3 12-vs-16-byte). Leaving the legacy u8 in the struct while the
    new identity is a catalog ID is a half-migrated layout; the audit
    prompt's Phase 2.5 explicitly says to flag this shape.
  - Risk If Not Fixed: Silent truncation if any code path still reads
    these fields. The risk grows as more "modder forgot to update X"
    review passes get less attention.
  - Recommendation: Either (a) actually remove the u8 fields now that
    `body_id`/`head_id` are canonical, or (b) widen them to `s16` in
    lockstep with `chrdata.headnum` so future drift is at least not
    truncating, or (c) keep them at u8 but add a `_Static_assert` that
    asserts the custom slot range is < 256, and remove the assert when
    the range grows -- forcing the migration to be explicit.
  - Cross-System Changes Required: Maybe (depends which option; option
    (a) touches save format)
  - Blocks Intended Outcome?: No (current code works; future code is at
    risk)

#### Medium Priority Findings

- **`MPOPTION_WEAPONGRAPH` bit position retired without "DO NOT REUSE"
  marker**
  - Severity: Medium
  - Confidence: Confirmed
  - Location: `src/include/constants.h` (MPOPTION_* block); the previously-
    defined `0x20000000` slot
  - Lineage: Authored-in-PD2
  - Pillar Impact: None (wire-protocol migration hygiene)
  - Defect Class: Lineage-Shape
  - What We Found: The Wave 7 cutover removed `MPOPTION_WEAPONGRAPH`
    (0x20000000) cleanly. The bit position is *not* reused in v51, but
    there is no comment / `_Static_assert` / placeholder marking "bit 29
    retired by c3849 Wave 7; do not reuse without considering v50 mixed-
    version semantics." A future MPOPTION add by a contributor unaware
    of the protocol bump history could reach for the lowest-free bit
    (which is now 0x20000000) and re-introduce a v50/v51 hazard.
  - Why It Matters: The v50/v51 protocol bump is the migration safety
    net, but the next MPOPTION addition is one slot reuse away from
    quietly entering the wire under a different semantic. The 06-12 audit
    flagged "wire-protocol changelog as header comment" as a cross-cutting
    concern; this is a concrete instance.
  - Risk If Not Fixed: A future contributor reuses the bit, a v51 client
    talks to itself fine but the changelog audit becomes harder to read.
  - Recommendation: Add a `/* 0x20000000 -- formerly MPOPTION_WEAPONGRAPH,
    retired in v51 (c3849 Wave 7); do not reuse without a new protocol
    bump */` marker next to the surviving MPOPTION_* defines.

- **`loaderPoolGet*` populated-flag fallback uses hard-coded `model.obj`
  if no `.obj`/`.gltf`/`.glb` member is found**
  - Severity: Medium
  - Confidence: Confirmed
  - Location: `port/src/loader_walker_body.c` (`s_sourceModelPathFromMeshArchive`);
    `port/src/loader_walker_head.c` (same)
  - Lineage: Authored-in-PD2 (new in 06-13..06-17 churn)
  - Pillar Impact: Mod-native Parity
  - What We Found: The new format-detection helper tries `model.obj`,
    `model.gltf`, `model.glb` in order via `fsFileSize(out) > 0`. If
    none is found, the helper falls back to a hard-coded `model.obj`
    path. The fallback is pragmatic for legacy archives but it can mask
    a format-detection failure as a "file exists but is empty" condition
    downstream -- the caller then attempts to load an .obj that may not
    be there.
  - Why It Matters: A mod with a missing or differently-named model file
    silently routes to the .obj fallback path instead of failing closed
    with a "no usable source" error. The c3844 source-only enforcement
    posture is "fail loudly on missing public source"; this is a quiet
    consolation path.
  - Recommendation: When all candidates fail `fsFileSize > 0`, return an
    error sentinel instead of falling back to the .obj guess. The caller
    can then emit a `CATALOG.BODY/HEAD.SOURCE_MISS` warning and fall to
    the loader pool's authored-base record.

- **`modmgrInstallArchiveFile` / `modmgrValidateArchiveFile` `error_len`
  is caller-trusted with no defensive cap**
  - Severity: Medium
  - Confidence: Confirmed
  - Location: `port/include/modmgr.h:147-157` (new public API);
    `port/src/modmgr.c` (`modmgrSetError`)
  - Lineage: Authored-in-PD2 (new in refactor)
  - Pillar Impact: None
  - What We Found: The new functions accept `(char *out_error, s32
    error_len)`. The `error_len > 0` check guards against negative/zero
    but not against "caller passed a length larger than the actual
    buffer." This is the standard C pattern and probably fine for internal
    use; flagged because the refactor *promoted* this to a public API.
  - Why It Matters: A new external caller (mod tooling, scripts) that
    misjudges the buffer size will overflow on `snprintf`.
  - Recommendation: Document the contract explicitly in `modmgr.h`
    ("error_len must be the actual byte capacity of out_error, including
    NUL"), or take a `size_t` rather than `s32` (`size_t` carries the
    "this is a buffer size" reading convention).

- **`weapon_graph_archive.c` nested-payload scan reads the entire
  archive into one allocation**
  - Severity: Medium
  - Confidence: Probable
  - Location: `port/src/weapon_graph_archive.c`
    (`weaponGraphArchiveScanNestedPayloadsFile`)
  - Lineage: Authored-in-PD2 (new in Wave 6b)
  - Pillar Impact: Modding Pipeline
  - Defect Class: Supply-Chain
  - What We Found: The function reads the whole `.pdweapon` archive
    into RAM via `weaponGraphArchiveReadBytesFile()` before enumerating
    nested payloads. For typical archives this is fine; a hostile or
    malformed archive declaring a 256 MB total but only a few small
    inner payloads forces a 256 MB allocation on the receiving client.
  - Why It Matters: The 06-12 audit flagged `extractArchive` as having
    only an implicit per-file cap. The same shape now appears here.
  - Recommendation: Cap the buffered read at a sane size
    (e.g. `WEAPON_GRAPH_ARCHIVE_MAX_BYTES`, perhaps 32 MB) and reject
    above that. Alternatively, stream-decode rather than buffering the
    whole archive.
