# Modding

> Component-based mod system. Typed `.pd*` content files plus `.pdmod` transport archives. JSON manifest + INI components. VFS over archive handles. Asset catalog is the single registration target. Network distribution with SHA-256 integrity. Reserved-name discipline at two layers.

---

## What it is

A mod is made of typed content units (`.pdweapon`, `.pdprojectile`, `.pdentity`, `.pdcharacter`, `.pdhead`, `.pdbody`, `.pdarena`, `.pdmesh`, `.pdanim`, `.pdsfx`, `.pdvoice`, `.pdsong`, `.pdui`, `.pdfont`, `.pdlang`, etc.) and can be distributed as a `.pdmod` archive (zip with `mod.json` manifest) or a folder under `mods/`. Each asset inside the bundle (map, character, skin, audio, etc.) is an independent component with its own `.ini` manifest (or JSON content entry in `mod.json`) and gets registered as an `asset_entry_t` in the catalog. Mods are not loaded as monolithic units; individual components are. `.pdmod` is the package/transport envelope for sharing and online delivery; the typed `.pd*` files remain the content organization surface.

## `.pdmod` archive format

Standard zip central-directory layout. Contents:

- `mod.json` (required) - manifest with id, name, version, author, description, base_fallback, dependencies, content (bodies/heads/arenas arrays), template, tags, requires_restart.
- Component `.ini` files (maps, characters, skins, weapons, audio, hud) at known sub-paths.
- External-format assets are standard authored files such as `.gltf`, `.glb`, `.obj`, `.png`, `.tga`, `.wav`, `.mp3`, `.ogg`, `.ttf`, `.otf`, and `.tsv`. Authored content packages and external-format `.pdmod` archives must not contain `.bin`; `.bin` is legacy-only and private generated cache stays outside shipped archives. Typed `.pd*` packages are the preferred content-unit surface, while `.pdmod` is the sharing/online transport envelope.

Path-traversal sanitization at parse time ([modarchive.c:13-17](../../port/src/modarchive.c:13)). One `FILE*` per archive for lazy per-entry extraction. Atomic write path: `modArchiveBegin / AddFileMem / AddFileDisk / Finish` streams to `.tmp` and renames on success.

## Manifest parsing

[modmgr.c:122-283](../../port/src/modmgr.c:122) hand-written token-by-token JSON parser sufficient for the `mod.json` schema. Same pattern as [savefile.c](../../port/src/savefile.c), [updater.c](../../port/src/updater.c). Falls back to filename-slug when `id` field missing. `audio.ini` fallback path for legacy audio mods.

`mod.json` content array supports embedded body / head / arena declarations alongside the file-based INI scan. Both paths converge on the same catalog registration API.

## Asset registration paths

Two paths, both ending in `assetCatalogRegister*`:

1. **INI scan path.** [port/src/assetcatalog_scanner.c:205-253](../../port/src/assetcatalog_scanner.c:205) walks component directories, parses `.ini` files, calls typed register functions (`assetCatalogRegisterBody`, `RegisterHead`, `RegisterArena`, `RegisterWeapon`, `RegisterAudio`, `RegisterHud`).
2. **JSON content path.** `modmgrRegisterModJsonContentBuf` parses `mod.json` content entries and calls the same `assetCatalogRegister*` functions.

Both paths use the typed catalog registration API; both flow into the same catalog rows. See [pillars/catalog.md](catalog.md) for the catalog model.

## Network distribution

[port/src/net/netdistrib.c](../../port/src/net/netdistrib.c) implements `SVC_DISTRIB_BEGIN / CHUNK / END`. Each missing component is shipped as a PDCA archive (zlib-compressed), chunked over the wire. Client decompresses, extracts, hot-registers via `assetCatalogRegister` ([netdistrib.c:1156-1232](../../port/src/net/netdistrib.c:1156)). Phase D-to-E manifest re-check at line 1258.

**v46 mandatory digest** (S507, 2026-04-28). `SVC_DISTRIB_BEGIN` carries a 32-byte SHA-256 digest of the exact compressed PDCA archive bytes. Clients reject zero/missing digests at BEGIN and verify accumulated compressed bytes before decompress/extract at END. Mixed v45/v46 play rejected at the ENet auth handshake.

## Active invariants

Per [constraints.md](../constraints.md):

- **`mods/` tree depth cap of 2 levels** (S293). Discovery scanners recurse exactly one level into top-level entries with no manifest.
- **Reserved names at two layers**: scan walker + archive-path-trusted check.
- **Catalog registers ALL assets**; mod content extends the catalog through the same typed registration API as base content.
- **Modding asset references are catalog IDs, not numeric handles** (2026-05-22). Modding tools, typed archive descriptors, nested dependency inventories, generated live files, and picker/dropdown surfaces must use human-readable catalog IDs in `[namespace]:[asset_type]_[name]` form. Numeric file numbers, model slots, sound IDs, animation slots, body/head numbers, and similar legacy handles may not be used as catalog IDs or modder-facing asset references.
- **Public typed archive references reject legacy numbers** (2026-05-25, c3842). The asset native-source guard fails public typed archive text that uses numeric or legacy-symbol asset-reference fields such as `model_id`, `modelnum`, `filenum`, `weapon_id`, `sound_id`, `texnum`, `MODEL_*`, or `FILE_*`. Scenario extraction no longer writes raw `setup.tsv`, `mpsetup.tsv`, or `visual_segments.tsv` public dumps because those exposed legacy model/table numbers instead of catalog IDs.
- **Public typed archive references must resolve to actual catalog names** (2026-05-27, c3844; TSV/CSV table guard extended 2026-05-28). Strict conformance collects catalog IDs declared by root and nested typed archives, then rejects unknown catalog-looking refs in descriptors, JSON graphs, public TSV/CSV asset-reference columns, and `_meta/manifest.json` dependency records. A syntactically valid `base:*` string is not sufficient; generated and authored references must name an actual catalog entry or an embedded dependency in the closure.
- **Scenario model references require `.pdmesh` archive closure** (2026-05-28, B-387). Scenario `objects.tsv` model catalog IDs are user-facing asset references and must point at real on-disk catalog archives. Base `.pdmesh` extraction now emits every `NUM_MODELS` `g_ModelStates` catalog model through `catalogModelIdByModelnum()`, so strict conformance can prove scenario model refs are editable/archive-backed instead of silently depending on private model slots.
- **`.pdmesh` skeleton metadata and nested source lookup are source-safe** (2026-05-28, B-388). Generated modeldefs may still carry legacy small skeleton tokens such as `SKEL_HEAD`; public-source export treats those as IDs instead of dereferenceable pointers, preserves `SKEL_HEAD` metadata, and resolves nested `.pdhead::mesh.pdmesh` manifests from the innermost archive path. This keeps all-model mesh extraction and source-gated weapon matches from stalling before runtime archive loading.
- **Mod enablement policy: default-enabled** (per [designs/modding/mod-enablement-policy.md](../designs/modding/mod-enablement-policy.md)). Mod-declared UI assets (themes today; skins, audio, weapons in future) enable on import unless the user opts out.
- **GL texture upload caps + cache-scoped teardown** (SP-15). Any mod-supplied PNG / image upload must clamp dimensions against `GL_MAX_TEXTURE_SIZE` and free via `glDeleteTextures` on cache teardown.
- **External-format content authoring + `.pdmod` transport** (2026-05-19, c3809). Typed `.pd*` files remain the preferred content-unit family, but modder-facing asset payloads are standard files plus grouped `.ini` / `.tsv` metadata. Authored content packages and `.pdmod` transport archives must not contain `.bin` files; any engine-native binary data must be generated as private runtime cache from external sources. `.pdmod` is used for packaging, sharing, Public Mods, and online-required content delivery. See [designs/modding/external-format-pdmod-pipeline.md](../designs/modding/external-format-pdmod-pipeline.md).
- **Fully self-contained typed asset archives** (2026-05-21, c3812/c3814). Each typed `*.pdxxx` content unit embeds its authored dependency closure on disk. Duplicate textures, materials, audio, meshes, animation targets, nested typed archives, and equivalent payloads across archives are acceptable for sharing and modding; catalog build/runtime dedupe by SHA-256 and catalog identity handles RAM waste after ingestion. Reference-only fields are metadata, not closure, unless the referenced authored payload is also embedded in the archive or carried as a contained nested dependency archive.
- **Public asset source is the native game source** (2026-05-25, c3842). For every asset family, the user-editable public files inside the typed archive are the source the game client consumes through catalog/provider loading. Engine-ready products may be generated as source-hashed cache for performance, but the final contract must not require parallel authored runtime files, opaque preprocessed dumps, or hand-maintained duplicates. This applies equally to extracted base assets and user mods.
- **Runtime ROM fallback is an asset-chain failure** (2026-05-27, c3844). ROM is bootstrap/source input only. After extraction/verification, runtime loads must resolve through extracted typed archive source, FileProvider/catalog provider source, or deterministic source-derived cache. Any ROM/RomProvider fallback needed because that chain is missing must fail loudly and be tracked as a migration defect at the owning asset-family boundary.
- **Source-only gate rejects raw extraction cache** (2026-05-28, B-382). FileProvider alone is not enough to satisfy the native-source contract: `data/<romid>/files`, `data/<romid>/segments`, and `.bin` paths are bootstrap/cache products, not clean public typed-archive source. The Debug source-only gate rejects those paths so c3844 cannot be falsely closed by replacing RomProvider handles with raw extracted ROM dumps.
- **Scenario stage setup/pads/tiles source gate** (2026-05-28, B-381). Scenario source-only mode now checks stage setup, briefing setup, pads, and tiles at the handle boundary. These runtime loads fatal with `ASSET.SOURCE_ONLY` if the stage still uses ROM/RomProvider handles, so `.pdscenario` gaps are exposed instead of being masked by legacy setup/pads/tile loads. The full source conversion remains under `c3844-s1`.
- **Scenario pads consume public source** (2026-05-28, B-383). Stage load now compiles `.pdscenario` `pads.tsv` through `scenarioSourceLoadPadsForStage()` into the runtime padfile layout before any legacy pad-handle fallback. The Scenario walker binds `pads.tsv` and related public setup members as archive-member FileProvider paths.
- **Scenario navigation tables consume public source** (2026-05-28, B-384). `.pdscenario` now requires decoded `navigation/waypoints.tsv`, `navigation/waygroups.tsv`, and `navigation/covers.tsv`, and the stage loader compiles them from archive-member FileProvider paths into runtime waypoint/group/cover tables. Empty tables mean the authored scenario is opting into deterministic generation from scene, pads, and volumes; extracted base archives carry decoded OG data for parity.
- **Scenario scene source feeds runtime tile cache** (2026-05-28, B-385). Generated `.pdscenario` `scene.glb` carries `_PD_ROOM` vertex metadata, the GLB compiler preserves room tags into colmesh triangles, and `tilesReset()` now compiles the runtime tile cache from the active Scenario scene/collision colmesh before legacy tile fallback. Chicago smoke verification proved 107 rooms / 6,661 tiles from `base_scenario_chicago.pdscenario::scene.glb`.
- **Scenario/Mission graph source activation is runtime-backed** (2026-05-28, B-385). `setupLoadFiles()` now activates `.pdscenario::level.graph.json` and, for solo stages, the matching `.pdmission::mission.graph.json` through real archive-member `fsFileLoad()` paths before setup fallback. If the stage row has no explicit scenario ref, runtime derives the source binding from the active stage catalog ID as `namespace:scenario_<stage_slug>` and resolves that catalog row. The active level graph table refs now select the public pads, volumes, setup fields, objects, objectives, waypoints, waygroups, and covers source members used by runtime loaders, and `volumes.tsv` is parsed into graph-owned trigger-volume source rows. Generated level graphs now also emit explicit `scenario.trigger.volume.source` nodes and activation validates the node count against public `volumes.tsv` rows before the trigger-volume source table is accepted. Generated `.pdmission` archives now mirror decoded scenario objective rows as `mission.objective.source` and `mission.objective.criteria.source` graph nodes, `objectives.tsv` points each row at the graph node plus scenario source row, `objectiveInsert()` validates the public graph row/difficulty/criteria sequence, active mission graphs drive objective criteria evaluation order, and Enter Room, Throw In Room, Holograph, COMPFLAGS/FAILFLAGS mission-stage flags, and tagged Destroy/Collect/Throw/Holograph object state now keep mutable runtime state in graph-owned state before `objectiveCheck()` records against the active mission graph. Enter Room and Throw In Room criteria also ask the graph-owned trigger-volume table to resolve pad/room matches whenever a level graph is active. Missing or invalid graph source/table refs are source-chain failures under the selected source-only family. Full behavior execution still needs the graph parity cutover: the OG backend remains a reference/parity backend until global settings, mission phase flow, broader trigger behavior, and AI action modules are replaced one by one with native graph nodes. Setup behavior links are now source-guarded through graph setup-link records.
- **Weapon source-gated runtime now proves nested mesh public sources** (2026-05-28, B-388). Final `weapon_match_source_gate_smoke` passed 35/35 with `base:dy357`, `base:model_dy357_hi`, and `base:model_cartridge_rifle` loaded from extracted public archive sources, no `Gdy357Z.bin`/`GcartridgeZ.bin` fallback, and no DY-357 `Falcon 2` fire-mode mismatch.
- **Debug source-only gate proves native loading one family at a time** (2026-05-27, c3842-s10). Settings > Debug exposes `Debug.AssetSourceOnlyType`, with one selected archive family at a time. Selected-family loads must come from public FileProvider source; catalog typed lifecycle loading and the file/texture/animation/sound gateways refuse ROM/static fallback so playtests expose remaining migration gaps instead of silently masking them.
- **Clean two-zone asset archive layouts frozen** (2026-05-24, c3824). Every current typed or otherwise referenceable family has a root descriptor and clean authoring-zone layout recorded in [designs/modding/asset-archive-clean-formats.md](../designs/modding/asset-archive-clean-formats.md). New emitters write manifest, inventory, provenance, validation, source handles, and hashes under `_meta/`; transition readers may accept old root metadata, but release/package gates must reject non-zip typed files, `.pdwpn`, authored `.bin`, missing root descriptors, root machine-metadata clutter in new outputs, and unresolved internal references.
- **Strict typed archive conformance** (2026-05-26, c3842 follow-up). Archive validation is family-schema exact, not a loose "at least one authorable file" check. `tools/asset_archive_conformance.py` opens root and embedded typed archives, checks required and allowed public entries, rejects stale public layouts and numeric/legacy public asset refs, and validates `_meta/manifest.json` recursively. Normal `.pdarena` archives must embed an intact `.pdscenario` under `dependencies/assets/scenarios/`; explicit Random selector meta-arenas are the only no-scenario variant.
- **Definitive optional-slot rule** (2026-05-27, c3842 reopened). "Allowed optional files" are not generic tolerance. Every optional public entry, dependency glob, and `_meta/` entry needs a recorded semantic role, owner subsystem/tool, loader/importer behavior, deterministic absence behavior, and final-vs-transition status. If that justification does not exist, the slot is invalid and the conformance validator must reject it.
- **Scenario archives must be human-readable source, not raw setup dumps** (2026-05-25, c3841; setup-field follow-up 2026-05-28). The `.pdscenario` public zone centers on textured `scene.glb`/`scene.gltf` as both DCC-openable source and scenario runtime source, with optional collision override, explicit pads/volumes/spawns, deterministic navmesh-generation inputs, decoded setup/objective tables, and graph-linked triggers/global settings. Raw `setup.tsv`/`mpsetup.tsv` word dumps are not public outputs; `objects.tsv`, `setup.fields.tsv`, `objectives.tsv`, `navigation.ini`, `level.graph.json`, and `.pdmission` `mission.graph.json` are the readable source entry points.
- **Asset archive modularization verification gates** (2026-05-24, c3838). The approved family boundaries are structurally sound, but implementation is not complete until [audits/asset-archive-modularization-verification-2026-05-24.md](../audits/asset-archive-modularization-verification-2026-05-24.md) is satisfied: catalog types/mappings, archive policy rows, scanner/packer/distribution descriptor maps, match-reachable manifest coverage, runtime utilization adapters, and the shared `_meta/manifest.json` dependency schema must all agree.
- **Weapon graph asset direction** (2026-05-21, c3814). The authored weapon extension is `.pdweapon` only; `.pdwpn` is fully deprecated, was never released, and must be removed rather than accepted, aliased, migrated, or supported for compatibility. Weapon behavior is graph JSON compiled to deterministic runtime IR. Physical projectile and deployed/thrown entity behavior are first-class `.pdprojectile` and `.pdentity` catalog assets, and weapon archives must embed all authored dependency payloads needed to edit, share, clone, and load the weapon, including nested projectile/entity behavior payloads. `.pdentity` is behavior/archetype data and does not replace `ASSET_PROP`. Exact duplicate embedded payloads share by SHA-256 over canonical archive content after ingestion. The base behavior audit is in [designs/modding/base-weapon-behavior-coverage.md](../designs/modding/base-weapon-behavior-coverage.md), with the current 86-weapon parameter matrix in [designs/modding/base-weapon-parameter-matrix.md](../designs/modding/base-weapon-parameter-matrix.md), module parameter spec in [designs/modding/weapon-graph-module-parameters.md](../designs/modding/weapon-graph-module-parameters.md), and runtime cutover split in [designs/modding/weapon-graph-runtime-cutover-plan.md](../designs/modding/weapon-graph-runtime-cutover-plan.md).
