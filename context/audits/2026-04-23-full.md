#### MEDIUM - 2 new findings (working-tree hygiene)

**AUDIT-23-M1 - `CMakeLists.txt` has a UTF-8 BOM in the working tree, uncommitted.**

- **Severity:** Medium
- **Area:** Code Quality / Build
- **Confidence:** Confirmed
- **Location:** `CMakeLists.txt:1` (working tree). Byte dump: `ef bb bf 63 6d 61 6b 65 5f 6d 69 6e 69 6d 75 6d` (BOM + `cmake_minimum`).
- **Lineage:** Authored in Cursor editor. The same byte was introduced on-commit in `bd9a07d7` (Cursor-authored), silently removed in a later auto-commit (`00637b13` area), and is now back as an uncommitted local edit.
- **Pillar Impact:** None directly. Build hygiene.
- **What We Found:** `git diff CMakeLists.txt` shows the only change is the 3-byte BOM prefix on line 1. CMake 3.16+ tolerates BOMs on the top file, but the flip-flop pattern (BOM in, BOM out, BOM back in) indicates an editor or tool is re-encoding the file every time it is opened.
- **Why It Matters:** (a) silent churn on every session pollutes diffs and masks real changes; (b) a hex-sensitive consumer (a shell-include, a patch tool, a CI linter checking for BOM) can trip on it; (c) file encoding drift is a reliable early signal of other encoding problems coming from the same editor (see AUDIT-23-M2).
- **Risk If Not Fixed:** Low immediate; medium-term this class of issue is a supply-chain cost - every contributor using the same editor will produce identical BOM-add diffs that someone has to strip.
- **Recommendation:**
  1. Strip the BOM from the working tree (`sed -i '1s/^\xEF\xBB\xBF//' CMakeLists.txt` or open/save via a normal editor).
  2. Find the editor / tool adding it (likely Cursor's default text encoding on this host). Change its default to "UTF-8 without BOM".
  3. Add a CI / pre-commit sanity check that rejects BOM on `*.txt`, `*.cmake`, `*.c`, `*.h`, `*.cpp` under the repo root.
- **Cross-System Changes Required:** No (single file + editor settings).

**AUDIT-23-M2 - `.gitignore` has no Word / Excel lock-file pattern, and a lock file did land in a Cursor commit.**

- **Severity:** Medium
- **Area:** Code Quality / Supply Chain
- **Confidence:** Confirmed
- **Location:** `.gitignore` (no `~$*` entry), `bd9a07d7` (committed `~$2_Implementation_Plan_Apr20.docx`, 162-byte Office lock file), `00637b13` (removed it).
- **Lineage:** Authored in PD2 via Cursor. The lock file is a classic Office artifact generated when a `.docx` is open.
- **Pillar Impact:** None directly.
- **What We Found:** Cursor committed a Word-generated `~$...docx` lock file in `bd9a07d7` along with the legitimate `PD2_Implementation_Plan_Apr20.docx`. It was removed in `00637b13`, but only because the file was deleted locally - not because `.gitignore` stopped it. The same pattern could recur any time a `.docx` in the repo root is open in Word during an auto-commit window.
- **Why It Matters:** Office lock files are ephemeral local state and should never enter history. Once committed, they are indistinguishable from real binaries in `git log --stat` output, they add noise to release bundles, and (for `~$` files specifically) older Windows tools occasionally choke on the leading tilde.
- **Risk If Not Fixed:** Low direct; medium long-term because dev-window auto-commit runs regardless of whether files in the working tree are transient.
- **Recommendation:**
  1. Add `~$*` to `.gitignore` alongside the existing build-artifact block.
  2. Consider also adding `*.tmp`, `*.swp`, `*~`, `.DS_Store`.
  3. Tighten the dev-window "auto-commit before release" step to use an explicit include list instead of `git add -A` (aligns with CLAUDE.md standing order 9: "prefer adding specific files by name rather than using git add -A").
- **Cross-System Changes Required:** No.
