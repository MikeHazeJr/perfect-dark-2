## Product note — “Go online” without a dedicated server (Mike’s direction)

**Question:** Is a simple in-client “go online” path (direct connect / P2P-style lobbies without running `PerfectDarkServer.exe`) *technically ad-hoc*?

**Audit position:** **No — it is not inherently ad-hoc at the transport/session layer.** The ENet stack already distinguishes **dedicated** vs **listen** hosting:

- `netStartServer()` in `port/src/net/net.c` allocates slot 0 to the local player when **`!g_NetDedicated`** (listen server), and leaves slot 0 free when **`g_NetDedicated`** (dedicated). Startup and CLI wiring (`--host`, `--dedicated`, `g_NetHostLatch`) already exist.
- What is *currently* enforced in product/UI is **dedicated-server-first discovery/join**, not an absence of listen-server capability: `port/fast3d/pdgui_menu_network.cpp` (file header, lines 4–6) and `port/src/net/netmenu.c` (lines 4–8) explicitly document **clients never host** and **legacy host menus removed**.

**Implication:** Adding a “Host / Go online” flow that calls `netStartServer()` (without `--dedicated`) is primarily **UX + gating + test matrix** work, reusing the same authority model the server already runs. That is **orthogonal** to the **game-agnostic dedicated server** goal: the dedicated binary can remain the long-term, plugin-bound host for operators, while the game client offers **embedded listen hosting** for casual sessions. The “ad-hoc” risk is **operational** (two hosting stories, NAT/ROM-check differences, support burden), not that the code path is a hack.

**Conflicts:** None with “committed to game-agnostic dedicated server” *if* that pillar applies to the **headless server binary** and its plugin boundary — not to forbidding listen-server in the client.

# 1) Inferred Project Goal & Intended Outcomes

### Inferred Purpose

- Modern PC port of *Perfect Dark* with **Catalog-first** asset identity, **mod/native parity**, **ENet-based** multiplayer, **rooms/hub** on the authoritative process, and a **separate dedicated server** binary for unattended hosting.
- **PD2-native** goals: Grid/social, modding pipeline, client online flows, and (stated) **game-agnostic** dedicated server — i.e. PD2-specific simulation and tables must not be the long-term core of `pd-server`.

### Likely Player & Contributor Types

- LAN / small-group players wanting **quick host** from one game install.
- Dedicated operators hosting **24/7** or large sessions via `PerfectDarkServer`.
- Modders and contributors touching Catalog, ImGui menus, and `port/src/net/*`.

### Core Workflows / Gameplay Loops (Inferred)

1. **Solo / CI** — offline; Catalog resolves assets; mods load like native.
2. **Online vs dedicated server** — connect by connect-code/browser; authenticate; rooms; lobby leader sends `CLC_LOBBY_START`-class flows; stage start with manifest/catalog sync.
3. **(Desired)** **Listen host from client** — same protocol as (2), but authority runs inside the game process (`g_NetLocalClient` at slot 0).

### Upstream Lineage Observations

- Large `src/game/` body matches **n64decomp** lineage (types, structure).
- **`port-net`-style** ENet, lobby, and distribution layers — experimental upstream, hardened in PD2 (protocol v38, catalog strings, cookies, admin RCON, room passwords, query handshake per `port/include/net/net.h`).

### Pillar Observations

| Pillar | Observation |
|--------|----------------|
| **Catalog SOT** | Strong: v27+ wire uses catalog ID strings; internal `net_hash` in `assetcatalog.c` is cache key, not wire identity. |
| **Mod / native parity** | Generally enforced; wire-delivered mod path has had asymmetry history — `netdistrib.c` + typed registration work continues. |
| **Modding pipeline** | Determinism and signing (updater Ed25519, manifest SHA) improved in recent waves; supply-chain still operator-dependent. |
| **Grid / social** | Hub/room layer (`hub.c`, `room.c`) is server-side; trust boundaries for any future Grid payloads must stay validated. |
| **Dedicated-server boundary** | **Not met** for “game-agnostic” — `server_stubs.c` still embeds PD2 globals and arena tables (see findings). |
| **Scaling** | Many loops scale with `NET_MAX_CLIENTS` (32); match slots still bounded by `MAX_PLAYERS`/`MAX_BOTS` and **u64** participant mask (64 bits). |

### Assumptions / Unknowns

- Runtime behaviour under packet loss, NAT collapse, and malicious peers requires fuzzing and live tests — not fully provable from static review alone.

# 2) Design Intent & Gameplay / Multiplayer Fit Review

### System & Workflow Validation Findings

#### Critical Issues

**C-1 — Game-agnostic dedicated server pillar still structurally unmet (policy vs code)**

- **Severity:** Critical (for the *pillar*, not necessarily for shipping PD2-only hosting)
- **Confidence:** Confirmed
- **Location:** `port/src/server_stubs.c` (PD2 globals, `g_MpArenas`-class data), `port/src/server_main.c`, `port/src/server_bridge.c`
- **Lineage:** Authored-in-PD2 (server split)
- **Pillar Impact:** Dedicated-server Boundary
- **Intended Outcome:** Server core reusable across games with PD2 behind a plugin API.
- **Current Behavior:** Stubs import `types.h`/`data.h` shapes and define PD2-specific state; networking references match config and lobby structures tied to PD2.
- **Gap:** No stable plugin ABI separating “core” from “PD2 game DLL”; refactoring cost remains **multi-week**.
- **Why It Matters:** Committed roadmap must plan budget; otherwise pillar text and code diverge indefinitely.
- **Risk If Not Fixed:** Maintainer confusion, impossible hiring bar for “second game” until boundary exists.
- **Recommendation:** Treat as **explicit programme of work**: plugin interface doc, stub reduction, message dispatch tables — parallel to feature work, not a single PR.
- **Cross-System Changes Required:** Yes (build, netmsg dispatch, stubs, possibly CMake targets)
- **Blocks Intended Outcome?:** Partially — blocks *pillar* as written, not PD2 online play.

#### High Priority Findings

**H-1 — Client “no host” product rule vs engine listen-server**

- **Severity:** High (for the **stated new goal**: in-client go-online / P2P-friendly hosting)
- **Confidence:** Confirmed
- **Location:** `port/fast3d/pdgui_menu_network.cpp:4-6`, `port/src/net/netmenu.c:4-8`; contrast `port/src/net/net.c:784-793`
- **Lineage:** Authored-in-PD2
- **Pillar Impact:** Online-mode Boundary
- **Intended Outcome:** User wants optional **listen hosting** without dedicated server.
- **Current Behavior:** Engine supports listen server; **UI and menu docs** say clients never host.
- **Gap:** No first-class Host wizard; debug menu can still call `netStartServer` (`pdgui_debugmenu.cpp` pattern).
- **Recommendation:** Add Host flow (port selection, firewall copy, optional UPnP/STUN status) calling `netStartServer` with `g_NetDedicated == false`; unify copy with dedicated server constraints (ROM/mod checks already differ for `!g_NetDedicated` in `netmsg.c` comments).
- **Cross-System Changes Required:** Yes (ImGui + net init order + tests)

**H-2 — Participant active mask is u64 (64 slot ceiling on wire)**

- **Severity:** High (scaling / future-proofing)
- **Confidence:** Confirmed
- **Location:** `src/game/mplayer/participant.c:364-399` (`i < 64` in encode); consumers in `netmsg.c` for `SVC_STAGE_START`
- **Lineage:** Authored-in-PD2 (B-12 Phase 3)
- **Pillar Impact:** Scaling Ceiling
- **Gap:** Raising `MAX_BOTS`/`MAX_PLAYERS` combination above 64 slots **silently truncates** mask semantics.
- **Recommendation:** `_Static_assert(MAX_PLAYERS + MAX_BOTS <= 64, …)` at compile time; long-term: variable-width mask or tiered message if slot count grows.

**H-3 — Dual hosting models increase test and security surface**

- **Severity:** High (operational / security)
- **Confidence:** Probable
- **Location:** Systemic — listen vs dedicated auth paths (`netmsg.c` ROM/mod checks gated on `!g_NetDedicated`)
- **Pillar Impact:** Trust-Boundary
- **Gap:** Two ways to be “server” implies two sets of abuse cases (local trust vs internet exposure).
- **Recommendation:** Document threat model per mode; ensure listen host defaults (firewall, token, rate limits) match dedicated where applicable.

#### Medium Priority Findings

**M-1 — `mpParticipantsEncodeActiveMask` loop uses `i < 64` not `capacity`**

- **Severity:** Medium
- **Confidence:** Confirmed
- **Location:** `participant.c:372`
- **Gap:** If `capacity` were ever > 64, slots 64+ never encode into mask (silent drop).
- **Recommendation:** Static assert tying `capacity` to wire format or assert `capacity <= 64` in debug.

**M-2 — Hub room 0 compatibility path**

- **Severity:** Medium
- **Confidence:** Confirmed (by comment)
- **Location:** `port/src/hub.c:9-12` — room 0 lifecycle synced from `g_Lobby.inGame` for backward compatibility.
- **Gap:** Multi-room evolution may carry legacy assumptions; easy to regress single-match flows.
- **Recommendation:** Track explicit “room 0 = legacy” in ADR; add integration test hooks when multi-room matures.

**M-3 — SP-1 class: `g_AmMenus[MAX_PLAYERS]` etc.**

- **Severity:** Medium (crash class)
- **Confidence:** Probable (systemic-bugs.md lists remaining sites)
- **Location:** e.g. `src/game/activemenu.c` / `bss.h` patterns
- **Recommendation:** Continue SP-1 grep-driven cleanup; never index `MAX_PLAYERS` arrays with bot mpindex.

#### Low Priority Findings

**L-1 — Internal catalog `net_hash`**

- **Severity:** Low
- **Confidence:** Confirmed
- **Location:** `port/src/assetcatalog.c` — CRC32 cache; not wire per `net.h` v27 note.
- **Recommendation:** Keep naming distinct from “wire hash”; document as internal only.

# 4) Security, Trust & Privacy Review

### Critical Issues

*No new Critical beyond systemic trust model (public hosting still depends on operator hardening).*

### High Priority Findings

**S-1 — `CLC_ADMIN` / `ADMIN_SUB_AUTH` online brute-force**

- **Severity:** High
- **Confidence:** Confirmed
- **Location:** `port/src/net/netmsg.c:6965-6977` — verify token path with logging, no per-client rate limit
- **Area:** Security
- **What We Found:** Constant-time verify does not limit attempt rate; log spam on failures.
- **Recommendation:** Rate-limit / lockout / disconnect policy; increase minimum token length at boot.

**S-2 — `netServerIssueCookie` documents non-CSPRNG mixing**

- **Severity:** High
- **Confidence:** Confirmed
- **Location:** `port/src/net/net.c:1301-1335`
- **What We Found:** Comment admits “Not a full CSPRNG”; uses `time`, performance counter, rolling SHA-256.
- **Recommendation:** OS CSPRNG bytes per cookie (`BCryptGenRandom` / `getrandom`) or seed once from CSPRNG at boot.

**S-3 — Ban list save atomicity & IPv6 canonicalization**

- **Severity:** High
- **Confidence:** Probable (static review; platform-specific)
- **Location:** `port/src/server_bans.c`
- **What We Found:** Replace/remove/rename pattern and string equality for addresses — known Windows + IPv6 caveat class.
- **Recommendation:** Atomic replace APIs + `inet_pton`/`inet_ntop` canonical compare path.

### Medium

- **Admin payload truncation** for LIST/STATUS when buffers fill (`netmsg.c` admin handlers) — operational visibility risk.
- **Query handshake (SEC-7)** — documented in `net.h`; ensure all server query paths use challenge-response (verify in deployment configs).

### Positive Observations

- **Protocol v38** bundles identity cookie, room passwords, admin channel, query mitigation — strong iteration.
- **`netbufReadStr`** NUL-termination enforcement (`netbuf.c:120-129`) closes a former systemic string hazard class.

# 5) Cross-Cutting Risks & Architecture Concerns

1. **Listen vs dedicated** — Engine supports both; **product** currently steers users to dedicated only. Reintroducing listen for “go online” must be a **deliberate UX + security** decision, not a hidden debug feature.
2. **Pillar honesty** — Game-agnostic server requires **interfaces**, not more stubs — coordinate docs (`pillars` / README) with roadmap.
3. **Scaling** — `NET_MAX_CLIENTS` (32) vs match slots (8+32) vs u64 mask (64) — three different ceilings; document the binding constraint for designers.
4. **Catalog** — Internal hash vs wire ID discipline is good; keep boundary reviews on any new “shortcut” resolver.
5. **Determinism** — Float / AI paths in `src/game/` remain legacy-heavy; net sync assumptions need ongoing regression.
