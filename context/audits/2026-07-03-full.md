#### High Priority Findings

- **CONNECT-CODE-DUPLICATES — Connect-code word tables contain 13
  duplicate entries across all four slots; some IP octets cannot
  round-trip**
  - Severity: High
  - Confidence: Confirmed
  - Location: `port/src/connectcode.c:28` (`s_Adjectives`),
    `:67` (`s_Nouns`), `:106` (`s_Actions`), `:177` (`s_Places`);
    matcher `:283-322` (`matchSlot`, longest-match with strict
    `plen > bestLen` → first-index wins on ties).
  - Lineage: Authored-in-PD2
  - Pillar Impact: Online-mode Boundary (connect codes are the
    sole join mechanism per `constraints.md:62`).
  - Intended Outcome: Connect codes encode a peer's IPv4 address
    + port as a 4-word or 6-word human-shareable sentence; every
    encoded value must decode back to the same bytes.
  - Current Behavior: The encoder writes `s_Table[byte]`; the
    decoder scans linearly and returns the *first* index whose
    word prefix-matches. When a word appears at two or more
    indices, the higher index's byte value silently maps to the
    lower on decode. Enumerated duplicates (Python-verified):
    - `s_Adjectives` (256): `"noble"` at 0x42, 0xe7 (1 collision)
    - `s_Nouns` (256): `"parrot"` at 0x1b, 0xc8; `"lantern"` at
      0x9a, 0xef (2 collisions)
    - `s_Actions` (256): `"charging toward"` at 0xa2, 0xe3;
      `"marching toward"` at 0xa3, 0xe0; `"materializing at"`
      at 0xd4, 0xec (3 collisions)
    - `s_Places` (256): `"a volcano"` at 0x38, 0xc0; `"a glacier"`
      at 0x3a, 0xc1; `"the colosseum"` at 0x76, 0x95, 0xca (triple);
      `"the pentagon"` at 0x91, 0xc8; `"the kremlin"` at 0x93,
      0xcb; `"the bermuda triangle"` at 0x9b, 0xf4; `"shangri-la"`
      at 0x9e, 0xf7 (8 non-first-index values silently collide)
  - Gap / Failure Mode: **14 IP octet values across the four
    slots decode to a different value than they encode.** For
    a random IPv4, per-byte collision probability is roughly
    1/256, 2/256, 3/256, 8/256 for the four slots → **~4.4%
    of random IPs will produce a connect code that
    non-round-trips.** Ports (6-word variant, extra 2 slots)
    face the same odds.
  - Why It Matters: `constraints.md:62` mandates connect codes
    as the *sole* mechanism for sharing server addresses; there
    is no raw-IP UI fallback. A user with a non-round-tripping
    IP genuinely cannot host a game. This has been in the tree
    since Session 49 without a uniqueness check.
  - Risk If Not Fixed: A silently-corrupted IP either fails to
    connect (visible bug: "join always times out") or, worse,
    connects to a *different* peer's IP (silent misroute — an
    unrelated third party receives the join attempt, potentially
    exposing their IP to unknown peers).
  - Recommendation: (a) Immediate: replace duplicates with unique
    words (word banks are large; 13 substitutions is trivial).
    (b) Add a startup `_Static_assert` (or a runtime `assert` in
    `connectCodeInit`) that walks each 256-entry list and
    verifies every entry is unique. Fail-loud on ship-time
    regressions. (c) Add a test that exhaustively round-trips
    all 2^32 IPv4 values through
    `connectCodeEncode`→`connectCodeDecode` and asserts identity
    (or, more efficiently, tests that each of the four tables
    is bijective by index).
  - Cross-System Changes Required: No (self-contained in
    `connectcode.c`).
  - Blocks Intended Outcome?: Partially (~4.4% of would-be hosts
    silently blocked or misrouted).

- **SAVE-MIGRATE-NOT-WIRED — Save load path never invokes
  `saveMigrateFile`; v1 saves are silently consumed as v2**
  - Severity: High
  - Confidence: Confirmed
  - Location: `port/src/savemigrate.c:145` (function defined),
    `port/include/savemigrate.h:95` (declared), zero call sites
    in `src/` or `port/`. Save load path in
    `port/src/savefile.c:230-244` (`saveCheckFileVersion`)
    logs a `LOG_NOTE` for `fileVersion < SAVE_VERSION` and
    returns 0 — no migration invoked; the "forward-compat
    fallthrough" is the loader's unknown-key skip.
  - Lineage: Authored-in-PD2
  - Pillar Impact: Save/Wire Format
  - Defect Class: None (semantic gap)
  - Intended Outcome: `SAVE_VERSION` bumped from 1 to 2 for
    SA-4 (session/string IDs replaced raw integers in save
    payloads). A v1 save on a v2 binary should either be
    migrated (fields renamed / added / removed) or loudly
    rejected.
  - Current Behavior: `saveMigrateInit()` registers **zero**
    migrations (comment at `savemigrate.c:8` is stale — still
    says "Currently SAVE_VERSION = 1"). `saveMigrateFile` is
    declared but never called; the load path merely logs the
    version mismatch and continues. A v1 save keyed with
    integer body/head fields will match nothing in the v2
    string-ID reader and default silently to fallback values
    (agent 0 / no character).
  - Gap / Failure Mode: Player character choice + progress from
    v1 saves silently disappears on first v2 boot with no
    diagnostic other than a `LOG_NOTE`.
  - Why It Matters: This was called out as PARTIAL in 06-26
    (version bumped; migration list empty). Verification this
    week confirmed the actual state is worse: **the migration
    function is defined but never wired**. Silent-consume beats
    loud-fail every time when data integrity is at stake.
  - Risk If Not Fixed: Users with v1 saves lose data with no
    warning. If SA-4 is the reason SAVE_VERSION bumped, the
    field rename means the load code cannot even represent v1
    identity — it needs a real migration, not just a version
    check.
  - Recommendation: (a) Wire `saveMigrateFile` into
    `saveCheckFileVersion` when `fileVersion < SAVE_VERSION`.
    (b) Register at least the integer→string-ID migration for
    body/head/scenario. If migration is intentionally deferred,
    switch the load path to loud-reject
    (`LOG_WARNING` + skip load) so users see the problem.
    (c) Update the stale comment at `savemigrate.c:8`.
  - Cross-System Changes Required: No.
  - Blocks Intended Outcome?: Yes (data loss without warning).

- **NET-WIRE-CLIENTID-CEILING — `netclient.id` widened to u32
  in memory but still serialized as u8 on the wire; hidden
  254-client ceiling**
  - Severity: Medium
  - Confidence: Confirmed
  - Location: `port/include/net/net.h:362` (`u32 id` in-memory),
    `port/include/net/net.h:224` (`NET_MAX_CLIENTS = 32`),
    wire serialization at `port/src/net/netmsg.c:1330, 2042,
    2161, 2554, 6935, 6984, 7768` (all `netbufWriteU8(dst,
    ncl->id)`).
  - Lineage: Authored-in-PD2 (pre-existing pattern, surfaced
    by this pass's scaling sweep)
  - Pillar Impact: Scaling Ceiling, Online-mode Boundary
  - Defect Class: Scaling
  - What We Found: The in-memory client id is `u32` (4B
    representable values) but every wire write uses
    `netbufWriteU8`, capping the wire representation at 256
    IDs. `NET_NULL_CLIENT = 0xFF` steals slot 255, giving an
    effective ceiling of 254 clients. `NET_MAX_CLIENTS = 32`
    is well below that today, but bumping it above 254 (a
    plausible dedicated-server target when S486 unfreezes)
    would silently truncate on the wire without any static
    assert.
  - Why It Matters: PD2's declared scaling target is host-
    or server-bound, not a fixed cap. This is exactly the
    class of hidden ceiling the audit prompt calls out.
  - Risk If Not Fixed: A future protocol bump that grows
    `NET_MAX_CLIENTS` past 254 silently truncates client
    IDs at wire boundary; the mismatch produces desyncs
    that only appear at scale (>254 clients on a single
    server).
  - Recommendation: (a) Add
    `_Static_assert(NET_MAX_CLIENTS < NET_NULL_CLIENT, ...)`
    in `port/include/net/net.h` near line 224. (b) Consider
    a typed `netbufWriteClientId()` helper so future
    protocol bumps to u16 don't require diff-hunting every
    `netbufWriteU8(dst, ncl->id)` call site.
  - Cross-System Changes Required: No.
  - Blocks Intended Outcome?: No (not visible until
    >254 clients).

- **PDEFFECT-N64-STRIDE-LATENT — `OBJTYPE_PADEFFECT` returns
  PC-struct `sizeof` with no `n64_padeffectobj` sibling —
  Phase 2.5 tripwire**
  - Severity: Medium
  - Confidence: Confirmed
  - Location: `port/src/preprocess/filesetup.c:97`
    (`case OBJTYPE_PADEFFECT: return sizeof(struct
    padeffectobj) / sizeof(u32);`); `port/include/preprocess/
    setup.h` has no `struct n64_padeffectobj`.
  - Lineage: Authored-in-PD2 (pre-existing pattern, adjacent
    to this pass's GASBOTTLE/SAFE fix)
  - Pillar Impact: Modding Pipeline
  - Defect Class: Layout
  - What We Found: The B-944 fix commit `68c5007f` fixed
    GASBOTTLE by switching to `n64_defaultobj` stride and
    fixed SAFE conversion. Three other switch cases still
    return PC-struct sizeof (`LINKGUNS`, `GRENADEPROB`,
    `PADEFFECT`). Two are byte-identical to their `n64_`
    siblings by structural coincidence (only word-sized
    fields). `PADEFFECT` is worse — it has no `n64_`
    counterpart at all. Currently safe (all fields are
    word-sized scalars), but if any future PC-side edit
    adds a pointer field or a wider type, the stride
    silently diverges from N64 wire binary with no
    build-time signal.
  - Why It Matters: This is the same class of bug as B-944
    caught latently. `constraints.md:41-42` mandates
    integer-native geometry runtime boundaries stay tight;
    layout drift at the ROM setup boundary is exactly what
    Phase 2.5 hunts for.
  - Risk If Not Fixed: A refactor that adds a pointer to
    `padeffectobj` on the PC side silently corrupts every
    stage that carries `OBJTYPE_PADEFFECT` in its setup
    binary — no compile error, no runtime error, just
    setup-stream corruption downstream of that obj.
  - Recommendation: Add `struct n64_padeffectobj` to
    `port/include/preprocess/setup.h` (a plain mirror of
    the current PC layout, but the *contract* — future
    PC edits must not diverge from it). Update
    `filesetup.c:97` to use it. This makes any future
    divergence a compile error (via `_Static_assert` if
    added) instead of silent corruption.
  - Cross-System Changes Required: No.

  - Severity: Medium

  decodes to.

### Medium Priority Findings

- **NET-AUTOSTART-LOG-EXPOSURE** (carry from 06-26).

- **MODASSET-ANIM-FIELD-OVERFLOW — partial fix**. The
  06-26 High is downgraded to Medium/Low. The
  `cap_frames > 0xffff → goto bad` guard at
  `port/src/modasset_compiler.c:2984` caps the multiply
  input so 65535 × expect_fields × 4 bytes cannot overflow
  `size_t` on 64-bit. `expect_fields` remains implicitly
  bounded by schema (max ~11 per part-field), but there is
  no explicit cap in the code path. On the target 64-bit
  build the residual risk is small. Recommend an explicit
  `expect_fields <= 32` guard alongside the existing
  `cap_frames` cap for defense-in-depth.

- **MODASSET-VTX-MATRIX-PARSE-VALIDATION — still open** (see

  there is no out-of-bounds hazard, but a short JSON array
  silently leaves the tail at `-1` default (which falls
  back to `matrix_index`). This is validation strictness,
  not memory safety — recommend rejecting arrays of
  length != 3.
