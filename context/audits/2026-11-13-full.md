### High Priority Findings

All 26 Highs from 2026-11-06 carry over. The three new Highs this audit are PD-N03, PD-N04 (bondgun.c WIP growth), and the strengthening of PD-H01 to day 31. One carryover (PD-06) is re-scored.

**NEW this audit:**

- **PD-N03 (NEW, HIGH) — `bgunQuantityCall` service dispatches `GGV_QUANTITY_APPLY` by re-entering `bgunSetAmmoQuantity` (ggvExecute self-recursion)**
  - Severity: High · Confidence: Confirmed · Area: Design Fit / Code Quality
  - Location: `src/game/bondgun.c` WIP — `bgunQuantityCall` handler's `GGV_QUANTITY_APPLY` branch calls `bgunSetAmmoQuantity(a.i, b.i)`. `bgunSetAmmoQuantity` itself launches `ggvExecute(ggvStockProgram(GGV_SET_AMMO_QUANTITY))`. If any stock program — or a modder-authored substitute — ever emits `GGV_QUANTITY_APPLY` from inside the ammo-apply program, the host re-enters its own `ggvExecute` with no recursion guard.
  - Lineage: Authored-in-PD2 · Pillar Impact: Modding Pipeline + Scaling Ceiling (stack) · Defect Class: Trust-Boundary (reentrancy)
  - Why It Matters: Stack blow-up on the ammo-pickup hot path. Doubly problematic because the modding pipeline specifically invites third-party authors to compose their own stock programs, and the `GGV_QUANTITY_APPLY` "commit" shape is the natural reuse site in a modder's mental model.
  - Risk If Not Fixed: One malformed or adversarial mod program crashes the host client via stack exhaustion. Observable at the first attempt to pick up ammo in a match using the mod.
  - Recommendation: Split the apply side-effect into a non-recursing internal (e.g., `bgunApplyAmmoQuantityRaw(func, value)`), have the service dispatch that, and keep `bgunSetAmmoQuantity` as the public `ggvExecute` entry. Add a static assertion in the stock program that `GGV_QUANTITY_APPLY` cannot reach the `bgunSetAmmoQuantity` entry.
  - Cross-System: Yes (bondgun + stock-program layer) · Blocks Intended Outcome: Partially.

- **PD-N04 (NEW, HIGH) — Four new GGV conversions in bondgun.c delete the native fallback branch entirely**
  - Severity: High · Confidence: Confirmed · Area: Design Fit · Defect Class: Trust-Boundary (availability)
  - Location: `src/game/bondgun.c` WIP — `bgunSetAmmoQuantity`, `bgun0f0a8c50` (reset function inversion), `bgunIsUsingSecondaryFunction`, `bgunGetReservedAmmoCount`. Each new body logs `"GGV: ... refused immutable program"` on `ggvExecute` failure and then does **nothing** — the previously inline native logic is deleted, not retained as an `else {}` or `#ifdef` fallback. The pre-WIP shape computed the correct answer unconditionally regardless of GGV availability; the post-WIP shape silently returns default/zero/false if the stock program fails validation at runtime.
  - Lineage: Authored-in-PD2 · Pillar Impact: Mod-native Parity (as **widening** of PD-04)
  - Why It Matters: On any program-level validator reject, ammo isn't set / inversion state isn't cleared / `IsUsingSecondary` returns `false` regardless of player state. Hot-path availability has regressed from hard-guaranteed to "depends on GGV program being valid at runtime." The WIP comments inside each body ("`// Check if this ammo type applies...`") describe the deleted native code but don't restore it. The 2026-11-06 PD-04 asymmetry now has four sibling cases where the native path isn't just skipped — it's *removed*.
  - Risk If Not Fixed: Silent gameplay breakage on any session running a mod whose stock program fails revalidation under a stricter build.
  - Recommendation: After each `sysLogPrintf(…"GGV: refused immutable program"…)`, `return` the correct native result (ammo set, inversion flag toggled, secondary-function boolean, reserved count) rather than falling through. The WIP already has the native logic documented in the remaining comments; restore the code the comments describe.
  - Cross-System: No (bondgun only) · Blocks Intended Outcome: Partially.

### Medium Priority Findings

All 2026-11-06 Mediums carry over. One new Medium this audit:

- **PD-N05 (NEW, MEDIUM) — `bgunQuantityWrite` writes `loadedammo[c->function]` without validating `c->function`**
  - Severity: Medium · Confidence: Probable · Area: Code Quality / Security · Defect Class: Trust-Boundary
  - Location: `src/game/bondgun.c` WIP — `bgunQuantityWrite`: `c->player->hands[HAND_RIGHT].loadedammo[c->function] = value.i;`. `c->function` is set earlier by the stock program through `GGV_QUANTITY_FUNCTION`. If a modded or corrupted program emits a function index outside `[0, FUNC_COUNT)`, the write is unbounded into the player struct. The sibling `GGV_QUANTITY_RESERVE` path writes `ammoheldarr[c->ammotype]` in the same shape.
  - Lineage: Authored-in-PD2 · Pillar Impact: Modding Pipeline (mod → engine corruption)
  - Why It Matters: Memory corruption surface opens up at the service boundary — the exact seam that the modding pipeline encourages third parties to extend. A single off-by-one in a modder's authored program lets content corrupt engine state silently.
  - Recommendation: Clamp or reject `c->function` / `c->ammotype` writes at the host service boundary (one bounds check per service, inside the switch case, guarded by the enum's max value). Alternative: treat these bindings as **read-only inputs to a single dedicated service** that performs the apply after a bounded dispatch — ties directly into the PD-N03 recursion fix.
  - Cross-System: Yes (service surface + stock-program authoring docs) · Must-fix before shipping the GGV layer to third-party modders.

### Low Priority Findings

All 2026-11-06 Lows carry over. Three new Lows:

- **PD-N06 (NEW, LOW) — `runner_supervisor.py::Native` re-reads receipt file to compute `ReceiptSha256` (TOCTOU window; also redundant work)**
  - Severity: Low · Confidence: Probable · Area: Security / Code Quality
  - Location: `tools/smoke-verify/runner_supervisor.py:182, 189, 202` — `receipt["ReceiptSha256"] = hash_bytes(plain(receipt["Path"]).read_bytes())` after `storage.write_run`. The write+read pair is inside `storage.locked()`, so another supervisor cannot race, but any out-of-band actor with write access to the retention directory between write and re-read can swap bytes before the hash commits. The writer already holds the bytes it wrote (`json.dumps(value)`); re-reading from disk discards that provenance.
  - Lineage: Authored-in-PD2
  - Why It Matters: `ReceiptSha256` can diverge from actual write-time provenance under adversarial filesystem access — minor because the retention directory is user-owned, but the re-read is also pointless work.
  - Recommendation: Hash the bytes `storage.write_run` wrote directly (return them from `write_run` alongside `Path`), rather than re-reading the file.

- **PD-N07 (NEW, LOW) — `runner_supervisor.py::check_client_identity` uses `type(x) is not int` (brittle to future JSON bridges)**
  - Severity: Low · Confidence: Confirmed · Area: Code Quality
  - Location: `tools/smoke-verify/runner_supervisor.py:50, 66` — `type(claimed.get("pid")) is not int or type(claimed.get("creation_ticks")) is not int`. `bool` is a subclass of `int`, so `type() is int` does correctly reject bool. But any future JSON bridge that returns an `int` subclass (not from `json.loads` directly, which is fine — from a handler layering on top) is rejected with a confusing `StorageError`.
  - Lineage: Authored-in-PD2
  - Why It Matters: Non-breaking today, brittle to future wrappers.
  - Recommendation: `isinstance(claimed.get("pid"), int) and not isinstance(claimed.get("pid"), bool)`.

- **PD-NN01 (NEW, LOW) — `SPECTATE_FRAME_NAME_MAX` read truncates one byte of legitimate payload when fully filled**
  - Severity: Low · Confidence: Confirmed · Area: Code Quality · Defect Class: Layout
  - Location: `port/src/net/netmsg.c:12954-12955` — `netbufReadData(src, (u8 *)blob[i].name, SPECTATE_FRAME_NAME_MAX)` reads exactly `SPECTATE_FRAME_NAME_MAX` bytes then force-nulls `blob[i].name[SPECTATE_FRAME_NAME_MAX - 1] = '\0'`. If the field is declared as `char name[SPECTATE_FRAME_NAME_MAX]` (common), the null-termination truncates a legitimate byte of payload when the sender filled the full width. The read also does not bound-check against the per-participant payload remaining in `src`.
  - Lineage: Authored-in-PD2
  - Why It Matters: Non-fatal (one byte truncated on fully-filled frames), but fragile — would silently desync string comparisons if the name is used for equality anywhere.
  - Recommendation: Either size the field as `[SPECTATE_FRAME_NAME_MAX + 1]` with explicit nulling, or write a bounded-string netmsg helper matching `netbufReadStr`'s shape for fixed-width fields.

- **CC-10 (UNCHANGED)** — Scratch-directory accumulation under `.claude/`. Now 93 untracked entries (was 92); the 2026-10-26 cohort of 40+ `.claude/gameplay-*20261026/` directories is unchanged.

- **CC-12 (NEW this audit) — GGV conversions in bondgun.c are deleting native behavior rather than preserving it under a feature flag**
  - Pattern: Each of `bgunSetAmmoQuantity`, `bgun0f0a8c50`, `bgunIsUsingSecondaryFunction`, `bgunGetReservedAmmoCount` in the WIP is now a thin `ggvExecute` wrapper with the native fallback *removed* and only comments left behind (PD-N04). In parallel, the apply-service dispatch has grown a self-recursion (PD-N03), and the service boundary performs unbounded indexed writes (PD-N05).
  - Shape: this is the GGV migration evolving from "compile-time-validated reinterpretation of native code" to "GGV *replaces* native code." That is a legitimate end state — but the correct order is (1) flag-guarded preservation, (2) parity receipts, (3) native deletion. The current WIP has skipped (1) and (2) and jumped to (3) for four functions.
  - Recommendation: Enforce the sequence. Every GGV conversion commit must preserve the native path under `#ifdef PD_GGV_BONDGUN` (or an equivalent runtime toggle) **plus** add a parity test (`ggv_vs_native_parity_for_bgunSetAmmoQuantity`, etc.) *in the same commit*. Only after the parity matrix is green in CI may a follow-up commit delete the native path. Encode the invariant as a reviewer checklist in `.githooks/` or in a `GGV-CONVERSION.md` note in `context/pillars/modding.md`.
