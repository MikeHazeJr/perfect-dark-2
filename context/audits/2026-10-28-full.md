## 1) Inferred Project Goal & Intended Outcomes

### Inferred Purpose
Perfect Dark 2 is a PC-only re-engineering of Rare's N64 Perfect Dark built on the `n64decomp` → `fgsfdsfgs/port-net` → `jonaeru/allinone` lineage, now diverged into a modding-first platform with: a Catalog-as-single-source-of-truth asset system, decentralized P2P multiplayer (ENet, 6-tier NAT path, listen-host as the shipping model), an ImGui-only menu layer, a first-class modding pipeline (`.pdmod` + typed `.pdxxx` sources with public GLTF-native authoring), a Forge level editor, a Theater record system, and — now in flight — a declarative "gameplay graph" execution layer (GGV) that aims to replace native weapon logic with validated, host-service-backed program graphs. The former standalone dedicated-server product is explicitly deprecated.

### Likely Player & Contributor Types
- Perfect Dark / GoldenEye veterans and speedrunners who want preserved feel without preserved defects.
- Mod authors using Blender / 3DS Max to export standard GLTF/GLB (public typed archive constraint; see PD-03 persistence).
- LAN / friend-group multiplayer hosts; shipping path is in-client listen hosting over connect codes.
- Contributors maintaining the Catalog, extracting ROM content, and (new) migrating native systems onto GGV executable graphs.

### Core Workflows / Gameplay Loops (Inferred)
1. Launch client → authored or extracted base content loads via the Catalog → single-player Campaign or Combat Simulator.
2. Host listen session → connect-code shared → peers join → room/lobby → playlist → match → endscreen → Play Again.
3. Mod author: pack public typed archives → distribute → remote peers extract on join → equal-footing load.
4. Forge: create prefabs → save `.pdmod` → test in Combat Simulator.
5. Theater: record live match → `.pdth` on disk → (future) playback.
6. **(New in flight)** GGV: author stock programs at compile time → bondgun.c dispatches hundreds of weapon operations through `ggvExecute(ggvStockProgram(...), &host, &result)` with host read/write/call shims replacing in-situ C logic.

- **PD-01 (CARRYOVER) — `struct packedpad` bitfield order does not match the preprocessed pad-file word**
  - Severity: Critical · Confidence: Confirmed · Area: Design Fit / Code Quality
  - Location: `src/include/types.h:323-333` (LE branch still declares `liftnum:4; room:10; flags:18`, inverted vs. the preprocessed layout that writes `flags:18; room:10; liftnum:4`). Consumers at `src/game/setuppads.c:230, 234, 248, 250`; working raw-mask site at `:257`. Producer `port/src/preprocess/filepads.c:17-29, 57-61`.
  - Lineage: Inherited-from-n64decomp · Pillar Impact: Scaling Ceiling (indirect) · Defect Class: Layout
  - **Still unfixed on dev tip and in WIP**; no bitfield reorder, no `_Static_assert`, no round-trip test.
  - Recommendation: Reorder bitfield to match the preprocessed word, OR remove the union and use raw mask/shift (like the one working consumer). Add a static assertion that `sizeof(struct packedpad) == 4` plus a round-trip unit test. · Cross-System: Yes. · Blocks Intended Outcome: Partially.

- **PD-02 (CARRYOVER) — PDCA archive format has no version field**
  - Severity: Critical · Confidence: Confirmed · Area: Design Fit
  - Location: `port/src/modpack.c:36, 220-275`; mirrored in `port/src/net/netdistrib.c`.
  - Lineage: Authored-in-PD2 · Pillar Impact: Modding Pipeline · Defect Class: Layout
  - Writer: `u32 magic = PDCA_MAGIC;` + `u16 file_count` (`modpack.c:228-234`). No version word. Any future header change silently misinterprets older artifacts.
  - Recommendation: Insert a `u16` version word after the magic now, bump the magic once, and gate deserialization on the version. · Cross-System: Yes.

- **PD-01A (NEW) — Agent-profile persistence uses `fprintf("%.9g", …)` + `strtod` without locale pinning (saved player data corruption on non-C locale)**
  - Severity: Critical · Confidence: Confirmed · Area: Design Fit / Code Quality
  - Location: Writer: `port/src/agent_profile_codec.c:1005-1028` (`scanline_alpha`, `master_volume`, `music_volume`, `gameplay_volume`, `ui_volume`, `screen_shake_intensity`). Reader: `agent_profile_codec.c:275-288` uses `strtod(buffer, &end)` and rejects when `*end != '\0'`.
  - Lineage: Authored-in-PD2 · Pillar Impact: Modding Pipeline / None (user persistence) · Defect Class: Determinism / Layout (persisted)
  - On a German, French, Dutch, Russian, Spanish, Italian, etc. Windows install (`LC_NUMERIC=de_DE.UTF-8` or equivalent): `fprintf` writes `0,5` but then on the next launch `strtod("0,5", &end)` yields 0.0 with `*end=','`, which the reader rejects as "number is out of range". The user's saved audio levels and visual preferences fail to load and silently reset to defaults every launch. If `LC_NUMERIC` differs between write-time and read-time, the file is corrupt both ways. (The modding-pipeline cache CQ-01 is one call site of this same bug.)
  - Why It Matters: Perfect Dark 2 is distributed free-of-charge to a European-heavy modding community; the single most common entry point to the game — the first launch — writes a settings file that the second launch cannot parse.
  - Risk If Not Fixed: Every non-C-locale user sees their settings reset on each launch; mod playlists, master volume, HUD alpha all drift back to defaults. Possibly reported as "settings don't save" bug reports with no obvious cause.
  - Recommendation: Snap `LC_NUMERIC` to `"C"` for every JSON write path in `port/src/`. Preferred: `uselocale(newlocale(LC_NUMERIC_MASK, "C", (locale_t)0))` scoped around the write and the read (or process-wide at `main()` entry since none of the game text is locale-formatted anyway). Add a CI job that runs `LC_ALL=de_DE.UTF-8 ./pd-tests` (round-trip of settings file). · Cross-System: Yes (settings codec + any shared JSON writer).

- **CQ-01 (CARRYOVER + WIDENED) — Locale-sensitive float formatting is broader than modasset_compiler alone**
  - Severity: Critical · Confidence: Confirmed · Area: Code Quality
  - Location (all unfixed, no `setlocale`/`uselocale` in `port/src`):

  - Lineage: Authored-in-PD2 · Pillar Impact: Modding Pipeline (determinism) · Defect Class: Determinism
  - Beyond the audits-to-date framing, note that `pdeffect_source.c` emits content that lands inside `.pdmod` archives (shippable). - **CQ-02 (CARRYOVER) — Pointer-width truncation in generated-GDL pixel matching**
  - Severity: Critical · Confidence: Confirmed · Defect Class: Layout
  - Location: `port/src/weapon_nested_runtime_harness.c:1117, 1133, 1253-1255` (still: `gdl[i].words.w1 == (uintptr_t)pixels` with `w1` as `u32`).

- **CQ-03 (CARRYOVER) — Unbounded `.pdmod` member allocation (zip-bomb class)**
  - Severity: Critical · Confidence: Confirmed · Area: Security / Code Quality
  - Location: `port/src/weapon_graph_v2_runtime.cpp:245` — `modArchiveExtractMemAlloc(archive, size, path, &length)` with only `!bytes || !length` rejection; result pushed into `std::string`.
  - Pillar Impact: Modding Pipeline (supply chain) · Defect Class: Supply-Chain

- **PD-H02 (NEW) — GGV interpreter has guarded integer division but **unguarded** float division across six opcodes**
  - Severity: High · Confidence: Confirmed · Area: Code Quality / Correctness
  - Location: `port/src/gameplay_graph_values.cpp:3192, 3195-3202, 3256-3258, 3281-3285` — `GGV_I_DIV_F`, `GGV_F_DIV`, `GGV_F_ADD_DIV_I`, `GGV_F_SUB_DIV_I`, `GGV_F_RPM_CREDIT`, `GGV_F_INTERPOLATE` with product/sum variants. Header comment at `gameplay_graph_values.h:553-556` explicitly says "I_DIV_TRUNC and U_SHR use the independently owned guarded gds leaf. A dynamic invalid divisor/count refuses at that node without publishing the final result" — but the comment does not extend to `GGV_F_DIV`.
  - Lineage: Authored-in-PD2 · Pillar Impact: None (determinism-adjacent) · Defect Class: Determinism
  - Current Behavior: `r[n.dst].f = r[n.a].f / r[n.b].f` silently produces `+inf`, `-inf`, or `NaN` on divisor zero. If that result flows into `GGV_TRUNCATE` (`r[n.dst].i = r[n.a].f`), on x86_64 the conversion of a NaN or ∞ to signed `int` is implementation-defined (typically `INT32_MIN = 0x80000000`), which then flows into `GGV_WRITE` for host bindings.
  - Why It Matters: PD2's GGV comment explicitly promises "refuses at that node without publishing the final result" for arithmetic hazards, and the compile-time validator cannot prove `b != 0` for a variable divisor. The exceptional-propagation path is accidental, not designed.
  - Risk If Not Fixed: A stock program whose author later edits a divisor expression can silently publish `INT32_MIN` into `GGV_FIRING` or `GGV_STATE_FRAMES` and corrupt native hand state. The scaffolding is still being authored; this is the right moment to prescribe the discipline.
  - Recommendation: Route float division through a `gds_f32_div(numerator, denominator, out)` leaf that returns refusal (make the current `return 0;` idiom explicit for 1/0 and NaN propagation). Alternatively, add a validator check that denominators of `GGV_F_DIV`/`GGV_I_DIV_F` are compile-time-nonzero `GGV_CONST`s. · Cross-System: Yes (gds + validator + stock programs that currently use variable denominators).

- **PD-H04 (NEW) — `wgV2RuntimeObserveHit` and sibling observers increment per-host counters via `hostFor(r->owner, …)` without owner-generation check (ABA leak into successor player)**
  - Severity: High · Confidence: Confirmed · Area: Code Quality / Correctness
  - Location: `port/src/weapon_graph_v2_runtime.cpp` — `effectObservation()` note "Post-effect evidence must never use deliveryHost as an admission filter. … A snapshot of a newer binding stays distinct from the original producer receipt." Then `wgV2RuntimeObserveDebit`, `wgV2RuntimeObserveNoise`, `wgV2RuntimeObserveHit`, `wgV2RuntimeObserveShotStats` each do:
    ```c
    if (r) if (auto *h = hostFor(r->owner, r->hand)) ++h->hit_effects;
    ```
  - Lineage: Authored-in-PD2 (uncommitted dev) · Pillar Impact: Online-mode Boundary · Defect Class: Trust-Boundary (ABA)
  - Current Behavior: `playerRecord(native)` looks up by raw `struct player *` in the `std::unordered_map`. If player P1 was retired and freed, and the slab allocator (or any arena) later re-hands the same address to a new `struct player` for player P2 that's inserted in the map, `hostFor(r->owner, r->hand)` returns P2's host. The subsequent `++h->hit_effects` counts P1's outstanding effect against P2's lifetime counters.
  - Why It Matters: The comment is honest that it's trading admission for observation ("a snapshot of a newer binding stays distinct from the original producer receipt" — only true for the receipt comparison, not for the ++ side-effect). The ledger harness depends on these counters being accurate (`graphLedgerConsumed` compares `row->consumes != 1 || row->debits[slot] != 1 || …`), so a successor's effects can log duplicate-detection failures across unrelated players.
  - Risk If Not Fixed: Smoke harness false-fails + telemetry noise are the current manifestation. If any production code is ever authored against these observer counters (e.g., a future throttle or anti-cheat heuristic), it inherits the ABA leak as a real security defect.
  - Recommendation: `effectObservation` and the four increment paths should take the receipt's `owner_generation` and compare against the resolved host's `owner->generation` before incrementing. Keep the snapshot path through `hostFor` (it already short-circuits `host_present` on mismatch) but never increment counters on a cross-generation host. · Cross-System: Yes (observer counters + ledger).

## 3) Code Quality Review

### Critical Issues

- **CQ-01 widened** — see PD-01A above.
- **CQ-02, CQ-03** — carryover (details above).
- **CQ-A01 (NEW) — GGV `Builder::append()` renumbers branch/jump/repeat targets by `+=offset`, but there is no cross-check that the appended source's own validator saw the composed program's longer `s.count`**
  - Severity: Critical · Confidence: Confirmed · Area: Code Quality
  - Location: `port/src/gameplay_graph_values.cpp:458-465 Builder::append`.
  - Lineage: Authored-in-PD2 · Defect Class: Layout (bytecode)
  - What We Found: `append` splices a `ggv_source` into the enclosing builder and offsets `BRANCH_FALSE`/`JUMP`/`REPEAT_WHILE` targets by the pre-splice `offset`. The individual sub-source was `static_assert(valid(...))`'d standalone, but the composed `b.s` is only validated when it's finally promoted to a stock program at the outer `static_assert(valid(controlSource))` site. If a sub-source has a `REPEAT_WHILE` with `target < pc` relative to its own origin but, post-splice, its target now falls below a nontrivially-higher `pc` such that it refers to a different sub-source's node, the composed validator should still catch it — but **the validator can only enforce reachability on the composition's final shape, not on each sub-source's intent**. A hand-authored builder sequence that happens to compile-time-validate can embed semantic drift (e.g., a jump into the middle of a sub-source's prologue) that no `static_assert` catches.
  - Why It Matters: Stock programs are built via a chain of `Builder::append()` / `b.jump()` / `b.branch()`. The whole correctness story depends on hand-authored indexes agreeing after splicing. If a future developer edits one sub-source and the offset in a `b.end(p)` doesn't shift accordingly, the only guard is the composite's `valid()` — which checks reachability but not intent.
  - Recommendation: Each sub-source should carry declared "entry" and "exit" labels; `Builder::append` should return a mapping or opaque handle, not a raw count-based offset. Add a sanity test that round-trips every stock program through `valid()` on reload (prepare + execute a smoke input) to catch any construction-time regression that the compile-time assertion missed. · Cross-System: No (interpreter-local).

- **CQ-04 through CQ-10** — all carryover from 2026-10-16 (snapshot padding memcmp, unordered_map iteration, compiler-version in hash, glTF 2 GiB admission, glTF scene node count, soundnumhack bitfield, BG header raw-word reads).

  - Location: `port/src/gameplay_graph_values.cpp:3201`.
