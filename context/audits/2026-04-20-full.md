### HIGH — 4 new findings

#### AUDIT-H1: CLC_ADMIN_AUTH has no per-peer brute-force rate limit

- **Location:** `port/src/net/netmsg.c:6943-6983` (ADMIN_SUB_AUTH dispatch
  path, pre-`is_admin` gate).
- **Evidence:** An unauthenticated peer can send `CLC_ADMIN` with
  subcode = `ADMIN_SUB_AUTH` repeatedly. Each attempt calls
  `serverAdminVerifyToken(token)` and logs `LOG_WARNING` on failure.
  No counter, no backoff, no disconnect-on-N-failures logic.
  The companion room-mutation limiter (`netmsgRoomRateAllow` at
  `netmsg.c:103-115`) exists for CREATE/JOIN/LEAVE but is **not**
  applied to CLC_ADMIN.
- **Impact:** Online brute-force of the admin token is bounded only by
  network RTT. With an 8-char token (current minimum, `server_admin.c:54`),
  a lowercase-alpha token is ~38 bits — ~hours on a gigabit LAN. An
  8-char mixed-case + digits + symbols token is ~52 bits — still feasible
  with a motivated attacker and weak password. The constant-time compare
  protects against timing, not against online volume.
- **Secondary impact:** Every failed attempt writes `LOG_WARNING` →
  log-flood amplifier (fills disk, harms observability).
- **Fix:** add `s_AdminAuthRate[NET_MAX_CLIENTS+1]` in `netmsg.c`
  modeled on `s_ChatRate` / `s_RoomMutationLast`. Drop CLC_ADMIN after
  3 failed auth attempts within 60 s, return `ADMIN_RESP_RATE_LIMIT`
  on subsequent attempts, and disconnect with
  `DISCONNECT_BANNED` after N=8 failures. Couple with a per-IP check so
  the peer cannot simply reconnect.
- **Effort:** 2–3 hours.

#### AUDIT-H2: `netServerIssueCookie` entropy source is not CSPRNG

- **Location:** `port/src/net/net.c:1301-1336`.
- **Evidence:** The header comment explicitly says *"Not a full CSPRNG —
  mixes SDL_GetPerformanceCounter with a persistent running hash seeded
  from time() and mixed with a secret that rotates on each call."*
  Per-call salt is `SDL_GetPerformanceCounter()` (monotonic, observable
  from any peer with a similar hardware clock) XORed with `time(NULL)`
  (one-second granularity, well-known). The persistent seed mixes in a
  function address (`&netServerIssueCookie`) — one value per process.
- **Impact:** An attacker who (a) joins the server or (b) scripts another
  dedicated server running against the same ENet peer gets very good
  upper/lower bounds on `SDL_GetPerformanceCounter` from their own hardware
  plus the observed `g_NetTick`. Cookie space is therefore **not** 128
  bits of entropy — closer to 40–60 bits after accounting for known time
  windows. Still materially better than the prior name-only reconnect,
  but below standard for an identity token meant to block session
  hijacking.
- **Fix:** call `BCryptGenRandom(NULL, out, 16, BCRYPT_USE_SYSTEM_PREFERRED_RNG)`
  on Windows (or `getrandom(out, 16, 0)` on Linux) once per cookie.
  Alternatively, seed the rolling digest with a one-time 32-byte
  `BCryptGenRandom` at server boot and keep the existing rolling-hash
  design — that also closes the gap.
- **Effort:** 30 minutes – 1 hour.

#### AUDIT-H3: `server_bans.c` save path is not atomic on Windows

- **Location:** `port/src/server_bans.c:156-167`.
- **Evidence:**
  ```c
  fclose(f);
  remove(finalPath);
  if (rename(tmpPath, finalPath) != 0) { … }
  ```
  On Windows, `rename()` fails if the destination exists — hence the
  preceding `remove()`. There is **no** `fflush` + `fsync` on the temp
  file before rename.
- **Impact:**
  1. Between `remove()` and `rename()`, `$S/bans.ini` does not exist. A
     concurrent reader (admin tool, log tailer) sees "no ban list."
  2. If the process crashes between remove+rename, the entire ban list is
     lost — the comment notes "we lose one ban at worst" but the crash
     window includes the remove(), so the truth is "lose the whole list
     at worst."
  3. Temp file is not fsynced before rename; a power loss between
     `fclose(f)` and `rename()` leaves a partially-written temp and
     missing final.
- **Fix:** use `MoveFileExA(tmpPath, finalPath, MOVEFILE_REPLACE_EXISTING
  | MOVEFILE_WRITE_THROUGH)` on Windows — atomic replace on the same
  volume. On POSIX, keep `rename()` (already atomic when target exists on
  same filesystem). Add `fflush(f); _commit(_fileno(f));` (Windows)
  before `fclose` for durability.
- **Effort:** 1 hour.

#### AUDIT-H4: `banAddrEq` does not canonicalize IPv6 addresses

- **Location:** `port/src/server_bans.c:30-38`.
- **Evidence:** Case-insensitive byte-by-byte string compare. No
  canonicalization to a numeric form. No handling of `::`-elision
  equivalence classes.
- **Impact:** The following all encode the same IPv6 address but
  **do not compare equal** under `banAddrEq`:
  - `::1` vs `0:0:0:0:0:0:0:1`
  - `::1` vs `::0001`
  - `2001:db8::1` vs `2001:0db8:0000:0000:0000:0000:0000:0001`
  - `1.2.3.4` vs `::ffff:1.2.3.4` (IPv4-mapped IPv6)
  Attacker banned as one form can reconnect through a proxy that formats
  the address the other way.
- **Fix:** canonicalize both sides through `inet_pton(AF_INET6,
  addr, &in6)` → `inet_ntop(AF_INET6, &in6, buf, sizeof(buf))` before
  storing / comparing, or compare `in6_addr` bytes directly. Fall back
  to string compare only if `inet_pton` fails (malformed IPv4 string).
- **Secondary:** also normalize the incoming address from ENet via
  `enet_address_get_host_ip` — confirm it emits a canonical form.
- **Effort:** 2–4 hours.

### MEDIUM — 4 new findings

#### AUDIT-M1: Admin token 8-char minimum is too low given no rate limit

- **Location:** `server_admin.c:54`.
- **Impact:** 8 chars × lowercase alphanumeric ≈ 41 bits. Couple with
  AUDIT-H1 (no rate limit) and an 8-char token is brute-forceable online
  in hours. Historical recommendation is ≥ 12 characters with
  mixed-case + symbols, or a token with ≥ 80 bits of entropy.
- **Fix:** bump minimum to 16 characters. Log a loud warning at server
  boot if the token has character-class entropy below ~50 bits.
- **Effort:** 15 minutes.

#### AUDIT-M2: `ADMIN_SUB_STATUS` and `LIST` replies silently truncate at `ADMIN_PAYLOAD_MAX`

- **Location:** `netmsg.c:7094-7135` (handlers write into a fixed-size
  `ADMIN_PAYLOAD_MAX` buffer).
- **Evidence:** The handlers use `snprintf(payload+off, sizeof(payload)-off, …)`
  but do not set a continuation flag when truncation occurs. `STATUS`
  loop breaks out on `off >= sizeof(payload) - 64`, drops the remaining
  clients silently.
- **Impact:** A 256-entry ban list at 80 chars per line = ~20 KB; silently
  truncated to ~25 entries. Admin may believe the ban they searched for
  is absent when it is simply off-the-end.
- **Fix:** split into multiple SVC_ADMIN replies with a `has_more` flag,
  or document the cap and return an explicit "…(truncated at N lines)"
  footer.
- **Effort:** 1–2 hours.

#### AUDIT-M3: Static `s_Ctx` and `s_Seeded` in `netServerIssueCookie` are not thread-safe

- **Location:** `net.c:1308-1310`.
- **Impact:** Currently not a live bug (ENet service loop is
  single-threaded). If the server ever moves to a threaded accept loop
  or a worker pool for RCON, two concurrent cookie issues would race on
  `s_Seeded` (double-seed) or `s_Ctx` (interleaved SHA-256 updates,
  producing colliding digests).
- **Fix:** either add a mutex around cookie issue, or document the
  single-threaded invariant in a comment block + `_Static_assert` (if
  feasible) on the invocation context.
- **Effort:** 15 minutes (comment); 1 hour (mutex).

#### AUDIT-M4: `H-3` u64 active-mask wire format has no compile-time tripwire

- **Location:** `src/game/mplayer/participant.c:364-399`, consumed by
  `netmsg.c:1236`.
- **Evidence:** `mpParticipantsEncodeActiveMask` loops `i < 64`. Decoder
  assumes `MAX_PLAYERS` player slots followed by `MAX_BOTS` bot slots,
  packed into slots [0..MAX_PLAYERS+MAX_BOTS-1]. Currently
  MAX_PLAYERS + MAX_BOTS = 8 + 32 = 40 — safely < 64.
- **Impact:** Not currently exploitable. But if MAX_BOTS is raised past
  56 (or MAX_PLAYERS past 32), participants in slots 64+ silently drop
  off the wire with no compile error and no runtime log.
- **Fix:** add to `participant.c` or `pdgui_constants_check.c`:
  ```c
  _Static_assert(MAX_PLAYERS + MAX_BOTS <= 64,
                 "participant active-mask wire format caps at 64 slots");
  ```
- **Effort:** 5 minutes.

### LOW — 5 new findings

#### AUDIT-L1: `CLC_ADMIN` handler does not audit-log token length on failure

- **Location:** `netmsg.c:6972-6977`. Log records client id + name, not
  the length or character-class of the failed token, so forensic review
  cannot tell "one weak token" from "exhaustive brute-force."
- **Fix:** log `strlen(token)` and whether the token had mixed case /
  symbols (bucketed, not the actual characters). 15 min.

#### AUDIT-L2: Hold-vs-tap ACTION_USE discrimination adds 250 ms latency to every reload

- **Location:** `port/include/actionmap.h` `ACTION_HOLD_THRESHOLD_MS`,
  synthesis in `src/game/bondmove.c`.
- **Impact:** Every tap-to-reload blocks for 250 ms to discriminate against
  a potential hold-to-interact. Noticeable in combat, especially for
  gamepad users accustomed to pre-hold behaviour. UX polish issue, not a
  correctness bug.
- **Fix:** snap reload synthesis on release if total hold time was below
  threshold (removes the 250 ms wait for the common case); or expose the
  threshold as a config. 30 min – 1 h.

#### AUDIT-L3: `server_admin.c` scrubs argv token but not the `chosen` local on error paths

- **Location:** `server_admin.c:33-62`.
- **Evidence:** the init path hashes `chosen` and scrubs the plaintext via
  a helper (per S393 log). On the early-return paths (no token configured,
  token < 8 chars), the `chosen` local holds the rejected plaintext until
  the stack frame is overwritten.
- **Impact:** a server crash-dump taken shortly after a failed boot could
  contain the intended-but-too-short admin token in cleartext. Low — only
  matters in a crash-report-upload flow that does not currently exist.
- **Fix:** `memset(chosen_buf, 0, sizeof(chosen_buf))` after the length
  check, regardless of outcome. 10 minutes.

#### AUDIT-L4: Low `static_assert` / `offsetof` coverage on serialized struct layouts

- **Scope:** project-wide. Grep for `static_assert|_Static_assert|offsetof`
  across `port/` returns 56 occurrences — most of them inside vendored
  ImGui. `pdgui_constants_check.c` (S392) is the only project-side
  consumer. No `_Static_assert` tripwires exist on `struct gset`,
  `struct mpchrconfig`, `struct netpreservedplayer`, or the SVC/CLC
  message payload structs.
- **Impact:** cross-cutting concern **X-6** from the 2026-04-19 master
  audit. The gset fix (LAYOUT-1) removed one instance of memcpy-on-wire
  but did not add a structural-layout tripwire. If the struct is reordered
  or a field added, the new field is silently serialized from padding or
  from the wrong offset.
- **Fix:** add an `_Static_assert` line next to every wire-format writer
  asserting `sizeof(struct gset) == expected` and `offsetof(…) == …` for
  each field. Do the same for `netpreservedplayer`, the savefile structs,
  etc.
- **Effort:** 1–2 hours for the top 10 serialized structs.

#### AUDIT-L5: `CLC_ADMIN` `BAN` extracts address via string parsing of `netFormatClientAddr`

- **Location:** `netmsg.c:7031-7059`.
- **Evidence:** The handler takes the `"ip:port"` string form returned
  by `netFormatClientAddr`, then walks `strrchr(':')` and looks for `[`
  brackets to recover the IPv6 form.  It is correct today but fragile:
  future changes to `netFormatClientAddr` can silently break ban
  storage format.
- **Fix:** either have `netFormatClientAddr` return a dedicated
  host-only string variant, or pull the `ENetAddress` directly off
  `tgt->peer->address` and `inet_ntop` it. 30 minutes.
