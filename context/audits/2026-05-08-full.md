## 1) Inferred Project Goal & Intended Outcomes

### Inferred Purpose
Perfect Dark 2 is a community fork of `fgsfdsfgs/perfect_dark` (`port-net` branch) re-engineered into a modding-first, P2P-multiplayer, social-Grid-aware game. Current shipping target (S486 constraint, 2026-04-27): **listen-host online connectivity inside the game client**, with the dedicated server (`pd-server`) deferred to a tooling/regression role. Catalog is the single source of truth for asset identity. Modding is `.pdmod` archive-based with SHA-256-pinned distribution (v46). The Grid (`port/src/forge/`) is both editor and discovery layer.

The primary architectural arc since 2026-05-01 is the **Catalog Universality Pivot** (Steps 4-5) plus its sibling **Engine Startup Acceleration** arc (Phases 1-5). The Universality Pivot retired the legacy aggregate `.pdbase` archive tier and replaced it with per-asset `.pd<ext>` files emitted from runtime authoring tables (`port/src/*data_authored.c`), then registered into the catalog through a universal directory walker. The startup acceleration arc parallelized verify, walker scan, and per-asset emit phases via a new `bootPoolForRangeBlocking` fan-out helper.

### Likely Player & Contributor Types
- PD/GoldenEye veterans expecting authentic feel with modern features.
- Modders authoring `.pdmod` archives (Maps, Weapons, UI Chrome, Skins, Audio).
- Community hosts running listen-mode servers.
- Speedrunners/challenge-runners using the Grid for repeatable encounters.
- Future: dedicated-server operators (track deferred per S486).

### Core Workflows / Gameplay Loops (Inferred)
1. **First-launch BYOR (Bring Your Own ROM)**: client extracts ROM to `data/<romid>/files/`, walks catalog, runs 13 per-asset emitters (`romextract_pd*.c`) to populate `data/<romid>/<kind>/*.pd<ext>` directories, walker registers them into the catalog row layer, loader pool finalizes the typed payload, game proceeds to title.
2. Single local player launches client -> selects mode (Solo / MP / Grid / Swarm-test) -> mission flow.
3. Listen-host: P2P 6-tier NAT traversal -> ENet auth handshake -> manifest exchange -> match start.
4. Mod author: `.pdmod` archive built locally -> server distributes via PDCA archive over `SVC_DISTRIB_*` -> client receives, SHA-256 verified, decompressed, hot-registered in catalog.
5. Grid (Forge): freefly editor places objects from catalog -> instantiates as live props/bots/spawn-pads on FREEFLY->NORMAL transition -> playable session.

## 2) Design Intent & Gameplay / Multiplayer Fit Review

### System & Workflow Validation Findings

#### Critical Issues

##### D-1) `bootPoolForRangeBlocking` deadlocks if any sub-task enqueue is dropped by queue overflow
- Severity: Critical (deadlock-on-overflow)
- Confidence: Confirmed
- Location: [port/src/boot_pool.c:341-360](../../port/src/boot_pool.c) (range fan-out), [port/src/boot_pool.c:232-252](../../port/src/boot_pool.c) (`bootPoolEnqueue` drop path)
- Lineage: Authored-in-PD2 (Engine Phase 4, 2026-05-03)
- Pillar Impact: None directly; affects boot reliability
- Defect Class: Trust-Boundary (between caller and pool)
- Intended Outcome: Manager dispatches `(worker_count - 1)` parallel workers + 1 inline manager run; each decrements `workers_remaining` once, manager waits on `cv_done` until all reach 0.
- Current Behavior (from code evidence): `b.workers_remaining = worker_count` is initialized BEFORE the enqueue loop. If `bootPoolEnqueue` rejects a job (queue at `BOOT_POOL_QUEUE_CAP=256`), it logs `LOG_ERROR` and silently returns without enqueueing. The manager still expects `worker_count` decrements but only receives `(actually_enqueued + 1)`. The wait at line 358 spins forever.
- Gap / Failure Mode: Today's exposure is bounded -- the boot orchestrator runs one `bootPoolForRangeBlocking` at a time, max `worker_count = 16`, so only 15 enqueues per call against a 256-slot queue. But: (a) any future caller that nests a fan-out inside a worker thread can fill the queue. (b) any future code path that enqueues to the boot pool concurrently with the orchestrator (currently none, but the API doesn't forbid it) can race the cap. (c) the failure mode is total -- the manager's wait never wakes, the boot worker thread is stuck, the user sees the boot overlay frozen at the active phase indefinitely.
- Why It Matters: This is a silent, total-stall bug class. The `LOG_ERROR` from `bootPoolEnqueue` is the only signal, and it fires *before* the deadlock manifests; once stuck, no further log is emitted.
- Risk If Not Fixed: First future caller that triggers nested fan-out (e.g. an emitter that itself fans out work) hits a frozen boot.
- Recommendation: Initialize `b.workers_remaining = 1` (for the inline manager), then increment by 1 for **each successful** enqueue. Either change `bootPoolEnqueue` to return success/failure, or have the helper count down explicitly with a thread-safe counter and only increment `workers_remaining` on confirmed enqueue. Add a static test that fills the queue and asserts `bootPoolForRangeBlocking` does not deadlock.
- Cross-System Changes Required: No (single file).
- Blocks Intended Outcome?: No today; partially in any nested-fan-out future.

#### High Priority Findings

##### D-2) Catalog read APIs return pointers post-unlock; concurrent register can dangle the result
- Severity: High (deferred-deref footgun)
- Confidence: Confirmed
- Location: [port/src/assetcatalog.c:438-448](../../port/src/assetcatalog.c) (`assetCatalogGetByIndex`), [port/src/assetcatalog.c:767-773](../../port/src/assetcatalog.c) (`assetCatalogResolve`), [port/src/assetcatalog.c:775-793](../../port/src/assetcatalog.c) (`assetCatalogGetMutable`), [port/src/assetcatalog.c:825-838](../../port/src/assetcatalog.c) (`assetCatalogResolveByNetHash`)
- Lineage: Authored-in-PD2 (catalog core; Engine Phase 4 added the lock around an existing pointer-returning API)
- Pillar Impact: Catalog SOT
- Defect Class: Layout (concurrent realloc invalidates returned pointer)
- Intended Outcome: Public catalog read APIs return a stable pointer that the caller can deref while no concurrent writer is active.
- Current Behavior (from code evidence): All four APIs lock, look up the pointer, **unlock, then return the pointer**. The pointer aliases into `s_EntryPool`, which `growEntryPool` realloc's at line 251. A concurrent walker thread calling `assetCatalogRegister*` can trigger `growEntryPool` between the public API's unlock and the caller's deref -- the pointer becomes dangling.
- Gap / Failure Mode: Today's walker callbacks ([port/src/loader_walker_anim.c:44](../../port/src/loader_walker_anim.c), [port/src/loader_walker_weapon.c:34,41](../../port/src/loader_walker_weapon.c), [port/src/loader_walker_head.c:30,33](../../port/src/loader_walker_head.c), [port/src/loader_walker_body.c:35,42](../../port/src/loader_walker_body.c), [port/src/loader_walker_arena.c:33,37](../../port/src/loader_walker_arena.c)) take the resolve result and only NULL-check it -- they do not deref the entry. So today the bug is dormant. But the cast-strip-const idiom (`(asset_entry_t *)assetCatalogResolve(id)`) makes the API look mutable; a future contributor adding `e->ext.head.headnum = X` would hit a heisenbug that only fires when realloc happens to land mid-resolve. The only walker that would currently deref a previously-resolved pointer (`loader_walker_anim.c`) explicitly notes the hazard at line 53-56 and uses `assetCatalogSetCategoryById` to re-resolve under-lock.
- Why It Matters: The catalog mutex was added in Phase 4 to make registration safe under concurrent walker fan-out. The corresponding read-side discipline is *not* documented at the function signature. The comment at [port/src/assetcatalog.c:74-77](../../port/src/assetcatalog.c) says "leaf mutators... do NOT lock: their caller is already inside a locked section or holds a stable pointer" -- but "stable" is undefined under concurrent registers.
- Risk If Not Fixed: Heisenbug class. Future walker callback that derefs the returned pointer occasionally crashes or corrupts an entry. The bug surfaces under load (when growth threshold is hit during fan-out) and is hard to reproduce.
- Recommendation: (a) For the read APIs: hold the lock through the deref, returning by value (a copy of `asset_entry_t`) instead of by pointer. The struct is ~600 bytes; this is acceptable given the lookup frequency. (b) Alternatively: provide a callback-based read API (`assetCatalogWithEntry(id, fn, ctx)`) that runs the callback under-lock. (c) Add a function-signature comment block on every pointer-returning API stating the dangle hazard. (d) Add a static test that pins the rule: walker callbacks must not deref a previously-resolved pointer after a register call.
- Cross-System Changes Required: Yes (every public read API + every walker callback that uses one).
- Blocks Intended Outcome?: No today; latent.

##### D-3) Boot.WorkerThreads pd.ini accepts [0..32] but pool caps at 16 silently
- Severity: High (UX-trust failure on a developer-facing config)
- Confidence: Confirmed
- Location: [port/src/boot_pool.c:146](../../port/src/boot_pool.c) (`configRegisterInt("Boot.WorkerThreads", &s_CfgWorkerOverride, 0, 32)`), [port/src/boot_pool.c:34](../../port/src/boot_pool.c) (`BOOT_POOL_WORKER_CAP 16`), [port/src/boot_pool.c:167-169](../../port/src/boot_pool.c) (silent clamp)
- Lineage: Authored-in-PD2 (Engine Phase 2)
- Pillar Impact: Build/Dev Tooling
- Defect Class: None (configuration mismatch)
- Intended Outcome: User can override worker count via pd.ini; range and behavior match.
- Current Behavior (from code evidence): `configRegisterInt` allows values 0..32 to be persisted in pd.ini. `bootPoolInit` reads the value, then silently clamps to `BOOT_POOL_WORKER_CAP = 16`. Mike sets `Boot.WorkerThreads=24`, sees that value persist in pd.ini after every save, but actually gets 16 workers.
- Gap / Failure Mode: When telemetry shows fewer workers than expected, troubleshooting hits the "I set 24, why am I seeing 16?" wall. The `BOOT_POOL: spawned N workers` log line at line 185 reveals the truth, but only on inspection.
- Why It Matters: pd.ini ranges are user-facing contracts. A range that allows values that silently get clamped is a reliability footgun.
- Risk If Not Fixed: Future tuning sessions waste time on a config that doesn't take effect. Confused bug reports.
- Recommendation: Either bump `BOOT_POOL_WORKER_CAP` to 32 (the queue is 256 slots, easily handles 32 workers), or set the `configRegisterInt` upper bound to `BOOT_POOL_WORKER_CAP`. Match them.
- Cross-System Changes Required: No.
- Blocks Intended Outcome?: No.

#### Medium Priority Findings

##### D-4) `assetCatalogGetPoolSize` reads `s_EntryPoolSize` without the catalog mutex
- Severity: Medium
- Confidence: Confirmed
- Location: [port/src/assetcatalog.c:450-453](../../port/src/assetcatalog.c)
- Lineage: Authored-in-PD2 (catalog core; Phase 4 added the mutex but missed this accessor)
- Pillar Impact: Catalog SOT
- Defect Class: Layout (atomicity claim relies on platform)
- What We Found: Reads `s_EntryPoolSize` directly. Concurrent `s_registerLocked` mutates the same field at line 491 + 498. The read is not technically atomic per C11 (UB on tearing in theory), though x86_64 makes a 32-bit aligned read atomic in practice.
- Why It Matters: Adding a missing lock here is trivial and makes the contract explicit. Right now it's an "atomic enough" claim that's not documented.
- Recommendation: Wrap with `CATALOG_LOCK()` for consistency, or document the unlock'd read in the function comment as acceptable per platform invariants.

##### D-5) `getLoadFactor` is O(N) inside the catalog mutex on every register
- Severity: Medium
- Confidence: Confirmed
- Location: [port/src/assetcatalog.c:271-285](../../port/src/assetcatalog.c) (called from `s_registerLocked` line 506)
- Lineage: Authored-in-PD2 (catalog core)
- Pillar Impact: Build/Dev Tooling (boot perf)
- Defect Class: None (perf footgun)
- What We Found: `getLoadFactor` linear-scans the hash table (initial size 2048, grows to ~4-8K with full catalog). It's called inside `s_registerLocked` for every register, holding the catalog mutex throughout. With Phase 4 fan-out, walker workers serialize on this scan. Approximate cost: ~3500 catalog entries * ~4096 slot-scans = ~14M iterations during boot, all under the mutex.
- Why It Matters: Currently submillisecond per call -- not a perf showstopper. But the lock-held duration is an order of magnitude longer than the actual register work, defeating much of the parallelism benefit. Also a perf cliff: when entry count grows (more mods, more meshes), the cost scales O(N²).
- Recommendation: Maintain a running `s_OccupiedCount` counter, incremented in `s_registerLocked` when allocating a new pool slot and during rehash, decremented in `assetCatalogClearMods` for the entries that drop. `getLoadFactor()` becomes O(1).

##### D-6) Walker callbacks all use the cast-strip-const pattern; comment-only protection
- Severity: Medium
- Confidence: Confirmed
- Location: [port/src/loader_walker_weapon.c:41](../../port/src/loader_walker_weapon.c), [port/src/loader_walker_head.c:33](../../port/src/loader_walker_head.c), [port/src/loader_walker_body.c:42](../../port/src/loader_walker_body.c), [port/src/loader_walker_arena.c:37](../../port/src/loader_walker_arena.c), [port/src/loader_walker_anim.c:44](../../port/src/loader_walker_anim.c)
- Lineage: Authored-in-PD2 (Step 5)
- Pillar Impact: Catalog SOT
- Defect Class: None (idiom hazard)
- What We Found: `e = (asset_entry_t *)assetCatalogResolve(id)` strip-casts the const-correctness signal. Today the callbacks don't deref `e` (only NULL-check), but the API LOOKS like a mutable handle. The single anim callback that needs to mutate the entry uses `assetCatalogSetCategoryById` (re-resolves under-lock) but the others don't have that pattern documented, so a future contributor adding "fix up the entry's X field" would naturally write `e->ext.X = Y` and trip D-2.
- Recommendation: Either rename the public read APIs to return `asset_entry_t *` (no const) explicitly, or migrate all five walker callbacks to call `assetCatalogResolve` and store the result in `const asset_entry_t *` and only NULL-check; make the mutator path go through typed helpers (`assetCatalogSetX(id, ...)`) that re-resolve under-lock. Add a grep-guard test for `(asset_entry_t *)assetCatalogResolve` in the loader_walker_*.c subtree.

##### D-7) Kanban dev tool: localhost HTTP server with `Access-Control-Allow-Origin: *` and no auth
- Severity: Medium (dev-only tool, but real CSRF surface)
- Confidence: Confirmed
- Location: [tools/kanban/server.py:35](../../tools/kanban/server.py) (`Access-Control-Allow-Origin: *`), [tools/kanban/server.py:127](../../tools/kanban/server.py) (`HTTPServer(("localhost", PORT), ...)`)
- Lineage: Authored-in-PD2 (added 2026-05-03)
- Pillar Impact: None (tool)
- Defect Class: Trust-Boundary
- What We Found: The kanban dev server binds to `localhost:7531` (good -- not exposed off-machine), serves `state.json` read/write/PATCH, and sets `Access-Control-Allow-Origin: *`. Any browser tab the user opens can issue cross-origin GET/POST/PATCH against `http://localhost:7531/api/state`. A malicious page Mike visits while the dev server is running can read or corrupt `tools/kanban/state.json` (project task tracking, possibly internal references the user doesn't want to leak).
- Why It Matters: This is the canonical CSRF / DNS-rebind attack surface. The wildcard CORS turns the localhost-only network bind from "safe by default" into "any tab can hit it." The tool is not in `release.ps1` (not shipped), so the impact is local to whoever runs the kanban server, but that's Mike's daily-driver machine.
- Risk If Not Fixed: Browser-tab exfil/corrupt of project task state on Mike's dev machine. Realistic threat model: low (Mike's browsing habits + the dev tool only runs while opened) but nonzero.
- Recommendation: Drop the `*` wildcard; either omit CORS entirely (same-origin only -- which is what `localhost:7531/index.html` is), or echo back `http://localhost:7531` from the `Origin` header only when it matches. Optionally add a SameSite-Strict cookie or simple bearer token in the URL for PATCH/POST. None of these are bulletproof CSRF defenses; the cleanest fix is no CORS header on a localhost-only tool.

- Area: Code Quality
- Location: [port/src/boot_progress.c:81-104](../../port/src/boot_progress.c) (decl), [port/src/boot_progress.c:170-173](../../port/src/boot_progress.c) (read inside `s_computeOverall_locked` -- correctly under lock), [port/src/boot_progress.c:343-350](../../port/src/boot_progress.c) (mutation inside `bootProgressMarkComplete` under lock), [port/src/boot_progress.c:154-158](../../port/src/boot_progress.c) (`configRegisterFloat` registers a pointer to `s_PhaseWeights[i]` -- the config layer reads/writes this pointer at configLoad/configSave time without the mutex)
- Lineage: Authored-in-PD2 (Engine Phase 5)
- Pillar Impact: None
- Defect Class: Layout (race between boot mutex and config layer)
- What We Found: `s_PhaseWeights[]` is a 22-float array. It's:
  - Read inside `s_computeOverall_locked` under the boot mutex.
  - Mutated in `bootProgressMarkComplete` under the boot mutex.
  - Pointed-to by `configRegisterFloat` so that configLoad and configSave both read AND write the cells **without** acquiring the boot mutex.
  
  configLoad runs at startup (before walker fan-out, so single-threaded). configSave runs at shutdown (after the boot worker has joined, so also single-threaded in practice). So today there's no actual race -- but the contract is fragile. A future contributor that adds "save weights mid-boot" or "reload pd.ini on signal" would race.
- Why It Matters: The weights live in `static float s_PhaseWeights[BOOT_PHASE_COUNT]`; configRegisterFloat captures the address. The `configRegisterFloat` API has no notion of "this value is mutex-guarded." This is a dual-ownership pattern that's only safe because of the current call ordering.
- Risk If Not Fixed: Future config feature breaks the timing assumption.
- Recommendation: Either (a) snapshot weights to a config-owned buffer at register time and have `bootProgressMarkComplete` write to that buffer under the boot mutex (configSave reads the snapshot, no race), OR (b) document the timing contract in the s_PhaseWeights declaration and add an ASSERT(!boot_active) to configSave.

##### Q-3) `s_animNameForCmds` is O(N) per anim ref in the pdwpn emitter; called per weapon per ref
- Severity: Medium-High (perf, not correctness)
- Confidence: Confirmed
- Area: Code Quality
- Location: [port/src/romextract_pdwpn.c:131-138](../../port/src/romextract_pdwpn.c) (called from anim ref emitters multiple times per weapon)
- Lineage: Authored-in-PD2 (BYOR Completion 2026-05-03)
- Pillar Impact: Build/Dev Tooling (boot perf)
- Defect Class: None (perf)
- What We Found: For each of 86 weapons, per anim slot (idle/equip/unequip/etc., ~5-10 per weapon), `s_animNameForCmds` does a linear scan of `g_AnimData[]` (110 entries). Total: 86 * ~7 * 110 = ~66K comparisons per pdwpn emitter run, all under the boot pool fan-out so N parallel workers each do their share. Not a hotspot, but unnecessarily quadratic.

##### Q-4) `loader_pool.c` mutex protects parsers but pool getter accessors are unlocked
- Severity: Medium
- Confidence: Confirmed
- Area: Code Quality
- Location: [port/src/loader_pool.c:138-146](../../port/src/loader_pool.c) (`POOL_LOCK`/`POOL_UNLOCK` macros), [port/src/loader_pool.c:166-203](../../port/src/loader_pool.c) (`loaderPoolGetWeapon`, `loaderPoolGetBotPref`, `loaderPoolGetWeaponCatalogId`, etc. -- none lock)
- Lineage: Authored-in-PD2 (Step 5)
- Pillar Impact: Catalog SOT
- Defect Class: Layout
- What We Found: The pool mutex (Engine Phase 4) wraps every `parse*` entry point. The getter accessors (`loaderPoolGetWeapon`, etc.) check `s_LoaderActive` and return a pointer into `s_Weapons[idx]`. They are not locked. During walker fan-out, parsers and getters run concurrently -- but the comment block at lines 26-29 says "Single-thread invariant: parses run on the main thread at startup before any other system can read pool data. No locking. Future multi-threaded loading would gate the pools behind an acquire/release fence on s_LoaderActive."

  This claim is now stale. Engine Phase 4 added a parser mutex specifically to allow concurrent parses. The matching reader-side discipline never landed.
- Why It Matters: Today's getters are only called *after* `loaderPoolFinalize` flips `s_LoaderActive=1`, which happens after walker workers join. So today there's no actual race -- but `s_LoaderActive` itself is read without atomicity guarantee, and the comment claims a no-locking invariant that the parser mutex contradicts.
- Recommendation: (a) Update the comment block to reflect the Phase 4 parser mutex and the walker concurrency. (b) Make `s_LoaderActive` an `SDL_atomic_t` and use `SDL_AtomicGet`/`SDL_AtomicSet` for explicit acquire/release. (c) Same for `s_HeadsLoaderActive`, `s_BodiesLoaderActive`, `s_ArenasLoaderActive`. (d) If the design assumes finalize-then-read serialization, document it as a hard invariant in `loader_pool.h`.

## 5) Cross-Cutting Risks & Architecture Concerns

- **Catalog/loader_pool concurrency model is half-documented** (D-2, Q-1, Q-4): Engine Phase 4 added catalog + pool mutexes around register paths but did not consistently update the read-side comments / atomicity discipline. The comment block at `assetcatalog.c:74-77` states an unsatisfiable invariant; the comment block at `loader_pool.c:26-29` claims a no-locking invariant that the parser mutex contradicts. -> Single coherent ADR for "catalog/pool concurrency under walker fan-out": acquire/release semantics on s_LoaderActive flags, lock-held duration for read APIs, mutator contract for `asset_entry_t *`-taking helpers.

- **Pointer-returning catalog APIs vs. realloc-on-grow** (D-2, Q-1): The fundamental design asymmetry is that registers can grow (realloc) while readers expect pointer stability. Each public read API leaks the returned pointer past the lock release. -> Either return-by-value (struct copy) or use callback-under-lock pattern. Pointer-returning APIs should be private/internal-only.

- **Boot pool fan-out queue cap mismatch** (D-1, D-3): `BOOT_POOL_QUEUE_CAP = 256`, `BOOT_POOL_WORKER_CAP = 16`, pd.ini accepts up to 32. The three numbers should be coherent: queue >> max_workers * max_nesting; pd.ini upper bound matches actual cap. -> Pick consistent values; document the relationship in a header comment.

- **BYOR authoring table isolation is comment-only** (S-4): The contract that `port/src/*data_authored.c` files are only included by their emitter is enforced by reviewer attention, not by build/test guards. Mid-flight migration residue risk applies (the 2026-05-01 cross-cutting concern). -> Add grep-guard test pin.

- **Walker manifest parser uses substring scans, not real JSON** (S-2): Tolerable today because input is self-trusted; risky as soon as user-supplied `.pd<ext>` files enter the data tree (e.g. mod pipeline expansion). -> Schedule a parser-hardening pass before any "users author .pd<ext> directly" feature ships.

- **Kanban dev tool is a localhost-bound CSRF surface** (D-7, S-3, Q-6, Q-7): Wildcard CORS + no auth + arbitrary PATCH key replacement. Dev-only impact, but on a machine that also handles project credentials. -> Drop wildcard CORS, cap Content-Length, whitelist PATCH fields.

- **Catalog Universality writer-side complete; reader-side still has Layer A residue**: per the 2026-05-01 audit's Top Catalog/Mod-parity Breakages, the deprecated integer asset siblings on `netplayermove`/`netrecentserver` and the hardcoded INI whitelist for wire-distrib still exist. Step 5 closed the writer surface; the wire/save reader surface is the next migration. -> Schedule a v47 wire bump for the deprecated integer field retirement.

- **Phase 2.5 N64-vs-PC stride defect class is live** (B-323): `MAX_BOTS=32` propagated through PC `sizeof(struct mpconfig)`/`sizeof(struct mpstrings)`. Pass C heap-isolated segments turned a previously-hidden over-read into a hard AV. Audit scope covered `dmaExec` / `SegmentRom*` / `MAX_BOTS` for similar patterns -- none other found in current code. -> Add a systemic-bugs.md SP entry documenting the pattern, and a grep-guard for `confignum * sizeof(struct ...)`-style segment offsets.
