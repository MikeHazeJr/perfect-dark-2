## 1. Inferred Goal

Land a coherent foundation for **The Grid** (unified Forge + Playtest facility): a Main Menu submenu that picks an arena from the catalog, configures a base scenario + variant, applies them to `g_MatchConfig`, and hands off to a Forge session that can be toggled in-place to Playtest via a Halo-style Back-button binding. Add bot lifecycle controls (spawn / remove / freeze) to the Playtest HUD, integrate with the existing F6 freeze machinery via `g_BotUpdatesDisabled`, and gate the new server build dependency `assetcatalog_api.c` so its client-only RNG path does not leak into `pd-server`.

Adjacent work: P5 attempted to fix B-228 (SP stages crashing as MP arenas through the lift / escalator-step transport gate) by inserting an `mptransport_diffflag` mask in `src/game/setup.c`. P8 then re-audited and concluded the fix is structurally in the wrong loader — keeping B-228 architecturally open.

### 2.4 The Grid

**Lifecycle:** P1 routes the Main Menu button to `s_MenuView == 6` instead of jumping straight into `pdguiForgeStartSession()`. Submenu state is fully local (`s_GridArenas`, `s_Grid*`). On Enter, `gridCommitEnter` resets `g_MatchConfig` via `matchConfigInit`, writes `stage_id` (string), `stagenum`, scenario, time/score limits, and three options bits, then calls `pdguiForgeStartSessionOn(stagenum)`.

**Toggle:** `ACTION_FORGE_TOGGLE` is bound on F7 (kbd) and `JBTN_BACK` (gamepad). The Back binding is shared with `ACTION_SCORECARD`. The author's inline comment (actionmap.cpp:1936-1946) acknowledges and rationalises the overlap.

**Bot HUD:** Playtest-mode HUD (`pdgui_forge_hud.cpp` NORMAL branch) renders bot status and exposes Insert / Delete / End / Home keys, sourcing state from the new `forge_bot_settings_t` and `g_BotUpdatesDisabled` mirror.

## 3. Code Quality

### Findings

#### AUDIT-24-H1 [HIGH | confirmed by independent re-grep]
**P5 (`216fd27f`) is a no-op for B-228 on the live codebase.**

- Diff inserts `mptransport_diffflag` masking logic and `OBJTYPE_LIFT` / `OBJTYPE_ESCASTEP` handling in `src/game/setup.c` (lines 1702, 1711, 1827, 1964 in current HEAD).
- `src/game/mplayer/setup.c` (the loader actually consulted when an arena loads as MP) contains **zero** matches for `OBJTYPE_LIFT`, `OBJTYPE_ESCASTEP`, `liftActivate`, or `escastep` (verified by `Grep -c` returning 0).
- B-228 reproductions occur on stages whose lifts/escasteps are loaded by the MP loader path; the SP loader's masking has no effect there.
- P8 (`052f540b`) already documents this and reopens B-228. This finding is the same defect reported from the audit perspective: **the fix that landed in P5 does not cover the failing path; B-228 remains a HIGH open bug, not a closed one**.

**Recommendation:** Move the mask logic into the MP loader path, OR (Option E from prior audits) bypass the per-arena mask entirely and load lift/escastep objects unconditionally for stages that ship them. Do not close B-228 until repro is verified on a stage that loads through `mplayer/setup.c`.

#### AUDIT-24-M1 [MEDIUM | confirmed]
**Comment-vs-code naming skew in P5.** `src/game/setup.c:1684` documents the mask variable as `mplift_diffflag`; the actual variable name (lines 1702, 1711, 1827, 1964) is `mptransport_diffflag`. The rename was correct (escasteps are not lifts) but the comment block didn't follow. Future readers searching for the documented identifier will not find it.

**Recommendation:** Single-line edit to `src/game/setup.c:1684` replacing `mplift_diffflag` with `mptransport_diffflag`.

#### AUDIT-24-M2 [MEDIUM | strong evidence, partial verification]
**Per-client RNG in `catalogPickRandomHeadIdForBody` is a desync vector if called outside a wire-broadcast post-pick.** `assetcatalog_api.c:576` calls `rngRandom() % count` with no seed coordination. Two clients independently invoking this function for the same bot slot pick different heads.

**Mitigated case:** match-setup writes the resolved `body_id` / `head_id` into `g_BotConfigsArray[slot].base.{body_id,head_id}` and the `mpchrconfig` struct is broadcast to peers — both clients then see the same head because the *result* is on the wire, not the *call*.

**Risk case:** Any future call site that picks then *uses* the head locally without a broadcast (e.g. previewing a bot in the menu, or a server-side simulant config that the server then re-picks) will desync.

**Recommendation:** Add a Doxygen-style header to `catalogPickRandomHeadIdForBody` warning callers it is *not* deterministic across clients and must be paired with a broadcast of the resolved ID. Verify the two `pdgui_menu_room.cpp` sites (around lines 2267 and 3404 per the P3 commit) feed into the wire path.

#### AUDIT-24-M3 [MEDIUM | confirmed by code read]
**`s_ValidHeadBuf[256]` is non-reentrant, not just non-thread-safe.** `assetcatalog_api.c:494` declares a module-static buffer. `catalogGetBodyValidHeadIds` returns a pointer into it (`s_ValidHeadBuf`). The author's comment dismisses concerns by citing "single-threaded by design," which addresses threads, not nested calls.

**Risk:** Any caller iterating two bodies and remembering the first list will silently observe the second body's heads. E.g. `for (i in bodies) { ids = catalogGetBodyValidHeadIds(...); cache[i] = ids; }` — every `cache[i]` ends up pointing at the same buffer, holding the last body's data.

**Recommendation:** Either (a) document the reentrancy contract on the API (return pointer is invalidated by the next call), (b) make the caller pass the output buffer + capacity, or (c) duplicate IDs into a small caller-allocated array on return.

#### AUDIT-24-M4 [MEDIUM | confirmed]
**`JBTN_BACK` is bound to both `ACTION_SCORECARD` and `ACTION_FORGE_TOGGLE` (actionmap.cpp:1934, 1948).** The acknowledgment comment is forward-looking and brittle:

> "scorecard in a solo Grid session is a no-op popup and the mode toggle is only consumed by `forgeTick` when a session is active."

Two failure modes the comment does not address:

1. **MP Grid sessions** (later phase) will have a real scorecard and a real mode toggle simultaneously active. Holding Back to view the scorecard will edge-trigger the toggle on every press *and* every release.
2. **Hold semantics:** `actionHeld(0, ACTION_SCORECARD)` polls a held state (pausemenu.cpp:867); `ACTION_FORGE_TOGGLE` consumers expect a single edge. If the toggle dispatcher uses a "press" event and the user holds Back across multiple frames, repeated edges may fire depending on the dispatch path.

**Recommendation:** Plan an explicit context-aware binding (Back → SCORECARD only outside Grid; Back → FORGE_TOGGLE only inside Grid), or move the in-Grid scorecard onto a different gamepad input in the same pass that wires it up. Track as a pre-MP-Grid blocker.

#### AUDIT-24-M5 [MEDIUM | confirmed]
**Grid submenu lives in `s_MenuView == 6`, not the menu pool.** `pdgui_menu_mainmenu.cpp` switches on a hand-rolled state-int rather than registering the submenu via the established `pdguiPushMenu` / pool dispatch. Implications:

- Input-authority handling (focus, modal stacking, ESC behaviour) does not benefit from menu-pool conventions
- Future "open Grid submenu from elsewhere" entrypoints have to learn `s_MenuView == 6` rather than push a registered dialog name
- Audit trail for menu state ownership is split (some menus pool-backed, this one not)

**Recommendation:** Track as a P1.5 polish item once the rest of the foundation lands; not blocking for the alpha cut, but should be reconciled before more submenus follow this pattern and ossify the divergence.

#### AUDIT-24-M6 [MEDIUM]
**`s_GridScenarios[]` is a parallel array to `s_BaseGameModes`.** `pdgui_menu_mainmenu.cpp:3942-3949` hardcodes the six base scenarios with a comment claiming match against `assetcatalog_base_extended.c`. Mod-authored scenarios will not appear in the Grid scenario picker without a code edit. Catalog SOT principle says this should be enumerated.

**Recommendation:** Replace the hardcoded array with an enumeration of `ASSET_GAMEMODE` (or whatever the type tag is) similar to `gridArenaCollect`. Until then, document the divergence in `context/known-issues.md` so it doesn't surprise a mod author trying to ship a new scenario.

#### AUDIT-24-L1 [LOW | confirmed]
**P7 bot HUD keybinds bypass `WantCaptureKeyboard`.** `pdgui_forge_hud.cpp:143-156` calls `ImGui::IsKeyPressed(ImGuiKey_{Insert,Delete,End,Home}, false)` without consulting `ImGui::GetIO().WantCaptureKeyboard`. The author's comment says these keys "are normally unbound during combat."

Mitigations present:
- Line 89: `if (pdguiIsActive()) return;` early-exits when *any* menu is open — covers the common case
- The HUD only renders / fires in `state == FORGE_SESSION_NORMAL` (Playtest), and only after `forgeSessionIsActive()` — so the keys are scoped to a session

Residual gap: any non-menu ImGui widget that wants keyboard (an in-game console widget rendered alongside the HUD, or a future text-input overlay) would still see the keys consumed by both.

**Recommendation:** Add `if (ImGui::GetIO().WantCaptureKeyboard) { /* fall through to render only */ } else { /* poll keys */ }`. One-line guard, matches the B-154 fix pattern.

#### AUDIT-24-L2 [LOW]
**P3 reduces `pickHeadIdForBody` in `matchsetup.c` to a one-line wrapper but leaves a parallel name in place.** Two layers of indirection (`matchsetup.c::pickHeadIdForBody` → `assetcatalog_api.c::catalogPickRandomHeadIdForBody`). Acceptable as a transitional shim; should collapse once call sites are migrated.

#### AUDIT-24-L3 [LOW]
**`gridArenaCollect` uses `realloc` on a `static GridArenaEntry *s_GridArenas`.** No `free` is called on rebuild — the realloc owns it. `gridArenaListBuild` opens with `free(s_GridArenas); s_GridArenas = NULL;` (mainmenu.cpp:4006-4009), so the lifecycle is correct. But the buffer is never freed at process shutdown — a benign leak (the OS reclaims at exit; no per-frame growth). Note for hygiene only.

### Positives

- **`s_teleportBotNearPlayer` null-safety is comprehensive** (`forge_runtime.c:254-260`): range-checks `aibotnum`, `g_Vars.currentplayer`, `currentplayer->prop`, `g_MpBotChrPtrs[slot]`, and `bchr->prop` before dereferencing. Plus a 100..5000u radius clamp matching the HUD slider range.
- **`gridCommitEnter` validates inputs before mutating `g_MatchConfig`** (mainmenu.cpp:4044-4051): empty-arena and out-of-range guards, both with `LOG_WARNING`. Failure path leaves the user on the submenu with a logged reason.
- **Error logging consistently uses the `[CATALOG-ERROR]` / `GRID.MENU` / `GRID.RUNTIME` prefixes**, making post-mortem grep tractable.
- **Server build gating is surgical:** only `catalogPickRandomHeadIdForBody` and the `lib/rng.h` include are wrapped in `#if !defined(PD_SERVER)`; the more general `catalogGetBodyValidHeadIds` remains available to server code.

## 4. Security / Trust

### 4.1 Wire surfaces

No new client-trusted surfaces introduced this pass. Grid submenu input is local only; scenario / variant data flows through `g_MatchConfig` which is authoritative on the host and broadcast via existing `SVC_*` paths.

### 4.2 Catalog ID handling

`gridArenaCollect`, `gridCommitEnter`, and `s_fillBotSlot` all use `strncpy(..., sizeof(dst) - 1)` followed by explicit null-terminate. No `strcpy`, no buffer-arithmetic. Pass.

### 4.3 Untrusted-input paths

- **Submenu values (time / score limits, options bits, scenario index):** clamped via `(u8)(s_GridTimeLimit & 0xff)` and bounds-check `s_GridScenarioIdx < 0 || >= s_GridScenarioCount`. Pass.
- **Forge object catalog IDs feeding `s_spawnBot` / `s_spawn_door`:** funnel through `catalogResolveProp` / `assetCatalogResolve`, which returns NULL on miss and the callers `LOG_WARNING` and skip. Pass.
- **`s_findFreeBotSlot` returns -1 on full pool**, checked at `forge_runtime.c:213-219`. Pass.

### 4.4 RNG / determinism

See AUDIT-24-M2 above. The picker is pseudo-random per-client. The risk is correctness (desync), not classical security — but both clients reading different state in a P2P session is the same shape as a trust violation.

### 4.5 Server boundary

`SRC_SERVER` continues to compile without the rngRandom symbol; the gate lands cleanly. No new server-leaking pathway.

### 4.6 Threat model regressions

None observed. Listen-vs-dedicated split, ROM/mod-check skip on dedicated, connect-code IP-hiding all unchanged.

## 5. Cross-Cutting Risks

### 5.1 Phase 2.5 — Upstream-shape pattern scan

No new fixed-count literals (`MAX_PLAYERS = 8`, etc.) introduced. `FORGE_RUNTIME_MAX_HANDLES`, `FORGE_PROP_POOL_SIZE = 64`, `FORGE_DOOR_POOL_SIZE = 16`, `FORGE_ZONE_RT_MAX = 128` are forge-scoped pool ceilings, not player counts. Acceptable.

`s_ValidHeadBuf[256]` cap on per-body head enumeration: today's catalogs are far below 256 heads/body; mod authors approaching this cap will hit the silent `ctx->count >= ctx->capacity` early-return at line 507 (no log). **Sub-finding (LOW):** add a `LOG_WARNING` at the cap so a mod author authoring a 257th head doesn't silently lose the entry.

### 5.2 Phase 2.5 — Data-layout / type-migration hazards

No struct rearrangements, no new bitfields, no new packed structs in this delta. `forge_zone_rt_t` (forge_runtime.c:88-102) uses an explicit `u8 pad[3]` aligned trailer; intentional padding is fine. No persisted-format changes.

### 5.3 Mod / native asymmetry

`gridArenaCollect` filters via `challengeIsFeatureUnlocked((u8)e->ext.arena.requirefeature)`. This is the right gate, but a mod-authored arena sets `requirefeature` itself — meaning a mod can either (a) set 0 (always available) or (b) set a feature ID the player has not unlocked, and silently disappear from the picker. Acceptable behaviour, but worth surfacing in mod-authoring docs.

### 5.4 Scaling ceilings

- Bot HUD keybinds (Insert/Delete/End/Home) are gamepad-unfriendly; only kbd users can drive Playtest's bot ops in the current shape. Will need gamepad bindings before the alpha is reachable on console-style controllers.
- Grid submenu scenario list is fixed-width 6 entries (AUDIT-24-M6).

### 5.5 Composite / interaction risks

- AUDIT-24-H1 (P5 no-op) + AUDIT-24-M4 (Back overlap) + AUDIT-24-M2 (RNG desync) all sit on paths that will get hammered when MP Grid lands. Recommend resolving M2 and M4 *before* multi-client Grid playtests; H1 is a separate SP→MP bridge bug independent of Grid.
