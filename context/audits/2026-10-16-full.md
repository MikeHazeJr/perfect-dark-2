## 1) Inferred Project Goal & Intended Outcomes

### Inferred Purpose
Perfect Dark 2 is a PC-only re-engineering of Rare's N64 Perfect Dark built on the `n64decomp` → `fgsfdsfgs` → `jonaeru/allinone` lineage, now diverged into a modding-first platform with: a Catalog-as-single-source-of-truth asset system, decentralized P2P multiplayer (ENet, 6-tier NAT path), an ImGui-only menu layer, a first-class modding pipeline (`.pdmod` transport + typed `.pdxxx` sources), a Forge level editor, a Theater record/replay system, and a listen-host-primary online model. The former standalone dedicated-server product is explicitly deprecated.

### Likely Player & Contributor Types
- Perfect Dark / GoldenEye veterans and speedrunners who want preserved feel without preserved defects.
- Mod authors using Blender/3DS Max to export standard GLTF/GLB; constraint demands that public typed archives open as source in standard DCC tools.
- LAN/friend-group multiplayer hosts; the shipping path is in-client listen hosting over connect-codes (no raw IP in UI).
- Contributors maintaining the asset catalog, extracting ROM content, and migrating native systems onto executable behavior graphs.

### Core Workflows / Gameplay Loops (Inferred)
1. Launch client → authored or extracted base content loads via the Catalog → single-player Campaign or Combat Simulator.
2. Host listen session → connect-code shared → peers join → room/lobby settings sync → playlist → match start → stage transition → scoring → endscreen → Play Again.
3. Mod author: pack public typed archives (`.pdmesh`/`.pdweapon`/etc. → `.pdmod`) → distribute → remote peers extract on join → equal-footing load through the Catalog.
4. Forge: create prefabs → place objects → save `.pdmod` → test in Combat Simulator.
5. Theater: record live match → `.pdth` on disk → (future) load/play/pause/seek.

### Upstream Lineage Observations
- **n64decomp**: `include/PR/gbi.h`, `src/lib/*`, `src/game/*` game logic (chr/prop/bondgun/setup), the pad-file layout, the audio sfxref packing, several bitfield structs over persisted ROM data.
- **fgsfdsfgs port / port-net**: SDL2 input, fast3d GBI translator, early ENet netplay (SVC_*/CLC_*), 8-player ceiling (now lifted to MAX_BOTS=32 + MAX_PLAYERS=8).
- **jonaeru/allinone**: per-arena mod-swap, legacy `g_ModNum` (removed), legacy filenum/slot addressing (now private migration debt only).
- **Authored in PD2**: Catalog SOT (`assetcatalog_*.c`), `.pdmod` + typed-archive extractors, weapon graph v2 (uncommitted expansion), Forge, Theater, ImGui menu system, connect-code mechanism, reconnect cookies (v57), stage lifecycle (v58), vehicle authority (v59), room access (v60), authenticated roster (v61).

### Pillar Observations (Catalog / Mod Parity / Modding Pipeline / Grid / Online Mode / Dedicated Server)
- **Catalog SOT**: HEALTHY. No `romProviderHandle()` / `fileProviderHandle()` / `assetprovider_internal.h` leakage outside the sanctioned shim. `src/game/modeldef.c:517` is a doc-comment, not a bypass. Manifest token many-to-one buckets have correct two-sided reverse-dispatch (no SP-45 regression). Payload-kind release switch at `assetcatalog_load.c:1995-2056` cleanly dispatches modeldef/animation/colmesh to their owners instead of blind `sysMemFree`.
- **Mod-native Parity**: MOSTLY HEALTHY. No raw `if (is_mod)` branches in loader/resolver/renderer paths. Three mild asymmetries identified (loader "assumed base" vs "MISSING" classification for unresolved rows; bot-profile tie-break preferring `base:`; `netmanifest.c` metric-only `s_entryIsMod`).
- **Modding Pipeline**: STRONG transport (`.pdmod` + PDCA network distribution with SHA-256 verification + commit/rollback) but new findings in authoring/compilation (locale-sensitive float formatting; unbounded buffer admission; node-count DoS; pointer-width GDL matcher; byte-wise snapshot `memcmp` depending on padding; compiler-version not folded into exposed source digest). GLB/GLTF admission just hardened on dev but newly rejects any REQUIRED extension — conflicts with Blender's default export.
- **Grid**: NO implementation surface found in `port/src/`. The audit prompt's "Grid" pillar is **not yet instantiated** in this codebase (Forge and Theater carry social/repeatability roles today). Treat Grid trust-boundary findings as future work, not current defects.
- **Online-mode Boundary**: HEALTHY on the vehicle/stage/cutscene streams (v56–v59 handlers are exemplary). Reconnect-inventory is non-atomic in one place (`invClear` before placement loop). SVC_PROP_DOOR accepts `clid == NET_MAX_CLIENTS` and silently aliases to `g_NetLocalClient`.
- **Dedicated-server Boundary**: Deprecated per constraints; `pd-server` target removed from routine verification. Server UI (`port/fast3d/server_gui.cpp`) correctly connect-code-encodes IP for display, which the newer NAT Diagnostics UI does NOT.

## 2) Design Intent & Gameplay / Multiplayer Fit Review

### Critical Issues

- **PD-01 — `struct packedpad` bitfield order does not match the preprocessed pad-file word**
  - Severity: Critical · Confidence: Confirmed · Area: Design Fit / Code Quality
  - Location: `src/include/types.h:323-333`; consumers `src/game/setuppads.c:230, 234, 248, 250`; producer `port/src/preprocess/filepads.c:17-29, 57-61`
  - Lineage: Inherited-from-n64decomp (bitfield union over N64 word)
  - Pillar Impact: Scaling Ceiling (indirect — wrong room routing) · Defect Class: Layout
  - Intended Outcome: Every pad's `liftnum`, `room`, and `flags` fields decode to the preprocessed stage data.
  - Current Behavior: The LE branch declares `liftnum:4; room:10; flags:18` (bits 0-3, 4-13, 14-31) while the preprocess at `filepads.c:17-29` writes `flags:18; room:10; liftnum:4` (bits 0-17, 18-27, 28-31) — bitfield order inverted relative to the actual file word. The raw-word read at `setuppads.c:257` works by accident because it does `(*(u32*)packedpad >> 14)`, bypassing the bitfield.
  - Gap: `packedpad->room` reads/writes the wrong bit slice entirely; the BE branch is also inconsistent with the preprocessed layout.
  - Why It Matters: Pad routing, portal walking, and `cdFindFloorRoomAtPos` get wrong room values for pads whose room was auto-populated.
  - Risk If Not Fixed: Latent collision/navigation defects on any stage whose pads are auto-filled; may already be papered over by other heuristics but will bite on new stages / modded arenas.
  - Recommendation: Either reorder the bitfield members to match the preprocessed word, or remove the bitfield union and switch `setuppads.c` fully to raw-mask/shift (consistent with the one working site at line 257). Add a static assertion that `sizeof(struct packedpad) == 4` plus a round-trip unit test.
  - Cross-System Changes Required: Yes (bitfield + consumers).
  - Blocks Intended Outcome: Partially.

- **PD-02 — PDCA archive format has no version field**
  - Severity: Critical · Confidence: Confirmed · Area: Design Fit
  - Location: `port/src/modpack.c:36, 220-275, 263-310`; mirrored in `port/src/net/netdistrib.c:82, 315, 553, 740, 827`
  - Lineage: Authored-in-PD2
  - Pillar Impact: Modding Pipeline · Defect Class: Layout
  - Intended Outcome: Mod packs round-trip across builds and future format changes stay forward-compatible.
  - Current Behavior: Header is `magic(4) + file_count(2)` — no version word. Inner `path_len`/`data_len` are `memcpy`'d from the stream with no explicit byte order.
  - Why It Matters: Any future header change is silently misinterpreted; the format is also non-portable to big-endian hosts (not currently targeted but documented as a project-portability concern).
  - Risk If Not Fixed: Backwards-incompat change to the mod format forces a hard flag day and a hash break on every previously-distributed `.pdmod`; cross-build mod sharing is fragile.
  - Recommendation: Add a single `u16` version word after the magic. Readers reject unknown versions; writers always emit the current version. Document as a one-time format bump.
  - Cross-System Changes Required: Yes (modpack writer, reader, netdistrib).
  - Blocks Intended Outcome: No (works today) · Partially (post-1.0 pipeline evolution).

### High Priority Findings

- **PD-03 — glTF document admission rejects any REQUIRED extension**
  - Severity: High · Confidence: Confirmed · Area: Design Fit
  - Location: `port/src/modasset_gltf_document.cpp` (new `readGltfDocument` function, in the uncommitted +85-line delta; `extensionsRequired` branch unconditionally returns false with reason `gltf_required_extension_unsupported`)
  - Lineage: Authored-in-PD2 (uncommitted dev)
  - Pillar Impact: Modding Pipeline / Mod-native Parity
  - Intended Outcome: Mod authors export public `.pdmesh` from Blender/3DS Max; the client admits standard glTF 2.0 content.
  - Current Behavior: Any extension name appearing in `extensionsRequired` causes rejection regardless of whether PD2's converter supports it (per the in-source comment "No standard extension has a complete converter implementation yet").
  - Gap: Blender's default glTF export marks `KHR_mesh_quantization` as REQUIRED whenever any mesh attribute uses an integer type (which is common for color/normal). Such exports fail admission with a terse reason string.
  - Why It Matters: Public typed archives are supposed to open and re-export cleanly in standard DCC tools; this gates a common export path.
  - Risk If Not Fixed: Mod creators see rejections they cannot easily diagnose; the authoring loop requires manual edits to the exported JSON.
  - Recommendation: Either (a) implement the handful of common REQUIRED extensions that are safe (KHR_mesh_quantization at minimum for integer attributes), or (b) soften the rejection to a diagnostic warning when the required extension is one PD2's converter can tolerate as a no-op. Document rejection reasons in `docs/modding/standard-source-authoring.md`.
  - Cross-System Changes Required: Yes (admission + converter + docs).
  - Blocks Intended Outcome: Partially.

- **PD-04 — Weapon-graph accepted path writes `shotdata.gset = *accepted` without `gsetPopulateFromCurrentPlayer`**

  - Location: `src/game/prop.c` (new `shotCalculateHitsSource`, around new lines 700-740); contrast legacy branch at new lines 744-748 which calls `gsetPopulateFromCurrentPlayer`.
  - Lineage: Authored-in-PD2 (uncommitted dev)

## 3) Code Quality Review

### Critical Issues

- **CQ-01 — Locale-sensitive float formatting in cache JSON (determinism + hash divergence)**
  - Severity: Critical · Confidence: Confirmed · Area: Code Quality
  - Location: `port/src/modasset_compiler.c:4262, 4269, 4330, 4337`
  - Lineage: Authored-in-PD2
  - Pillar Impact: Modding Pipeline (determinism) · Defect Class: Determinism
  - What We Found: `writeObjMeshJson` / `writeModelMeshJson` use `fprintf(f, "    [%.9g, %.9g, %.9g]%s\n", ...)` with the process's current `LC_NUMERIC`. On any locale that formats floats with `,` (de_DE, fr_FR, …) the cache JSON is both malformed AND different-bytes-than-C-locale. No `setlocale(LC_NUMERIC, "C")` anywhere in `port/src`.
  - Why It Matters: The modding pipeline's determinism promise ("identical inputs yield identical outputs") breaks per-locale. Any downstream cache keyed on content hash flakes.
  - Risk If Not Fixed: Mod verification hashes diverge between locales; CI/machine disagreement; cross-user cache poisoning if someone shares cache artifacts.
  - Recommendation: `setlocale(LC_NUMERIC, "C")` at `port/src` boundary (either process-wide at startup for the compiler/tool paths, or scoped around the JSON write via `uselocale` on glibc). Add a round-trip test in a non-C locale CI job.
  - Cross-System Changes Required: No.

- **CQ-02 — Pointer-width truncation in generated-GDL pixel matching**
  - Severity: Critical · Confidence: Confirmed · Area: Code Quality
  - Location: `port/src/weapon_nested_runtime_harness.c:1117, 1133, 1253-1255`
  - Lineage: Authored-in-PD2 (uncommitted dev, part of the +1020-line expansion)
  - Pillar Impact: Modding Pipeline · Defect Class: Layout
  - What We Found: `(u8)(gdl[i].words.w0 >> 24) == (u8)G_SETTIMG && gdl[i].words.w1 == (uintptr_t)pixels`. The Gfx `w1` word is `u32` (N64 lineage width), compared against a 64-bit host pointer cast via `uintptr_t`. On x86_64 any address whose bits 32+ are nonzero compares false permanently.
  - Why It Matters: `harnessModelHasTexture` and `harnessModelFirstPixels` report "no texture" even on correct GDLs; harness regression tests pass against wrong state. The same shape at 1253-1255 for tile tmem/mask extraction.
  - Risk If Not Fixed: The uncommitted smoke harness scaffolding is unreliable on 64-bit (the only target).
  - Recommendation: Store 64-bit host pointers in a side table keyed by GDL index, or encode `pixels` through the same `catalogWriteAssetRef` pattern used elsewhere. Do not compare `w1` to a host pointer.
  - Cross-System Changes Required: Yes (harness).

- **CQ-03 — Unbounded `.pdmod` member allocation (zip-bomb class)**
  - Severity: Critical · Confidence: Confirmed · Area: Security / Code Quality
  - Location: `port/src/weapon_graph_v2_runtime.cpp:243-248`
  - Lineage: Authored-in-PD2
  - Pillar Impact: Modding Pipeline (supply chain) · Defect Class: Supply-Chain
  - What We Found: `member()` calls `modArchiveExtractMemAlloc(archive, size, path, &length)` with only `!bytes || !length` as rejection. No ceiling on `length` vs. the archive container size; the result is immediately pushed into `std::string`.
  - Why It Matters: A `.pdmod` whose central-directory claims a multi-GB uncompressed length for `mesh.ini` / `descriptor.settings` drives the host to OOM before any content integrity gate runs.
  - Risk If Not Fixed: Malicious mod pack = host OOM / denial of service.
  - Recommendation: Impose a per-member decompressed cap (e.g., 32 MiB for INI/descriptor; configurable higher for geometry) and a compressed-to-decompressed ratio cap. Reject before allocation.
  - Cross-System Changes Required: Yes (weapon_graph_v2 and any other `modArchiveExtractMemAlloc` caller — audit all).

### High Priority Findings

- **CQ-04 — `wg_v2_runtime_snapshot` compared byte-wise including padding**
  - Severity: High · Confidence: Confirmed · Defect Class: Layout
  - Location: `port/src/weapon_nested_runtime_harness.c:2619, 2681, 2686, 628`; `port/src/weapon_graph_v2_runtime.cpp:114-139`
  - What We Found: Snapshot built with `memset(&out,0,sizeof(out))`, then `*out = snapshot(*h)` (field-wise C++ copy — padding bits indeterminate). Later `memcmp(&after, &before_b, sizeof(after))` asserts "no change". With mixed `uint64_t/int/float/int[2]` fields, padding bits are not guaranteed equal.
  - Risk: Logically-equal snapshots fail the harness; logically-different snapshots pass if padding happened to zero on one side.
  - Recommendation: Replace `memcmp` with explicit field-by-field comparison, or implement an operator== that ignores padding. If the harness truly needs `memcmp`, author a `memset`-before-each-write discipline on every snapshot producer.

- **CQ-05 — `std::unordered_map` iteration order affects retirement/scope accounting**
  - Severity: High · Confidence: Confirmed · Defect Class: Determinism
  - Location: `port/src/weapon_graph_v2_runtime.cpp:57-58, 120-122, 341-345`
  - What We Found: `runtime->players` is a hash map keyed on raw `struct player *`. `wgV2RuntimeRetirePlayers()` iterates; order is nondeterministic across runs, STL implementations, and host RAM layouts.
  - Risk: Log line order, retire-callback ordering, replayability — all drift. Netplay replay/determinism rule applies to deterministic constructs here.
  - Recommendation: Use `std::map<void*, …>` or a vector-of-pairs sorted by key before iteration. Only the enumeration order matters; the map's amortized cost does not.

- **CQ-06 — Compiler-version bytes absent from exposed source-closure hash**
  - Severity: High · Confidence: Confirmed · Area: Code Quality
  - Location: `port/src/modasset_compiler.c:10227-10242`
  - What We Found: `modAssetCompilerBuildAnimationClipHashed` builds `source_sha256` from `domain || source_digest || frame_count_be`. Neither `MODASSET_COMPILER_VERSION` nor `MODASSET_COMPILER_ANIMATION_VERSION` is folded in. Downstream cache (e.g., `weapon_graph_v2_runtime.cpp:309-316`) keys on this exposed digest.
  - Risk: A compiler-version bump changes native payload bytes but exposed digest stays identical → stale payload served from cache.
  - Recommendation: Include compiler version(s) in the hash input. Add a conformance test: identical source + bumped version → different hash.

- **CQ-07 — glTF document size ceiling at INT32_MAX permits 2 GiB admission**
  - Severity: High · Confidence: Confirmed · Defect Class: Supply-Chain
  - Location: `port/include/modasset_gltf_document.h:12` plus `port/src/modasset_gltf_document.cpp:221, 369`
  - What We Found: `MODASSET_GLTF_DOCUMENT_LIMIT = 2147483647u` is used both as JSON length ceiling and (via `unsignedValue`) as the buffer `byteLength` ceiling. No proportional ceiling vs. source archive size, no total RSS budget.
  - Risk: Any member authored at 2 GiB flows through `fsFileLoad` before gameplay/catalog policy runs.
  - Recommendation: Policy-driven ceiling (e.g., 128 MiB) with explicit override for authored content; reject early.

- **CQ-08 — glTF scene node storage sized to attacker-controlled count**
  - Severity: High · Confidence: Confirmed · Defect Class: Supply-Chain
  - Location: `port/src/modasset_gltf_document.cpp:548, 573, 594, 609`
  - What We Found: `std::vector<SceneNode> nodes(node_count)` where SceneNode ≈ 288 bytes; `node_count <= 2147483647u` admitted. A malicious `.pdmod` with `nodes.length = 10^7` forces ~3 GB allocation.

- **CQ-09 — `union soundnumhack` bitfield packing is compiler-defined over persisted sfxref data**
  - Severity: High · Confidence: Confirmed · Defect Class: Layout
  - Location: `src/include/types.h:3520-3546`; consumers in `src/lib/snd.c` (lines 214, 988-992, 1069-1071, 1723, 2097-2098, 2115, 2168-2172, 2255-2259, 2310, 2480-2492, 2527-2529)

  - Risk: Wrong `mp3priority`, `hasconfig`, `confignum`, `id` on any compiler that disagrees with current assumptions. Persisted (ROM audio tables + mp3 playlist state as sfxref).
  - Recommendation: Compile-time assertion for round-trip of a known value; or replace bitfield with explicit shift/mask.

- **CQ-10 — BG header raw-word reads without explicit swap confirmation**
  - Severity: High · Confidence: Probable · Defect Class: Layout

## 5) Cross-Cutting Risks & Architecture Concerns

- **CC-01 — Determinism posture is fragile.** CQ-01 (locale float), CQ-05 (unordered_map iteration), CQ-06 (compiler version not in hash) each attack the "identical inputs yield identical outputs" invariant through a different seam. Recommend one deterministic-output CI job that bakes a known mod from source and compares byte-exact SHA-256 across (a) C vs non-C locale, (b) libstdc++ vs libc++, (c) compiler-version bump. The CI should fail when any of these differ.

- **CC-02 — Bitfield pattern is a recurring defect class.** PD-01 (packedpad), CQ-09 (soundnumhack), potentially other ROM-persisted bitfield unions. Standard remediation: replace bitfield unions over persisted bytes with explicit `shift & mask` accessors; add a static assertion for byte width; add a round-trip unit test per field. Treat any new bitfield union over persisted bytes as rejected-on-review.

- **CC-03 — Pointer-width hazards in N64-lineage code are latent.** CQ-02 (Gfx w1 vs host pointer), CQ-20 (host_header 0x14/0x20), CQ-10 (BG segment pointer expansion). All reach the moment a 64-bit host meets a lineage structure sized for 32-bit. Audit `grep -n 'uintptr_t\|sizeof.*host\|0x14\|0x20' src port` for a complete inventory.

- **CC-04 — Admission policies for mod content are not uniformly bounded.** CQ-03 (`modArchiveExtractMemAlloc`), CQ-07 (glTF JSON size), CQ-08 (scene node count), CQ-17 (archive loaded twice unbounded) — each is an independent DoS vector. Factor into one shared budget module invoked at every mod-content entry point; publish ceilings in `docs/modding/`.

- **CC-05 — Menu lifecycle has grown a watchdog culture.** PD-07 is explicit; PD-19 (PushID/PopID mismatch) suggests more. Recommendation: author a lifecycle-fail CI gate that greps the latest smoke log for `INPUTCTX watchdog:`, `MENU: watchdog --`, `MENU: underflow detected` — any hit fails the gate. Treat each as a bug, not a diagnostic.

- **CC-06 — Networking has implicit single-peer trust (PD-15).** 15 explicit `srccl` checks across 14k lines means the vast majority of SVC_ handlers rely on ENet's "one peer = the server" shape. If a future topology (dedicated-plus-listen hybrid, ICE sidecar, broker relay) establishes a second peer, every unchecked handler becomes a trust-boundary violation. Author an architectural ADR: either enforce `srccl == g_NetLocalClient` universally and generate the check via macro, or move to an explicit trust-token field in every SVC_ wire frame.

- **CC-07 — Grid pillar is architectural scaffolding only.** The audit prompt lists Grid as a first-class pillar; the codebase has no implementation. Either (a) excise Grid from the audit prompt until an actual module exists, or (b) stand up a stub module so future reviews have a target. Current state produces noise in audits that should be focused.
