#### High Priority Findings

- **NET-AUTOSTART-NO-TIMEOUT — `--host-autostart` settle phase has no
  timeout**
  - Severity: High
  - Confidence: Probable
  - Location: `port/src/main.c:2902-3050` (`bootHostAutostartTick`);
    state machine statics at `port/src/main.c:325-330`
  - Lineage: Authored-in-PD2 (new in c3845)
  - Pillar Impact: Online-mode Boundary
  - Defect Class: Determinism
  - Intended Outcome: Listen-host detects a remote client in
    `CLSTATE_LOBBY`, waits ~120 frames (≈2s) for manifest settle,
    then fires `netLobbyRequestStartWithSims()` exactly once.
  - Current Behavior: The settle counter is **frame-based**, not
    wall-clock-based. If `mainTick` stalls (long GC pause, GL driver
    hitch, manifest-distribution stall), the settle counter ticks
    forward as fast as the frames do — but the *remote client's state*
    may not be advancing at the same rate. If the remote disconnects
    mid-settle, no path returns the state machine to a "no remote in
    lobby" state — the host can sit in `Phase=1` forever waiting.
  - Gap / Failure Mode: A real-internet peer with packet loss, jitter,
    or a client crash mid-handshake can leave the host's autostart
    state machine wedged. The smoke uses 127.0.0.1 with perfect
    reliability, so this never surfaces in CI.
  - Why It Matters: c3845 is the gate to MP one-box. The smoke proves
    the golden path works; the production target (real-internet
    listen-host) needs the state machine to be self-recovering against
    peer drop.
  - Risk If Not Fixed: Real-world MP-room creators report "host hangs
    on autostart" with no logged cause; the host log only shows
    "waiting for client settle" repeating forever.
  - Recommendation: Add a wall-clock timeout on the settle phase
    (e.g., 10s) and a "remote client departed mid-settle" transition
    that returns to Phase=0 (no client in lobby). Log every state
    transition so a future bug report can be diagnosed without a live
    repro.
  - Cross-System Changes Required: No (self-contained in main.c).
  - Blocks Intended Outcome?: Partially (works on loopback; fragile on
    real net).

- **NET-SMOKE-COVERAGE — `listen_host_match_smoke` is golden-path only**
  - Severity: High
  - Confidence: Confirmed
  - Location: `tools/smoke-verify/tests/listen_host_match_smoke.json`
    (the full 117-line fixture)
  - Lineage: Authored-in-PD2 (new in c3845)
  - Pillar Impact: Online-mode Boundary
  - Defect Class: Trust-Boundary
  - Intended Outcome: An automated MP gate that catches regressions in
    listen-host match lifecycle (room join → ready → match start →
    spawn → score → end → endscreen).
  - Current Behavior: The smoke verifies the happy path: host arms
    `--launch-mp-room base:arena_mp_felicity base:combat 0`, client
    auto-connects on 127.0.0.1:27200, settle/autostart fires, both
    players spawn (slot 0 + 1), scores replicate, time-limit end, both
    show endscreen. **Coverage gaps:** no malformed `SVC_*`/`CLC_*`,
    no out-of-order packet ordering, no peer disconnect mid-flow, no
    server-message-from-client (`SVC_*` sent by client) rejection,
    no rate-limit thrash, no identity/cookie spoof, no malformed mod
    push, no reconnect.
  - Gap / Failure Mode: A `CLC` handler that fails to validate state
    order (e.g., accepts `CLC_MANIFEST_STATUS` before `CLC_AUTH`), or
    fails to reject a `SVC_*` from a client, will pass the smoke and
    enter the shipping bar.
  - Why It Matters: The smoke is now the canonical MP gate. If it
    only proves the golden path, the trust-boundary properties the
    online-mode pillar declares are *unproven* by automated test.
  - Risk If Not Fixed: A future refactor (or a hostile peer) breaks
    a trust boundary, the smoke still passes, the bug ships.
  - Recommendation: Extend with adversarial variants — at minimum:
    (a) a peer that sends `SVC_*` (should be rejected at server eval),
    (b) a peer that sends `CLC_MANIFEST_STATUS` from an unauthenticated
    slot (should be ignored), (c) a peer that disconnects between
    `CLC_MANIFEST_STATUS` and `CLC_AUTH` (host should clean up slot),
    (d) a peer with mismatched protocol version (already covered by
    the v51 exact-equality reject at `netServerEvConnect`, but pin it
    explicitly in the smoke matrix).
  - Cross-System Changes Required: No (smoke fixture only).
  - Blocks Intended Outcome?: Partially (the MP path works; the trust
    properties are unverified).

  flag intent unclear**
  - Severity: Medium
  - Confidence: Unverified
  - Location: `port/fast3d/scenario_scene_renderer.cpp:1600-1614`
  - Lineage: Authored-in-PD2 (B-936 follow-on)
  - Pillar Impact: None
  - Defect Class: Lineage-Shape (workaround-as-fix risk)
  - Intended Outcome: The world DL (game VP) renders correctly atop

    feature in the scene's projection silently breaks.
  - Recommendation: Decide intent. If permanent: rename to
    `--clear-depth-after-scene` (no `--debug-` prefix), document why

    architecture would be separate depth buffers / shared projection

    temporary: add a TODO with the exit criterion and an owner.
  - Cross-System Changes Required: No (rename + comment only).

### High Priority Findings

- **MODASSET-ANIM-FIELD-OVERFLOW — Allocation `cap_frames *
  expect_fields * sizeof(u32)` lacks multiplication overflow guard**
  - Severity: High
  - Confidence: Confirmed
  - Area: Code Quality
  - Location: `port/src/modasset_compiler.c:2987-2989`
    (special-parts allocation for ANIMFIELD_08 / ANIMFIELD_CAMERA)
  - Lineage: Authored-in-PD2 (new in B-942/B-944 schema-v5 work)
  - Pillar Impact: Modding Pipeline
  - Defect Class: Layout, Supply-Chain
  - What We Found: The allocation `calloc((size_t)cap_frames *
    (size_t)expect_fields, sizeof(u32))` reads `cap_frames` and
    `expect_fields` from author-provided GLTF extras. `cap_frames` is
    capped at `0xFFFF` (line 2984); `expect_fields` is bounded by
    `animPartFieldCount()` (max ~11 per schema). For *valid* archives
    this is fine (≤ ~7.7 MB), but the multiplication itself has no
    overflow check. A future schema bump that grows the field count
    beyond the implicit cap, or a malformed archive that bypasses
    `animPartFieldCount`, can overflow.
  - Why It Matters: Animation source comes from mod archives, which
    is the modding pipeline's primary untrusted-input surface. The
    pillar mandate is "fail loudly on invalid source, never silently
    consume."
  - Risk If Not Fixed: Hostile or malformed `.pdanim_chr` causes an
    integer-wrap in the calloc size argument, the allocation
    succeeds at a small wrapped size, the subsequent indexed write
    overflows the heap → potential RCE under a mod-supply-chain
    attack.
  - Recommendation: Add explicit overflow guard before the multiply:
    `if (cap_frames > 0 && expect_fields > UINT32_MAX / cap_frames /
    sizeof(u32))` → reject the archive with a loud log
    (`MODASSET.ANIM.OVERFLOW`). Same pattern wherever
    `cap_frames * field_count`-shaped arithmetic appears.
  - Cross-System Changes Required: No (self-contained in
    modasset_compiler.c).

- **MODASSET-VTX-MATRIX-PARSE-VALIDATION — `vtx_matrix` JSON parse
  may not validate all 3 array elements**
  - Severity: High
  - Confidence: Probable (parse loop not in diff range; needs
    direct read of the JSON-side parser)
  - Area: Code Quality
  - Location: `port/src/modasset_compiler.c` (caller of the
    per-corner matrix parser around line 6288+ in the existing file)
  - Lineage: Authored-in-PD2 (new in B-942)
  - Pillar Impact: Mod-native Parity, Modding Pipeline
  - Defect Class: Layout
  - What We Found: The per-corner matrix array is declared as
    `obj_triangle_t::vtx_matrix[3]` and initialized to `-1` in all
    mesh-add paths (`modasset_compiler.c:668, 7127-7129` —
    `objMeshAddTriangleWithTexcoords`, `generatedModeldefReadFaces`).
    The JSON parse reads `model.faces.json`'s `"vtx_matrix"` array
    (optional for pre-B-942 archives). If the field is present but
    malformed — short array `[m0]` instead of `[m0, m1, m2]` — the
    initialization defaults at `-1` provide a safe default, but
    *only if the parser skips the truncated array entirely*. If the
    parser reads what it can and leaves the unread slots at their
    init values, the partial parse is safe. If the parser reads what
    it can and overwrites with garbage, vertices 1 and 2 mis-bind to
    whatever index the partial JSON produced.
  - Why It Matters: This is exactly the layout-class defect Phase
    2.5 hunts for — a typed field with a known stride where the
    consumer assumes complete arrays.
  - Risk If Not Fixed: Modder accidentally truncates a `vtx_matrix`
    array (typo, hand-edit), the chr body renders with garbage bone
    bindings on one or two corners per triangle, leg-scramble
    returns silently.
  - Recommendation: Verify the parser explicitly checks the array
    has exactly 3 elements and rejects (with logged warning) any
    other length. The auto-detect path (model.obj/gltf/glb fallback
    in `loaderPoolGet*`, see prior 06-19 Medium) is the right
    template.
  - Cross-System Changes Required: No.

### Medium Priority Findings

- **MODASSET-ANIM-FIELD-VALUES-BOUNDS — `sp->field_values[frame_idx
  * expect_fields + fi]` is row-stride-indexed without per-row
  field-count check**
  - Severity: Medium
  - Confidence: Probable
  - Area: Code Quality
  - Location: `port/src/modasset_compiler.c:2988-2989, 3003`
  - Lineage: Authored-in-PD2 (new in B-942/B-944 schema-v5 work)
  - Pillar Impact: Modding Pipeline
  - Defect Class: Layout
  - What We Found: Allocation is `cap_frames * expect_fields * u32`.
    Access pattern is `sp->field_values[frame_idx * expect_fields +
    fi]`. The inner loop checks `fi != expect_fields` per row, which
    enforces the field-count invariant for the *current* row only.
    If the JSON encodes per-row field counts that differ from
    `expect_fields`, earlier rows with fewer fields would lead to
    later rows' `frame_idx * expect_fields + fi` computations
    indexing beyond the allocated region.
  - Why It Matters: Each row is parsed independently; the row-stride
    is a global invariant. Mismatch between authored row width and
    schema-declared `expect_fields` is silent.
  - Recommendation: After parsing each row, assert `(frame_idx + 1)
    * expect_fields <= alloc_count`. Or, on a row's first field,
    pre-compute `row_base = frame_idx * expect_fields` and assert
    `row_base + expect_fields <= alloc_count`.
  - Cross-System Changes Required: No.

- **B-944-SCAN-COVERAGE — Anim S32 overflow guard may cover only
  the part-header walk, not the frame-data inner loop**
  - Severity: Medium
  - Confidence: Probable
  - Area: Code Quality
  - Location: `port/src/romextract_pdanim_chr.c` (around the
    `s_animSkipPartHeader` and `s_readBeS32` family of functions)
  - Lineage: Authored-in-PD2 (B-944 fix)
  - Pillar Impact: Modding Pipeline
  - Defect Class: Scaling, Lineage-Shape
  - What We Found: The visible delta-side guard checks `ptr > end`
    after the part-header walk (e.g., logging `"part header
    overflow at part=%u"`). The commit subject reads "Decode sweep:
    anim S32 overflow + font clip" — the font clip is clearly
    bounded. The S32 frame-data overflow path (where each frame's
    `s32` field value is read individually) is not visible in the
    diff window the agents read. If the guard only protects the
    header walk, a malformed/long frame chain can still overflow
    a single `s32` arithmetic operation.
  - Recommendation: Grep `port/src/romextract_pdanim_chr.c` for
    every `s_readBeS32`, `s_readBeS16`, `s_readBeU32` etc. call and
    confirm each reads through a bounds-checked cursor. The
    canonical pattern is `if (ctx->ptr + sizeof(s32) > ctx->end)
    { fail loudly; return; }` *before* the cast/read, not after.
  - Cross-System Changes Required: No.

- **RNDR-VAO-RESTORE-DISCIPLINE — Scene renderer's VAO/VBO restore
  is correct but not structurally enforced**
  - Severity: Medium
  - Confidence: Probable
  - Area: Code Quality
  - Location: `port/fast3d/scenario_scene_renderer.cpp:1413, 1635`
    (save/restore pair); state mutations between the pair
  - Lineage: Authored-in-PD2 (B-936 follow-on, commit `bc86441f`)
  - Pillar Impact: None (rendering correctness)
  - Defect Class: Lineage-Shape
  - What We Found: The VAO/VBO save/restore is correctly paired for
    the current linear control flow. Two-pass alpha-blend
    introduces glEnable(GL_BLEND), glBlendFunc, glDepthMask(FALSE)
    on pass 1 → restoration on exit; these mutations are
    state-cache-transparent because the raw-GL scene renderer does
    not consult or update fast3d's `rendering_state`. If a future
    refactor adds an early-return or exception path between
    1413 and 1635, the restore is skipped and the next fast3d draw
    sees inherited state.
  - Recommendation: Wrap the section in a RAII-style C++ guard
    (constructor saves, destructor restores) so the restore is a
    structural invariant, not a discipline. The codebase already
    uses C++ in `port/fast3d/`, so this is idiomatic.
  - Cross-System Changes Required: No.

### Critical Issues

- (none distinct from Section 2/3).

### High Priority Findings

- **SMOKE-COMPILED-IN — Smoke harness is compiled into the release
  binary (no `#ifdef DEBUG`)**
  - Severity: High
  - Confidence: Confirmed
  - Area: Security
  - Location: `port/src/smoke_harness.c` (the file as a whole);
    `port/src/pdmain.c:791` (unconditional tick hook);
    `port/src/main.c:3347-3349` (always-link initialization)

  - Pillar Impact: Online-mode Boundary
  - Defect Class: Trust-Boundary, Supply-Chain
  - What We Found: The smoke harness is permanently linked into
    the binary. The agents verified the only activation gate is
    `sysArgGetString("--smoke")` returning non-null
    (`smoke_harness.c:872-875`). All entry points
    (`gfxRequestSmokeScreenshot`, event dispatch,
    `bootHostAutostartTick` arming) depend on either the flag or
    the armed-state global.

    becomes a debug-mode-in-production foothold. The pattern itself
    is the risk, not today's specific code.

    that exposes the harness (e.g., reads the screenshot buffer
    from a network packet, fires an autostart from a peer message)
    and the gate is bypassed. Also: an attacker with a debugger or
    save-game injection can flip the armed-state globals at runtime
    without ever passing CLI args.

    `#ifdef PD2_SMOKE_ENABLED` defined only in dev builds, or
    (b) add a build-time assertion that every harness entry point
    is `static` to `smoke_harness.c`, with public surface limited
    to one `smokeHarnessTick()` that checks a *runtime-immutable
    init flag*. Today's runtime flag is set via
    `smokeHarnessInit()` which itself is callable any time.
  - Cross-System Changes Required: Maybe (release build CMake).

  - Severity: Medium
  - Confidence: Probable
