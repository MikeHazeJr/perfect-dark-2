## 1) Inferred Project Goal & Intended Outcomes

### Inferred Purpose
Perfect Dark 2 is a community fork that takes Rare's *Perfect Dark* PC port (`fgsfdsfgs/perfect_dark`, `port-net` branch) and re-engineers it into a modding-first, P2P-multiplayer, social-Grid-aware game with a PC-only target (`x86_64`/Windows/MSYS2-MinGW + CMake). The current shipping target (S486 constraint, 2026-04-27) is **listen-host online connectivity inside the game client** -- the dedicated server (`pd-server`) builds and runs as tooling/regression coverage but is deferred behind the in-client release. The Catalog is the single source of truth for asset identity. The Grid (`port/src/forge/`) is both a level editor and a social discovery layer; modding is `.pdmod` archive based with SHA-256-pinned distribution.

### Likely Player & Contributor Types
- PD/GoldenEye veterans expecting authentic feel with modern features
- Modders authoring `.pdmod` archives (Maps, Weapons, UI Chrome, Skins, Audio)
- Community hosts running listen-mode servers
- Speedrunners / challenge-runners using the Grid for repeatable encounters
- Future: dedicated-server operators (track deferred per S486)

### Core Workflows / Gameplay Loops (Inferred)
1. Single local player launches client -> selects mode (Solo / MP / Grid / Swarm-test) -> mission flow.
2. Listen-host: P2P 6-tier NAT traversal -> ENet auth handshake -> manifest exchange -> match start.
3. Mod author: `.pdmod` archive built locally -> server distributes via PDCA archive over `SVC_DISTRIB_*` -> client receives, SHA-256 verified, decompressed, hot-registered in catalog.
4. Grid (Forge): freefly editor places objects from catalog -> instantiates as live props/bots/spawn-pads on FREEFLY->NORMAL transition -> playable session.
5. Swarm-test: developer harness benchmarks chr/bot pipeline at 4..256 chrs, escapes `MAX_BOTS=32` via private aibot pool.

### Upstream Lineage Observations
- **`n64decomp/perfect_dark`**: `src/game/`, `src/lib/` are still N64-decomp shape -- 234k LOC, ROM-address file names (`game_175f50.c`), `s32/u8/f32` typedefs, `bool` redefined as `s32` (constraint), 50+ headers per TU, magic-string stage allocation tables in `port/src/pdmain.c:147`. PD2 has not redrawn the decomp/port boundary; it has additively layered on top.
- **`fgsfdsfgs/perfect_dark` (`port-net`)**: most of `port/src/net/` and `port/fast3d/` is descended from this. Net protocol has been bumped 19+ versions on the PD2 side (v27 -> v46), which is the cleanest signal of how aggressively PD2 has departed from the parent.
- **`jonaeru/perfect_dark` (`allinone`)**: Asset-pack legacy. PD2 retired the `g_ModNum` integer mod selector entirely (2026-03-24, removed constraint); shadow asset arrays gone. The AllInOne lineage now survives only as historical content (Goldfinger/Kakariko/etc. maps) registered through the modern catalog.
- **PD2-authored**: catalog system, .pdbase loader (S591 F11/F12/F13), Forge editor, Modding Hub, Grid, Mod Manager UI, manifest pipeline, P2P 6-tier orchestrator, dedicated server skeleton, presence/voice (Ed25519 signed), connect codes, swarm-test harness, identity profile system, save migration framework. All substantive additions.

### Pillar Observations (Catalog / Mod Parity / Modding Pipeline / Grid / Online Mode / Dedicated Server)
- **Catalog**: F13 (Layer A retirement for weapons) shipped 2026-04-30. `g_Weapons[]`/`g_AibotWeaponPreferences[]` and 110 animation arrays gone; `src/game/invitems.c` reduced from 5789 to ~50 lines. .pdbase as parallel format to .pdmod is now real, not aspirational. Manager pattern is ready for bodies/heads/arenas/audio. **Other asset types still in Layer A** (stage table, headsandbodies, modelstates, etc.) -- migration not complete.
- **Mod parity**: largely intact, but a wire-vs-local asymmetry exists on the `.pdmod` hot-register path (see Finding D-3).
- **Modding pipeline**: deterministic enough on the build side (`mod.json` + INI). v46 added mandatory SHA-256 digest at `SVC_DISTRIB_BEGIN`. Distribution hardening is one of the stronger areas reviewed.
- **Grid**: a substantial editor exists; runtime instantiation is fixed-pool. Recent bug fixes (B-299/B-300/B-301/B-302 from S594 on 2026-05-01) addressed editor-visibility, exit-routing, select-spawn-attach, and chr-body hot-reload. B-298 (vehicle IMC consumers missing) deferred.
- **Online-mode boundary**: present (`g_NetMode`, `g_NetDedicated`, `g_NetLocalClient`) but the boundary discipline relies on guards rather than a typed mode object. ROM/mod check is correctly skipped for dedicated. Cutscene wire (`CLC_CUTSCENE_SKIP`) authoritatively binds skip requests to `srccl->playernum`.
- **Dedicated server**: `pd-server` builds. Game-agnostic broker work (P4-B/P4-C) deferred per S486; today the server is PD2-specific with a per-game plugin ABI ADR drafted but not implemented.

### Assumptions / Unknowns
- This audit did not run the full pd-tests suite. Pin-test claims in pillar docs are taken at face value where the test name is documented (e.g. `tests/test_versions_pin.c`, `tests/test_save_migration.cpp`).
- Runtime behavior of forge runtime / swarm test was not verified -- only the static call shape.
- `.pdbase` parity self-test (`loaderPdbaseRunParityCheck`) was inspected at the level of constraint documentation; actual diffs against `g_Weapons[]` not confirmed mid-audit because that table no longer exists in the tree as of F13.
- No external-platform big-endian or 32-bit target exists today; the endian/pointer-width findings below are forward-looking.

## 2) Design Intent & Gameplay / Multiplayer Fit Review

### System & Workflow Validation Findings

#### Critical Issues

##### D-1) `.pdmod` wire-distributed mods cannot register theme/font/chrome assets
- Severity: High (Critical for parity intent)
- Confidence: Confirmed
- Location: [port/src/net/netdistrib.c:1160-1163](../../port/src/net/netdistrib.c) (`ini_names[]` whitelist)
- Lineage: Authored-in-PD2
- Pillar Impact: Mod-native Parity / Modding Pipeline
- Defect Class: None (functional asymmetry)
- Intended Outcome: Mod content (locally installed AND wire-delivered) flows through identical registration paths and produces identical catalog rows. Theme mods, UI chrome mods, font mods all register cleanly regardless of source.
- Current Behavior (from code evidence): `netDistribClientHandleEnd` walks a hardcoded list of INI filenames (`map.ini`, `character.ini`, `bot.ini`, `prop.ini`, `textures.ini`, `texture.ini`, `skin.ini`, `weapon.ini`, `audio.ini`, `hud.ini`, `sfx.ini`, `music.ini`). Theme bundles are not in the list. UI Chrome mods (the `mods/UI Chrome/<slug>/` flow added in S293 with the depth-cap constraint) are not in the list. Font mods are not in the list. Mods that ship an embedded `mod.json`-only manifest (no INI) are not in the list. Wire-delivered mods of these types fall through to the `iniFilenameToAssetType -> ASSET_NONE` warning path, leaving the entry not type-resolvable until a full local-disk scan/refresh happens.
- Gap / Failure Mode: Locally-installed theme/chrome/font mods work; wire-delivered ones silently fail to register their primary asset type. A user joining a host whose theme bundle they don't have receives the bytes but never sees the theme.
- Why It Matters: Direct violation of mod-native parity. The "if you stripped the labels you couldn't tell native from mod" property breaks: source-of-acquisition (local vs wire) materially changes which mod types work.
- Risk If Not Fixed: Theme-distribution feature is effectively local-only; users joining listen hosts cannot pick up host-distributed UI customizations. Future mod types added without updating this list have the same failure mode.
- Recommendation: Replace the hardcoded INI filename list with a registration via `mod.json` content array (already used by local scanner via `modmgrRegisterModJsonContentBuf`). Or, at minimum: extend the list to include `theme.json`, `chrome.json`, `font.ini`, and add a fallback path that runs the same `modmgrScanDirectory` walker on `destdir` after extraction (which would find every category of mod the local scanner finds).
- Cross-System Changes Required: Yes -- `netdistrib.c`, `assetcatalog_scanner.c`, `modmgr.c`, possibly `pdgui_theme_loader.cpp`.
- Blocks Intended Outcome?: Partially (mod-native parity for non-INI mod types).

#### High Priority Findings

##### D-2) Forge runtime prop pool and door pool silently truncate maps
- Severity: High
- Confidence: Confirmed
- Location: [port/src/forge/forge_runtime.c:74](../../port/src/forge/forge_runtime.c) (`FORGE_PROP_POOL_SIZE 64`), [port/src/forge/forge_runtime.c:80](../../port/src/forge/forge_runtime.c) (`FORGE_DOOR_POOL_SIZE 16`), drop sites at lines 344 and 585
- Lineage: Authored-in-PD2
- Pillar Impact: Grid Trust / Scaling Ceiling
- Defect Class: Scaling
- Intended Outcome: Forge maps can use up to FORGE_MAX_OBJECTS = 1024 objects. The runtime instantiates whichever subset of those are props/doors at FREEFLY->NORMAL transition.
- Current Behavior (from code evidence): editor-time storage is sized 1024 ([port/src/forge/forge_core.c:32](../../port/src/forge/forge_core.c)). At runtime, prop pool is 64 entries and door pool is 16. Spawn loop drops anything over the cap with `LOG_WARNING` ("door pool full -- uid=N '<id>' dropped" / "GRID.RUNTIME: prop pool full"). The map appears to load successfully but with content silently missing.
- Gap / Failure Mode: A user authoring a mid-size Grid map (the design doc allows 1024 placed objects) hits a silent truncation at runtime. No visual indicator in editor, no warning before transition, no UI feedback after the warning is logged.
- Why It Matters: Grid's value proposition is repeatability + creator authorship. Maps that look correct in the editor but silently lose content on play are a trust/UX failure for the entire pillar.
- Risk If Not Fixed: Mods will ship maps that play differently from how they were authored. Bug reports will be hard to triangulate ("the door is missing only when I play, not when I edit"). Edge cases: 17-door maps, 65-prop maps, prefab expansions that push over the cap.
- Recommendation: (a) Make the pools dynamically sized -- they live in MEMPOOL_STAGE which has 64 MB headroom, and a struct defaultobj or doorobj is well under 1 KB. (b) If keeping the cap, surface it in the editor as a budget meter and refuse to enter play mode when over budget. (c) At minimum, raise both caps to match the editor cap (1024 and at least 64) and add a pre-transition validator that lists which uids will be dropped.
- Cross-System Changes Required: Yes -- `forge_runtime.c`, `pdgui_forge_editor.cpp` (budget UI), possibly `forge_core.h` for new warnings struct.
- Blocks Intended Outcome?: Partially (Grid maps above the cap silently lose content).

##### D-3) Vehicle IMC actions have no consumer (B-298, deferred)
- Severity: High
- Confidence: Confirmed
- Location: bindings at [port/src/actionmap.cpp](../../port/src/actionmap.cpp), missing consumer in `src/game/bondbike.c:840` (legacy bondmove channel read instead)
- Lineage: Inherited-from-port + new IMC layer authored in PD2
- Pillar Impact: Online-mode Boundary / None directly, but blocks vehicle-mode online play
- Defect Class: None (incomplete migration)
- Intended Outcome: Vehicle dismount, throttle, steer, etc. flow through the typed actionmap (`ACTION_VEHICLE_*`) for both gameplay and IMC suppression discipline.
- Current Behavior (from code evidence): per S594 session log, `grep -r "ACTION_VEHICLE" src/game/` returns ZERO. The `bondbike.c::bbikeTick` reads `g_Vars.currentplayer->speedforwards/sideways/theta` (legacy bondmove) instead of `actionPressed(ACTION_VEHICLE_*)`. Bindings exist and fire (per playtest log), but no consumer.
- Gap / Failure Mode: Mike confirmed in the S594 playtest -- "I jumped on the Hoverbike. I was unable to operate it or exit it." Vehicle IMC layer is wired in but legacy gameplay code never adopts it.
- Why It Matters: Vehicles are a gameplay surface. The IMC architecture exists specifically so contextual input (FREEFLY vs NORMAL vs VEHICLE) is uniformly suppressed/promoted; a layer with no consumer is dead UX.
- Risk If Not Fixed: Vehicles unusable in any mode. Future Grid maps that include vehicle pickups will be effectively decorative. When the joint Menu/Input pillar slice resumes (per Mike's S594 directive), this is the first consumer to migrate.
- Recommendation: Migrate bondbike.c (and any other vehicle/turret consumers) to read the actionmap directly. The session log already notes this is deferred; this audit logs it for cross-reference completeness so it isn't lost when the next pillar slice starts.
- Cross-System Changes Required: Yes -- `src/game/bondbike.c`, possibly `bondmove.c`, IMC layer documentation.
- Blocks Intended Outcome?: Yes for vehicle workflows.

##### D-4) Dedicated server is PD2-specific despite "game-agnostic" architectural goal
- Severity: High
- Confidence: Confirmed
- Location: `pd-server` target in [CMakeLists.txt:716](../../CMakeLists.txt) shares `port/src/net/net.c` and includes ~50 game headers transitively. ADR draft at [context/designs/connectivity/pd-server-plugin-abi.md](../designs/connectivity/pd-server-plugin-abi.md) is marked deferred per S486.
- Lineage: Authored-in-PD2
- Pillar Impact: Dedicated-server Boundary
- Defect Class: Trust-Boundary
- Intended Outcome: Per audit-prompt and pillar doc -- `pd-server` is "an independent server binary designed to host PD2 *and other games*." PD2-specific logic lives behind a per-game plugin boundary.
- Current Behavior (from code evidence): server target links the same source tree as the client; `pd-server` knows about g_NetClients, g_MpSetup, the spawn weapon flow, room state, room-leader logic, mod manifest checks, ban list -- none of these have a per-game abstraction. The plugin ABI ADR exists (per pillar doc) but no plugin interface in code.
- Gap / Failure Mode: The architectural goal is currently aspirational. A PD2 zero-day in the server would be a server zero-day for any other game once the plugin model lands.
- Why It Matters: The audit-prompt and pillar doc both identify game-agnosticism as a first-class architectural pillar. Today the server is in tier with the client, not behind a typed boundary. This is a known deferral but is treated as a finding here because the audit framework grades against the stated intent, not the current ship plan.
- Risk If Not Fixed: When dedicated-server work resumes (post-S486 deferral), the code will need substantial re-architecture before it can host any game other than PD2. Plugin ABI design will face a much larger surface than if the boundary were drawn earlier.
- Recommendation: Treat the deferral as a *deferred fence*, not a deferred feature -- when the next dedicated-server slice begins, plugin ABI must land *before* further server-only logic accretes. Concrete starting moves: extract a per-game header (`pd_game_plugin.h`) that the server core only includes through a typedef'd struct of function pointers. Move the spawn-weapon resolver, manifest validation, and room-leader logic into pd-side plugin functions.
- Cross-System Changes Required: Yes -- substantial. CMakeLists, server source split, every shared `port/src/net/*.c` file inspected for game-specific calls.
- Blocks Intended Outcome?: Yes (architectural pillar).

- Severity: Medium
- Confidence: Confirmed
- Location: [port/include/net/net.h:285-297](../../port/include/net/net.h) (`netplayermove`), [port/include/net/net.h:212-225](../../port/include/net/net.h) (`netrecentserver`)

- Blocks Intended Outcome?: No (functionally correct today; structurally erosive).

##### D-6) `s_is_forge_door` substring match could collide with future catalog IDs
- Severity: Medium
- Confidence: Confirmed
- Location: [port/src/forge/forge_runtime.c:325-328](../../port/src/forge/forge_runtime.c) (`s_is_forge_door`)
- Lineage: Authored-in-PD2
- Pillar Impact: Catalog SOT
- Defect Class: None
- Intended Outcome: Forge runtime can identify door catalog IDs unambiguously.
- Current Behavior (from code evidence): `return strstr(catalog_id, ":door_") != NULL;` -- substring search anywhere in the ID. A future catalog ID like `base:underdoor_pad` or `mods/x:my_door_clip` would match.
- Gap / Failure Mode: false positive door classification routes a non-door catalog entry through the doorobj allocation path (line 337-451) which assumes door fields. Crash or silent corruption depending on where it falls.
- Why It Matters: substring matches over catalog IDs treat the namespace as informally structured. The catalog has typed entries (ASSET_DOOR is implicit via prop type, but no enum yet); the runtime should ask the catalog "is this a door?" rather than do a string scan.
- Risk If Not Fixed: When mods or future PD2 features introduce IDs that incidentally contain `:door_`, classification corrupts. Especially likely with ID namespacing conventions that haven't been formalized.
- Recommendation: Add a typed predicate `catalogIsForgeDoor(asset_entry_t*)` (or look at `entry->category == "doors"`) and use it. Or anchor the prefix: `strstr(id, ":door_") == id + namespace_len + 1`. Best: introduce ASSET_DOOR or use `entry->ext.prop.is_door`.
- Cross-System Changes Required: Yes -- forge runtime + catalog header.
- Blocks Intended Outcome?: No (functional today).

## 3) Code Quality Review

### Critical Issues

##### Q-1) PDCA archive format writer/reader endianness mismatch
- Severity: Critical (forward-looking; functional today only because all targets are LE)
- Confidence: Confirmed
- Area: Code Quality + Layout Integrity
- Location: writer at [port/src/net/netdistrib.c:213-215](../../port/src/net/netdistrib.c), [netdistrib.c:248-284](../../port/src/net/netdistrib.c); reader at [netdistrib.c:601-628](../../port/src/net/netdistrib.c)
- Lineage: Authored-in-PD2
- Pillar Impact: Modding Pipeline / Catalog SOT (mod content integrity)
- Defect Class: Layout (Phase 2.5: endianness hazards on migrated types)
- What We Found: The PDCA archive format (the on-the-wire mod transfer format AND the on-disk inferred format) writes multi-byte fields in HOST byte order, but reads them with LE conversion (`PD_LE16` / `PD_LE32`). On x86_64 (PLATFORM_LITTLE_ENDIAN, where `PD_LE*` is identity per `src/include/platform.h:69-71`) this works. On a hypothetical big-endian target, the writer would emit BE bytes and the reader would bswap them to host (BE) -- corrupted result. More immediately concerning: a BE-host writer and an LE-host reader cannot share archives. Compare this to the netbuf layer (`port/src/net/netbuf.c:218-246`), which correctly applies `PD_LE16/32/64` on the writer side BEFORE memcpy, and applies it on the reader side AFTER memcpy. The netdistrib bypass (used for large payloads) lost the symmetry.
- Why It Matters: PDCA archives are the wire/file representation of distributed mods. An LE-only assumption locks PD2 to one byte order. Even on the current LE-only platform, a future feature like archive caching, hash-stable catalog payloads, or cross-host signed mod authoring would inherit the asymmetry as a correctness bug rather than the cosmetic platform-portability issue it is today.
- Risk If Not Fixed: Future cross-platform support breaks silently (no test pin, no platform CI catches this). Any mod author shipping their .pdmod from a BE host produces archives unreadable on LE.
- Recommendation: Apply `PD_LE16(path_len)` / `PD_LE32(fsize)` / `PD_LE32(magic)` / `PD_LE16(file_count)` BEFORE memcpy on the writer side. Add a test pin: `tests/test_distrib_pdca.cpp` writes a known-content archive and asserts the byte layout against a fixed hex blob, so any future endian regression is caught at unit test time.
- Cross-System Changes Required: No (single file).

##### Q-2) `netbufWriteU16/U32/U64` use unaligned direct-cast writes (UB on strict-alignment targets)
- Severity: High (Critical for correctness on non-x86 targets)
- Confidence: Confirmed
- Area: Code Quality
- Location: [port/src/net/netbuf.c:218-246](../../port/src/net/netbuf.c)
- Lineage: Inherited-from-port-net (likely)
- Pillar Impact: None directly; affects every net write
- Defect Class: Layout (Phase 2.5: alignment and padding drift)
- What We Found: Reader was migrated to `memcpy` (per `H-6` comment at [netbuf.c:61](../../port/src/net/netbuf.c)) to avoid unaligned reads. Writer was not migrated -- still uses `*(u16 *)&buf->data[buf->wp] = PD_LE16(v);` (line 221). Same pattern at U32 (line 231) and U64 (line 241).
- Why It Matters: Misaligned writes through a casted pointer are undefined behavior on strict-alignment ISAs (ARM v7, MIPS, SPARC). x86_64 happens to handle them; the LSP project's Switch homebrew target (mentioned upstream) was on aarch64 which usually allows unaligned but is permitted to fault. Future ports re-introduce this as a portability bug.
- Risk If Not Fixed: Crashes on any future strict-alignment build target. UBSan run on the test suite would already flag this.
- Recommendation: Mirror the reader pattern -- `u16 leval = PD_LE16(v); memcpy(&buf->data[buf->wp], &leval, sizeof(leval));`. Same for U32 and U64.
- Cross-System Changes Required: No (single file).

#### High Priority Findings

##### Q-3) Server distribution queue is unbounded-fanout single-tick serial
- Severity: High
- Confidence: Confirmed
- Area: Code Quality + Scaling
- Location: [port/src/net/netdistrib.c:60](../../port/src/net/netdistrib.c) (`DISTRIB_MAX_QUEUE 64`), [netdistrib.c:503-534](../../port/src/net/netdistrib.c) (`netDistribServerTick` -- one transfer per tick across all clients)
- Lineage: Authored-in-PD2
- Pillar Impact: Scaling Ceiling / Dedicated-server Boundary
- Defect Class: Scaling
- What We Found: Server-side distribution queue is server-wide (not per-client), capped at 64 active entries, processes exactly one transfer per server tick. `streamComponentToClient` runs the entire transfer (build archive, compress, send all chunks via `enet_peer_send` loop) inside the same tick body. For a 50 MB component split into 16 KB chunks, that's ~3200 enet_peer_send calls in one tick. The queue's `s_QueueHead`/`s_QueueTail` FIFO state is unused -- both `netDistribServerHandleDiff` and `netDistribServerTick` linear-scan for any active slot, breaking FIFO ordering implicitly.
- Why It Matters: For a listen host with 1-3 friends this is fine. For a future dedicated server with N clients each needing several mods: at one component per server tick (60Hz), wholly serial across clients, the worst case is 60 components/sec. A 32-client lobby where each client needs 8 mods is 256 transfers, ~4 seconds of queue drain assuming each transfer is small. A fully populated queue with 64 entries, processing one per tick, all hitting `streamComponentToClient` synchronously, is a per-tick stall vector. The FIFO miswire means a client who diff'd late might get serviced before a client who diff'd first.
- Risk If Not Fixed: Server tick frame stalls during mod distribution. Late-joiners block earlier-arrived clients. Dedicated server scaling story breaks down under realistic mod loads.
- Recommendation: (a) Per-client queues -- one structure per netclient. (b) Async chunk send: the per-tick budget is "send up to N bytes" or "send N chunks" rather than "complete one component." (c) Fix or remove `s_QueueHead`/`s_QueueTail` -- either implement actual FIFO or delete the unused fields.
- Cross-System Changes Required: No (one file, plus possibly netclient struct for per-client state).

##### Q-4) `netDistribClientHandleEnd` allocates `archive_bytes + 1024` for decompress without overflow guard against `archive_bytes` close to UINT32_MAX
- Severity: High
- Confidence: Confirmed
- Area: Code Quality + Security
- Location: [port/src/net/netdistrib.c:1117-1133](../../port/src/net/netdistrib.c)
- Lineage: Authored-in-PD2
- Pillar Impact: None
- Defect Class: Trust-Boundary
- What We Found: Code at line 1122 rejects `archive_bytes > 256MB` (good). Then line 1127 computes `raw_len = archive_bytes + 1024` -- safe given the 256MB cap. **But** line 769 also rejects at `MAX_DISTRIB_ARCHIVE_BYTES = 512MB` -- so two different caps exist (`256MB` for END/decompress, `512MB` for BEGIN). A malicious server could pass BEGIN's check (claims 400MB), allocate `s_RecvSlots[i].compressed_buf` and accumulate that many bytes, only to be rejected at END. **Allocation budget mismatch** lets a hostile server consume up to 512MB of client compressed buffer per slot before the END-side cap fires. With RECV_SLOTS=4, that's 2GB potential RAM exhaustion before any decompress is attempted.
- Why It Matters: Resource-exhaustion vector. The per-slot grow budget at `netDistribClientHandleChunk` has its own cap (`128MB` at line 900), so the worst-case compressed buffer is 128MB per slot, 512MB across slots -- still substantial. The trust-threshold approval prompt fires on `archive_bytes > threshold_mb*1MB` (default 256MB), so a 200MB archive bypasses the prompt.
- Risk If Not Fixed: A hostile listen host can OOM clients by claiming valid-but-large archive_bytes within the threshold then streaming mostly-noise compressed data. SHA-256 verification fails, but only after the buffer is filled.
- Recommendation: Single-source the cap. Pick one (probably `MAX_DISTRIB_ARCHIVE_BYTES` at 256MB to match the END-side check). Add an upfront check that `archive_bytes <= MAX_DISTRIB_ARCHIVE_BYTES` matches the recv-grow cap (`128MB * 2 = 256MB`). Reduce the per-slot recv buffer cap to match the trust threshold so non-approved-mod traffic can never exceed `s_TrustThresholdMb * 1MB`.
- Cross-System Changes Required: No (single file).

### Critical Issues

##### S-1) Distribution trust threshold is bypassed by sub-threshold sequential transfers
- Severity: High (treated as Critical because it neuters a primary user-facing trust control)
- Confidence: Confirmed
- Area: Security
- Location: [port/src/net/netdistrib.c:847-856](../../port/src/net/netdistrib.c)
- Lineage: Authored-in-PD2
- Pillar Impact: Modding Pipeline / Online-mode Boundary
- Defect Class: Trust-Boundary
- What We Found: `netDistribClientHandleBegin` checks `archive_bytes > threshold_bytes` per-archive. The session-aggregate cap (`NET_DISTRIB_MAX_SESSION = 200MB`) is enforced at line 794-805 and is correct as far as it goes. But the **trust threshold prompt** (line 847-856) only fires per archive. A hostile listen host can ship 10 archives at 200MB each (well under the 256MB default threshold), totaling 2 GB. Each one prompts no warning, each one fits under the threshold, and the session cap fires only at 200MB total -- but the threshold is intended to be a per-mod approval gate, not a budget summed across mods.
- Wait -- re-reading: `NET_DISTRIB_MAX_SESSION = 200MB` per the const at `net.h:242` is a hard cap, so the actual exposure is 200MB total per session, not 2GB. **However**, the trust-threshold UX is still inconsistent: a single 257MB mod fires the prompt; ten 25MB mods (250MB total) don't, even though they exceed the prompt threshold *in aggregate*. From a user-trust standpoint, "I approved no big downloads, I got 250MB of mods" is a UX-trust failure even if the bytes-in-flight remained capped.
- Why It Matters: The trust threshold is the user's "stop, ask me first" surface. Per-archive sizing means a server author can chunk a malicious payload into 256MB-just-under-threshold bites and stay invisible.
- Risk If Not Fixed: User-trust UX hole on the most security-relevant control surface.
- Recommendation: (a) Track session-cumulative threshold separately from session-cap. When `s_ClientStatus.session_bytes_total + archive_bytes > threshold_bytes`, prompt regardless of single-archive size. (b) Also add a count-based threshold: prompt after N archives in a session even if the bytes are small.
- Cross-System Changes Required: No (single file).

##### S-2) PDCA archive byte order isn't authenticated as part of the SHA-256 digest scope
- Severity: Medium (Confirmed; not exploitable today because all targets are LE)
- Confidence: Confirmed
- Area: Security
- Location: [port/src/net/netdistrib.c:391](../../port/src/net/netdistrib.c) (`sha256Hash(compressed, ...)`)
- Lineage: Authored-in-PD2 (S507)
- Pillar Impact: Modding Pipeline
- Defect Class: Trust-Boundary
- What We Found: The v46 digest covers the compressed-archive bytes that cross the wire. Good. **But** the archive's internal multi-byte fields are written in host byte order (per Q-1). On an LE host, the digest is over LE-encoded internals. On a hypothetical BE host, the same logical archive would have BE-encoded internals and a different digest. So the `expected_sha256` validates byte-equality of the on-wire payload, not semantic equality of the archive. A signed catalog of (id, sha256) authored on an LE host would not validate on a BE host even for an identical archive content.
- Why It Matters: Any future "signed mod catalog" or "Catalog Authority" trust model that pre-computes (id, sha256) tuples gets locked to the byte-order of the signing host. Since PD2 is LE-only today this is a forward-looking issue -- but it's a footgun for the supply-chain pipeline the project intends to build.
- Risk If Not Fixed: When/if signed mod catalogs land, signatures will become non-portable across host architectures. The fix is the same as Q-1: enforce LE on the archive format.
- Recommendation: Combine with Q-1 fix. Once writer applies LE conversion, archive layout is platform-independent and sha256 is portable.
- Cross-System Changes Required: No.

#### High Priority Findings

##### S-3) Mod over-the-wire INI whitelist bypass risk via `iniFilenameToAssetType` -> `ASSET_NONE`
- Severity: Medium
- Confidence: Confirmed
- Area: Security + Mod-native parity (joint)
- Location: [port/src/net/netdistrib.c:929-945](../../port/src/net/netdistrib.c) and `populateExtFromIni` at line 970
- Lineage: Authored-in-PD2
- Pillar Impact: Catalog SOT / Mod-native Parity
- Defect Class: Trust-Boundary
- What We Found: `iniFilenameToAssetType` maps INI filename -> asset_type_e. A mod whose INI filename is unknown returns ASSET_NONE (line 944). The handle-end path logs `LOG_WARNING` and continues registering with type=ASSET_NONE (line 1192-1199 of the wider netDistribClientHandleEnd). An ASSET_NONE entry in the catalog has no typed resolver and is never read; this is logically a soft-fail. **However**: nothing on the wire-side validates that the INI filename is one of the allowed names. A hostile server could (a) ship an archive containing both `weapon.ini` AND a malformed `audio.ini`, both register, only one populates ext fields. (b) Exploit any path where a registered ASSET_NONE entry is later queried by ID and the typed-resolver-not-implemented case is more permissive than the typed path.
- Why It Matters: Wire-delivered mods enter the catalog with weaker type discipline than locally-installed mods. The local scanner (`assetcatalog_scanner.c`) drives off `mod.json` content array AND scans for known INI names; the wire path only does the latter. Inconsistent attack surface.
- Risk If Not Fixed: Future code paths that iterate the catalog and assume "everything has a type" will encounter ASSET_NONE entries from wire-distributed mods and behave unexpectedly.
- Recommendation: Mirror the local scanner's behavior on the wire side. Specifically: require `mod.json` for any wire-distributed mod, parse it, only register based on its content array entries -- not on stray INI files.
- Cross-System Changes Required: Yes.

##### S-4) `streamComponentToClient` doesn't validate `entry->dirpath` is under the configured mod directory
- Severity: Medium
- Confidence: Probable (depends on registration discipline)
- Area: Security
- Location: [port/src/net/netdistrib.c:262](../../port/src/net/netdistrib.c) (`buildArchiveDir(buf, ..., entry->dirpath, "")`)
- Lineage: Authored-in-PD2
- Pillar Impact: Modding Pipeline
- Defect Class: Trust-Boundary
- What We Found: The server walks `entry->dirpath` (an absolute path stored at registration time) and packages everything inside. `entry->dirpath` is set wherever `assetCatalogRegister*` is called and the field is filled with whatever `dirpath` the caller passes. If a future code path registers an entry with `dirpath` set to a sensitive directory (`/etc`, `C:/Windows`, `~/.ssh`), the server would happily archive and ship that path's contents.
- Why It Matters: The trust model assumes `dirpath` is always under a sandboxed mod directory. Today every register site (per `assetcatalog_scanner.c`, `assetcatalog_base.c`, `modmgr.c`) does point at mod-tree directories, but no server-side check enforces this invariant.
- Risk If Not Fixed: A future bug or attacker-influenced registration path leaks filesystem contents over the wire.
- Recommendation: Add an explicit guard in `streamComponentToClient`: `if (!fsPathIsUnderModDir(entry->dirpath)) return;`. Add a registration-time invariant check too.
- Cross-System Changes Required: Yes (one new helper, one new check at registration).

#### Medium Priority Findings

##### S-5) Hostile peer can claim `srccl->playernum >= MAX_PLAYERS` and pass through cutscene-skip handler
- Severity: Low
- Confidence: Confirmed
- Area: Security
- Location: [port/src/net/netmsg.c:4595-4604](../../port/src/net/netmsg.c)
- Lineage: Authored-in-PD2 (S511)
- Pillar Impact: Online-mode Boundary
- Defect Class: Trust-Boundary
- What We Found: Reader logic: `if (srccl->playernum < MAX_PLAYERS) { playernum = srccl->playernum; } if (playernum >= MAX_PLAYERS) { reject; }`. If `srccl->playernum >= MAX_PLAYERS` (which should never happen for an authenticated client but is not statically asserted), the function falls back to the requested_playernum read from the wire. The line 4599 check then rejects if requested_playernum >= MAX_PLAYERS, but a malicious client could send a valid-looking requested_playernum and the function would accept `playernum = requested_playernum` from the wire when srccl->playernum is invalid.
- Why It Matters: Trust assertion is conditional, not unconditional. The constraint says "server must bind to authenticated `netclient.playernum`" -- the implementation binds *if* netclient.playernum is in range, otherwise allows wire override.
- Risk If Not Fixed: A misconfigured client with playernum=0xFF could trigger cutscene skips on behalf of another slot. Practical exploitability is low (playernum is server-assigned at auth, very narrow window).
- Recommendation: Make the binding unconditional: `if (srccl->playernum >= MAX_PLAYERS) reject; else playernum = srccl->playernum;`. Drop the requested_playernum value entirely.
