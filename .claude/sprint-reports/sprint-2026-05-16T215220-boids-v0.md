## Goal

Extend the existing GPU compute kernel (`port/fast3d/swarm_gpu.cpp::kSwarmCs`) from
pure seek-player to classical Reynolds (1987) boids: separation + alignment +
cohesion accumulated over peers in the same SSBO, blended with the seek vector.
Surface-plane projection (Slice 6) preserved so sloped-floor locomotion still
works.

## Changes

### `port/fast3d/swarm_gpu.cpp`

1. **`struct swarm_params`** (C++ mirror of SSBO Params block) extended with 8
   floats (2 vec4 groups, std430-friendly):
   - `boid_sep_radius`, `boid_align_radius`, `boid_coh_radius`, `_pad_b0`
   - `boid_seek_weight`, `boid_sep_weight`, `boid_align_weight`, `boid_coh_weight`

2. **GLSL Params block** mirrored the same 8 fields.

3. **Defaults set at upload site** (next to `s_Params.max_speed = 5.0f`):
   ```
   sep_radius   = 60.0   (~1.5x Skedar collision radius)
   align_radius = 200.0
   coh_radius   = 300.0
   seek_weight  = 1.0
   sep_weight   = 1.5
   align_weight = 0.4
   coh_weight   = 0.3
   ```

4. **Shader main()** rewritten inside the existing `d > 1.0` guard:
   - Boids accumulator loop: O(N^2) reading peer `(px,py,pz,vx,vy,vz)` from `b[j]`
     for all `j != i`, partitioning into sep/align/coh windows by distance.
   - Each rule produces a unit-vector steering term (or zero).
   - Blended steering = weighted sum, projected onto surface plane,
     renormalised to unit, scaled by `max_speed`.
   - Fallback to plain seek if blended length is near-zero (e.g. sep+coh
     cancel out).
   - Existing `step > d` clamp preserved so `max_unit_per_frame` stays
     bounded by `max_speed`.

### Shader excerpt (inner loop + blend)

```glsl
for (int j = 0; j < int(P.count); j++) {
    if (j == int(i)) continue;
    vec3 p_j = vec3(b[j].px, b[j].py, b[j].pz);
    vec3 offset = pos - p_j;
    float dist = length(offset);

    if (dist > 0.001 && dist < P.boid_sep_radius) {
        sep_sum += offset / (dist * dist);
        sep_n++;
    }
    if (dist < P.boid_align_radius) {
        align_sum += vec3(b[j].vx, b[j].vy, b[j].vz);
        align_n++;
    }
    if (dist < P.boid_coh_radius) {
        coh_sum += p_j;
        coh_n++;
    }
}
...
vec3 steer = P.boid_seek_weight  * seek_dir
           + P.boid_sep_weight   * sep_steer
           + P.boid_align_weight * align_steer
           + P.boid_coh_weight   * coh_steer;
steer = steer - dot(steer, surface_up) * surface_up;
float steer_len = length(steer);
if (steer_len > 0.0001) steer /= steer_len;
else                    steer = seek_dir;
vec3 vel = steer * speed;
pos += vel * P.dt * 60.0;
```

### First-dispatch shader compile

First attempt failed:
```
WARNING: BENCHMARK.SWARM.GPU: compute shader compile failed:
0(142) : error C7537: OpenGL does not allow 'centroid' after a type specifier
```

Root cause: `centroid` is a reserved GLSL qualifier (used for centroid
sampling in fragment shaders). Renamed local variable from `centroid` ->
`group_center`. Second build + run: shader compiled + linked successfully:
```
BENCHMARK.SWARM.GPU: compute shaders available (GL 4.3)
```

No further compile/link errors.

### Higher-tier estimates (NOT measured; deferred to smoke run)

With the cycler unreachable in my run, I can only project:
- 256 bots: inner loop = 256*255 ~= 65K reads. Modern dGPU ~0.05ms; perf should
  be well within 20ms.
- 512 bots: ~260K reads. Should still be ~1-2ms of GPU work.
- 768 bots: ~590K reads. Maybe 2-5ms.
- 4096 bots: ~16.8M reads. This is where naive O(N^2) starts hurting. Modern
  GPU 1-3ms ideally; integrated GPUs could blow to 30-50ms.

The shader logic itself is straightforward (a single loop with three radius
windows and a vec3 accumulator each); a quality compiler should unroll the
inner-body well. The dominant cost will be SSBO bandwidth -- 4096 invocations
each reading 4096 records of 24 bytes (pos+vel) = 384 MB/dispatch. At 60 Hz,
~23 GB/s. Well within mid-range desktop GPU memory bandwidth.

## Spatial grid v1 recommendation

The naive O(N^2) loop scales linearly per invocation; at 768 bots projected
GPU cost is still 2-5ms which is acceptable. At 4096 the load triples vs 768
in raw reads but should still be < 10ms on any modern dGPU. So v0 ships
behaviour and is unlikely to be hard perf-bound at the smoke ceiling (768).

**Spatial-grid v1 is the right next slice** but is NOT urgent. Trigger conditions:
- Smoke at 4096 shows `frame_avg_ms > 30` consistently
- Mike playtests integrated-GPU laptops and observes < 30 fps at 1024+ bots
- We push the ladder above 4096

The grid implementation will be: per-frame CPU-side cell-bucketing (the swarm
slot table already has all positions), upload as a second SSBO, shader does a
3x3x3 cell-neighbourhood scan instead of full-N. Spec lives in the
gpu-swarm-and-test-scenarios design doc.
