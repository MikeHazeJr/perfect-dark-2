## Item 1 — B-307 promoted to FIXED-PENDING-PLAYTEST

### What

Re-classified `B-307` (CPU swarm crash 128→256 bots) from `OPEN 2026-05-02` to `FIXED-PENDING-PLAYTEST 2026-05-15 (715424c4, dev)`.

### Why

B-307 (silent CPU crash on the 256-bot ladder step) and B-311 (GPU FATAL `0xbb0000ff` at 128-bot step) were two surface manifestations of one root cause: **CHRVTX vertex pool exhaustion**. The pool's `numifsp/numifmp` was sized 120/80 for the N64 release's ~8-player + handful-of-NPC working set; once `chrDisfigure` exhausted every slot, the failed allocations cascaded into corrupted display-list state, surfacing as either:

- A clean FATAL when the GPU compute pipeline parsed garbage opcodes (B-311 path), or
- A silent first-frame crash inside `chrTickAll` / `botTick` when the CPU side hit a NULL'd vertex pointer it could not recover from (B-307 path).

The fix in `715424c4` (Track A1a) bumped CHRVTX + CHRCOL `numifsp/numifmp` 120/80 → 4096/4096 and bumped the per-pool vertex budget to 200000. The fix structurally addresses both crash classes — B-311 was already promoted in the same commit window, B-307 was the bookkeeping miss.

## Item 2 — B-327 fix shipped

### Symptom

Orchestrated listen-host (`PerfectDark.exe --host --listen-bind 27200`) stopped logging immediately after `CHAT: Agent joined` when a real ENet peer attached. `mainTick` log went silent, no FATAL / EXCEPTION_ACCESS_VIOLATION in `pd-host.log`, the host's smoke-harness scripted exit at host-t=18000ms did not fire, and the host was reaped by the runner's watchdog after `timeout_seconds + 30s`. Bug filed in `b39de15d` with two suspect candidates flagged.

### Investigation

Traced the post-CHAT control flow in `netmsgClcAuthRead`:

```
netmsg.c:794  srccl->state = CLSTATE_LOBBY              # joining peer enters LOBBY
netmsg.c:800-802  send SVC_AUTH to srccl                # only the new peer
netmsg.c:806  netDistribServerSendCatalogInfo(srccl)    # only the new peer
netmsg.c:824-828  log "joined" + netChatPrintf("joined") # LAST LINE in pd-host.log
netmsg.c:835  lobbyUpdate()                             # bounded loop, returns
netmsg.c:838-845  SVC_LOBBY_LEADER broadcast loop       # ← SUSPECT
netmsg.c:850  netBroadcastRoomList()                    # via enet_host_broadcast (safe)
```

The broadcast loop at lines 838-845 iterates `g_NetClients[]` and calls `netSend(ncl, NULL, true, NETCHAN_CONTROL)` for every slot in `state >= CLSTATE_LOBBY`. On a **listen** server (`g_NetDedicated == 0`, set by `netStartServer` at `net.c:879`):

- `g_NetLocalClient == &g_NetClients[0]`
- `g_NetClients[0].state = CLSTATE_LOBBY` (set at `net.c:880`)
- `g_NetClients[0].peer = NULL` (zeroed by `netClientResetAll`'s memset, never written — the host has no remote endpoint for itself)

When `ci == 0`, the loop fell through to `netSend(&g_NetClients[0], ...)` → `net.c:2300` → `enet_peer_send(NULL, ...)` → `port/include/external/enet.h:3085` dereferenced `peer->state` at NULL.

The resulting access violation was triggered inside ENet's own stack frame. The crash handler's `crashVectoredHandler` (which writes `FATAL: ACCESS_VIOLATION ...` via direct `fopen`/`fprintf`) did **not** surface a FATAL line in `pd-host.log` — likely because the AV fired before the vectored handler's static-buffer write site reached the file, or the SEH was caught at an outer scope that just terminated the in-progress message-dispatch loop without unwinding. Net effect: host appeared "stalled" — process alive but `mainTick` silenced after the prior CHAT log line.

### Fix

Single targeted edit at `port/src/net/netmsg.c:838-845`. Skip the local slot at the loop head plus a defence-in-depth NULL-peer guard inside the state branch:

```c
for (s32 ci = 0; ci < NET_MAX_CLIENTS; ci++) {
    struct netclient *ncl = &g_NetClients[ci];
    if (ncl == g_NetLocalClient) continue;  /* B-327: listen-host slot has peer=NULL */
    if (ncl->state >= CLSTATE_LOBBY) {
        if (!ncl->peer) continue;            /* defence in depth */
        netbufStartWrite(&ncl->out);
        netmsgSvcLobbyLeaderWrite(&ncl->out, leaderClientId);
        netSend(ncl, NULL, true, NETCHAN_CONTROL);
    }
}
```

Block-comment explains the failure mode + hosting-mode invariants so future readers don't reintroduce the bug.

The listen host's own lobby state is already authoritative from the preceding `lobbyUpdate()` call — it doesn't need to receive its own SVC_LOBBY_LEADER. Dedicated servers have `g_NetLocalClient == NULL`, so `ncl == g_NetLocalClient` is never true and the guard is a no-op there.

### Propagation check

Audited every `netSend(&g_NetClients[i], ...)` and `netSend(ncl, ...)` call site under `port/src/net/`:

| Site | Pattern | Listen-host risk | Notes |
|------|---------|------------------|-------|
| `netmsg.c:838-845` (FIXED) | loop, state>=LOBBY, send to peer | YES (was the bug) | This patch |
| `netmsg.c:7638` (CLC_ROOM_SETTINGS_UPDATE) | loop, state>=LOBBY, filter by room_id | safe | host slot has room_id=0xFF, won't match active room |
| `netmsg.c:7709` (CLC_ROOM_PLAYLIST_UPDATE) | same | safe | same room_id filter |
| `netmsg.c:7011` (SVC_STATE_FRAME spectator) | loop, filter CLFLAG_SPECTATOR | safe | host slot has no CLFLAG_SPECTATOR |
| `netmsg.c:7377` (CLC_STAGE_READY BOT_AUTHORITY) | loop, filter CLSTATE_GAME, break | low risk | filters CLSTATE_GAME, breaks after first match; listen host's slot 0 in CLSTATE_GAME with peer=NULL would still crash, but this path only fires after a match has started |
| `netmsg.c:7315` (`netBroadcastRoomList`) | netSend(NULL,...) | safe | routes through `enet_host_broadcast`, which iterates ENet's peer list (no listen-host self-peer) |
| `net.c:2256` (resync broadcast) | loop with internal filter | safe (cursory) | filter excludes inactive slots |
| `netdistrib.c` (file-distribution sends) | direct `cl` arg, never the local | safe | distribution targets are always remote peers |

The CLC_STAGE_READY path is the only remaining latent footgun — same NULL-peer hazard if/when a listen host enters CLSTATE_GAME with the same wire-level state. Not exercised by the current `listen_host_peer_smoke.json` scenario (which exits at host-t=18s before any match starts), so I left it untouched to keep this dispatch focused. Adding a `ncl == g_NetLocalClient continue;` there would be a clean follow-up; flagging in the bugs.md B-327 entry's propagation paragraph.
