## Step 1 — Symbolicate

`addr2line` returned `??` for the stripped binary, so I walked `objdump --syms PerfectDark.exe` and extracted all `(sec 1)(ty 20)` text symbols to a sorted file. The crash PC is `+0x110970` from module base; subtracting the `.text` VMA offset (0x1000) gives offset `0x10F970` within the section. Looking up that offset against the 38k function-symbol table:

```

+0x673d0  (text 0x663d0)  -> chrCalculatePushPos  +0x1e9
+0x685b7  (text 0x675b7)  -> chr0f01f378          +0x704
+0x3c4114 (text 0x3c3114) -> modelUpdateChrInfo   +0x1a7
+0x3c426e (text 0x3c326e) -> modelUpdateInfo      +0x1f
+0x62af7  (text 0x61af7)  -> chr0f0220ec          +0xcd

+0x135a90 (text 0x134a90) -> propsTickPlayer      +0x48e
+0xccb49  (text 0xcbb49)  -> lvRender             +0x88f
```

The crash chain is fully resolved. Disassembling `objFindByTagId+0xe`:
```
   140110962:  sub    $0x28,%rsp
   140110966:  call   <tagFindById>
   14011096b:  test   %rax,%rax
   14011096e:  je     <return>
   140110970:  mov    0x10(%rax),%rax     <-- AV (reading tag->obj)
```

`tagFindById` returned a non-NULL pointer (so bounds check `tag_id >= 0 && tag_id < g_NumTags` passed), but `tag->obj` deref crashed. That means `g_TagPtrs[tag_id]` returned a **stale pointer** to freed tag memory.

The crashing call: `objFindByTagId(chr->myspecial)` at `src/game/chr.c:293` — the chair lookup in `chrCalculatePushPos`.

## Step 2 — Root cause

`chrInit` (`src/game/chr.c:1148`) does NOT initialise `chr->myspecial`. It initialises `padpreset1`, `proppreset1`, `chrseeshot`, `chrseedie`, `chrpreset1`, `chrdup` to -1 — but skips the setup-data-derived block (`myspecial`, `yvisang`, `naturalanim`, `teamscandist`, `convtalk`).

The standard allocation paths fill those in explicitly:
- `body.c:707-714` writes them from MP packed AI data
- `body.c:801-808` writes them for eyespy
- `botmgr.c:181` writes `chr->myspecial = -1` for AI bots

But the GPU swarm benchmark (`port/src/swarm_test.c::spawn_one_skedar`) bypasses all three paths. It calls `chrAllocate` -> `chrInit` and then sets a hand-curated subset of fields (bodynum, headnum, team, maxdamage, radius, height, aibot, myaction). `myspecial` is left as MEMPOOL_STAGE garbage from previous allocations in that slot.

At 256/512-bot tiers, slots happened to land on freshly-mempAlloc'd memory where `myspecial` was either 0 or `-1`-coincident — harmless. At the 768 tier, the cycler did `despawn_all` (freed 491 slots) followed by `respawn_ring(768)` (claimed 747 slots via `propAllocate` LIFO). New high slot indices crossed into MEMPOOL_STAGE bytes previously written by the arena's `g_StageSetup.props` tag-using setup data (Felicity stage has tagged objects). `chr->myspecial` picked up a tagnum-shaped garbage value. `tagFindById`'s bounds check passed, `g_TagPtrs[tag_id]` returned a stale pointer, and `tag->obj` deref crashed.

The last breadcrumb `slot=747 ... action=0` is consistent: ACT_INIT = 0 (the chr's first tick, never transitioned to STAND). The first chrTick on a swarm bot at high slot index, on the first frame after a fresh respawn, walks through `chr0f01f378` (the `modelSetAnim70` callback registered at `chr.c:1400`) which routes through `modelUpdateInfo` -> `chr0f0220ec` -> `chrCalculatePushPos`. The chair lookup at line 293 hits the stale `myspecial` and AVs.

---

## Step 3 — Fix

`src/game/chr.c::chrInit` now initialises the setup-data block:

```c
chr->myspecial = -1;     /* canonical "no chair" sentinel */
chr->yvisang = 0;
chr->teamscandist = 0;
chr->convtalk = 0;
chr->naturalanim = 0;
```

Why -1 for `myspecial`: every reader gates on `myspecial != -1` (chr.c:292), `myspecial >= 0` (chraction.c:3279, chraicommands.c:4958), so -1 is the sentinel they already expect to mean "no chair." Setting it in `chrInit` makes every chrAllocate caller — including future swarm-class users that bypass the setup-data init blocks — start from a known-safe state.

The other four fields (`yvisang`, `teamscandist`, `convtalk`, `naturalanim`) have no current ptr-deref risk but the setup-data init paths write them, so the implicit contract is "post-chrInit they have a defined value." Initialising them in the same block honours the contract.

Per `feedback_no_half_measures`: this is the structural fix at the init layer; no defensive guard added in `objFindByTagId` (would silence symptoms across the codebase without surfacing future schema drift). Class: SP-7-adjacent (magic-init drift — fields written by some allocation paths and not others, with downstream readers assuming "init means initialised").

## Step 7 — Propagation check

Other readers of `chr->myspecial`:
- `chr.c:292` — `chrCalculatePushPos` chair lookup (the crash site)
- `chraction.c:3279` — chair sit-down action
- `chraicommands.c:4958` — AI script chair query
- `propobj.c:11547` — chair regeneration sweep (writer side, sets to -1)

All readers gate on `myspecial != -1` or `myspecial >= 0`. Setting `-1` in chrInit makes them all skip the deref. No reader-side changes needed.

Other `chrInit`-missed fields with the same drift pattern:
- `yvisang` — vertical visibility angle, used in `chr.c::chrIsCloseToVertical` etc. (numeric, no ptr deref)
- `teamscandist` — team-scan distance, used in chr behaviour (numeric, no ptr deref)
- `convtalk` — conversation flag (numeric, no ptr deref)
- `naturalanim` — natural-anim flag (numeric, no ptr deref)

These are init in the same block for symmetry and to honour the implicit contract.

Not propagating to similar swarm-class consumers: the swarm test was the surface where the bug presented, but the fix lives in `chrInit` which is shared by ALL `chrAllocate` paths, so any future caller benefits.
