## Goal

Close the Slice 3 perf gap left by the Track 1+5 ship at commit `937bfc9b`. The
swarm apply loop's chrSetPosWithCachedGround path was backed out under a
conservative mitigation (kept chrSetPos(findground=true), saving only the
surface_up sampler), netting ~20% raycast reduction at 512 bots vs the 80%
Slice-3 target.

## Shipped

Single commit, three structural pieces:

1. **`chrSetPosWithCachedGround` room sync — unconditional.** Dropped the
   `if (newrooms)` gate that skipped the `propDeregisterRooms + roomsCopy +
   chr0f0220ac` trio when the caller passed `chr->prop->rooms` back to itself
   (which the swarm apply loop does). The trio now matches `chrMoveToPos`'s
   unconditional behavior. The internal `chr0f0220ac` re-resolves `prop->rooms`
   via `bgFindEnteredRooms` on the just-written `prop->pos`, so drift across
   room boundaries is tracked correctly.

2. **`chrSetPosWithCachedGround` sets `CHRCFLAG_FORCETOGROUND`.** This was the
   second-stage root cause. `chrMoveToPos` (line 15780) sets the flag every
   call; the bondwalk fall path (`chr.c:920`) consumes it and SNAPS the chr to
   its current ground level, BYPASSING the fall accumulator. The cached helper
   was missing this set, so swarm bots — which have no `chr->aibot` and so do
   NOT benefit from the chr.c:881-902 off-map fallback — fell unchecked
   whenever the cached ground (from the previous frame's pos) didn't match the
   `chrTickBg`-sampled ground at the just-applied pos. After a few frames,
   `manground <= -30000` triggered the pit-death branch at chr.c:940, setting
   `CHRHFLAG_DELETING`. Next chrTick called `chrRemove` + returned
   `TICKOP_FREE`, freeing the prop and leaving `s_Swarm[i].chr` pointing at a
   prop whose `prop->chr` was NULL. The cycler's next `despawn_all` AVed.

3. **Swarm apply loop re-enables `chrSetPosWithCachedGround`.** With the
   helper fixed, `port/fast3d/swarm_gpu.cpp::swarmGpuStepAndApply` routes
   through the cached helper using `s_FloorCache[i]` data populated by the
   pre-pass. Both chrSetPos-internal raycasts skipped on cache hit AND miss
   (miss-path's `cdFindGroundInfoAtCyl` already runs in the pre-pass and is
   shared via the cache). The `BENCHMARK.SWARM.GPU.PERF` log line now reports
   `chrsetpos_raycasts=0` and tracks total raycasts = `2 * sampled` (miss path
   only).

## Decisions

**Root cause diagnosis took two iterations.** The Track 1+5 worker's sprint
report (`sprint-2026-05-16T205111-slice3-perf-merge.md`) correctly identified
the missing chrMoveToPos pre-flight as suspect, but the conservative mitigation
they shipped left both invariants (room sync AND `CHRCFLAG_FORCETOGROUND`) on
the table. My first attempt fixed only the room sync (drop the `newrooms`
gate); smoke still surfaced the same B-332 crash at the 8→16 cycle within
~10 seconds, with `BENCHMARK.SWARM.GPU.VEL: active=6` dropping from 8 mid-cycle
(bots dying before the next cycler fired).

Tracing the bot-death flow through `chr.c:867-1003` surfaced the
`CHRCFLAG_FORCETOGROUND` invariant. The fall-logic guard at chr.c:920 is the
chokepoint: if the flag is set, the fall accumulator is bypassed entirely; if
not, the fall logic runs and can drive `manground` to -30000 (pit death) for
chrs with no `aibot` (= the swarm population). The Track 1+5 worker's
"conservative mitigation" worked precisely BECAUSE `chrSetPos(findground=true)`
calls `chrMoveToPos` which sets the flag — the surface_up cache hit save was
real, but the helper-vs-chrSetPos invariant gap was hidden behind that.

## Investigation: build env false-FAILED

Mid-session I ran into a class of compile failures where `ninja` reported
`FAILED: [code=1]` for every C compile job, no stderr, no obj output. Direct
invocation of the same `cc.exe` command from `bash` reproduced the silent
exit=1. Root cause: the agent's bash session inherited a `PATH` with
`/mingw64/bin` ahead of `/c/msys64/mingw64/bin`. The pre-`/c/msys64/...` entry
has `libgcc_s_seh-1.dll` but no `gcc`/`cc.exe` — gcc's sub-binary chain
(`cc1.exe`, etc.) loaded the wrong DLL and aborted silently. Setting
`PATH=/c/msys64/mingw64/bin:$PATH` ahead of every ninja invocation restored
clean builds. Logged here so a follow-up sprint can patch
`devtools/build-env.sh` to filter out the unprefixed `/mingw64/bin` entry the
way `_build-env-prelude.ps1` does.

## Follow-ups

- **Build env PATH ordering.** Patch `devtools/build-env.sh` to filter out
  `/mingw64/bin` (no leading `/c/msys64`) entries when ninja's GCC sub-binary
  chain needs the canonical `/c/msys64/mingw64/bin` DLL set. Currently the
  workaround is to prefix `PATH=/c/msys64/mingw64/bin:$PATH` before every
  ninja invocation. Not urgent for shipping but improves agent build
  ergonomics.

- **Re-measure ticks/sec at each tier in a non-smoke playtest.** The smoke
  harness caps frame_avg_ms at ~10 ms (SDL pacing in headless mode); the
  numbers don't reflect actual GPU swarm tick wall-clock. Mike's interactive
  playtest at 512 / 768 bots with the live perf overlay will tell us the real
  per-frame savings from the 85-91% raycast reduction.

- **Tighten `SWARM_FLOOR_SAMPLE_DRIFT_CM`.** Hit rate at low counts could be
  pushed higher. At 256 bots the rate was ~60% (per Track 1+5 sprint report);
  bumping drift from 60 cm to e.g. 120 cm would push hit rates up at the cost
  of slightly more stale ground data. Worth a playtest cycle.
