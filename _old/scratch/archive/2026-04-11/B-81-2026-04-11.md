# B-81 Fix — JSON recursion guard (2026-04-11)

## Bug

Crafted save file with pathological nesting depth → `s_skip_value` recurses unboundedly
→ stack overflow crash. Two attack surfaces:

1. **Recursion depth**: `s_skip_value` called itself without a depth cap. A JSON file with
   10,000 levels of `{"k":{"k":{"k":...}}}` would blow the stack.

2. **File size**: `readFileContents` had no size cap. A 500MB crafted save file would
   `malloc(500MB)` before any parsing began, causing memory exhaustion.

## Fix (port/src/savefile.c)

### 1. Depth guard — already in place, verified correct

```c
#define S_MAX_DEPTH 64  /* max JSON nesting depth */

static void s_skip_value(sparse_t *p, s32 depth) {
    if (depth > S_MAX_DEPTH) {
        while (*p->pos) p->pos++;  /* drain to EOF — clean abort */
        return;
    }
    ...
    s_skip_value(p, depth + 1);  /* bounded recursion */
}
```

- Max real stack depth: 65 frames of `s_skip_value` (depth 0..64, then drain at 65).
- Drain approach propagates cleanly: all outer while loops see STOK_EOF and exit.
- Already in the codebase; confirmed correct. No change needed.

### 2. File size cap — ADDED

```c
#define SAVE_MAX_FILE_BYTES (256 * 1024)  /* 256 KB hard cap */
```

In `readFileContents`, after `ftell`:
```c
if (len <= 0 || len > SAVE_MAX_FILE_BYTES) {
    fclose(fp);
    if (outLen) *outLen = 0;
    return NULL;
}
```

- Also fixed the implicit `long → size_t` cast in `malloc(len + 1)` → `malloc((size_t)len + 1)`.
- 256KB is orders of magnitude above the largest legitimate save file (~2-5KB).

## Why only savefile.c

The recursion happens exclusively in `s_skip_value` which is local to `savefile.c`.
The parse loops in `saveLoadAgent` / `saveLoadSystem` / `saveLoadMpPlayer` / `saveLoadMpSetup`
are all iterative (while loops), not recursive. No other file is involved.
