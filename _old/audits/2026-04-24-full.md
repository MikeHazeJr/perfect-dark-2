## 1. Inferred Goal

Land a coherent foundation for **The Grid** (unified Forge + Playtest facility): a Main Menu submenu that picks an arena from the catalog, configures a base scenario + variant, applies them to `g_MatchConfig`, and hands off to a Forge session that can be toggled in-place to Playtest via a Halo-style Back-button binding. Add bot lifecycle controls (spawn / remove / freeze) to the Playtest HUD, integrate with the existing F6 freeze machinery via `g_BotUpdatesDisabled`, and gate the new server build dependency `assetcatalog_api.c` so its client-only RNG path does not leak into `pd-server`.

Adjacent work: P5 attempted to fix B-228 (SP stages crashing as MP arenas through the lift / escalator-step transport gate) by inserting an `mptransport_diffflag` mask in `src/game/setup.c::setupCreateProps`. P8 then re-audited and concluded the fix is structurally insufficient — keeping B-228 architecturally open. (Diagnosis revised below from the prior audit pass: the issue is not "wrong loader" but "nothing for the relax filter to relax".)

## 3. Code Quality

### Findings

#### AUDIT-24-H1 [HIGH | confirmed by independent re-grep — diagnosis revised this pass]
**P5 (`216fd27f`) is a no-op for B-228 because base-game MP arena setup blobs do not contain LIFT/ESCASTEP macros at all.**

The prior framing of this finding ("P5 is in the wrong loader, the fix should move to `mplayer/setup.c`") is **incorrect** and is corrected here.

- `src/game/mplayer/setup.c` is the multiplayer character-select / lobby-menu module, **not** a prop loader. Its top-of-file includes (`menu.h`, `mainmenu.h`, `menudialogdef`, etc.) and contents (menu handler functions, dialog struct definitions) confirm this. It contains zero `setupCreate*` calls and zero `OBJTYPE_*` switch arms.
- The single prop loader for both SP and MP is `setupCreateProps` in `src/game/setup.c` (line 1586). MP arena loads also dispatch through this function.
- P5's `mptransport_diffflag` mask therefore IS in the right loader (lines 1702-1720, 1827, 1964).

The actual reason P5 is a no-op was already documented by the foundation-pass audit on 2026-04-23 (`context/audits/foundation-pass-2026-04-23.md:159`):

> "`mptransport_diffflag` is a NOOP on the current codebase — the filter rejects nothing because nothing loads. P5 is kept as structural insurance (a mod could ship an MP setup with lift + exclude bits, in which case the relax applies) but alone does not close B-228."

In other words: the base-game MP setup blobs (e.g. `mpsetupnewcombat.c`, the CS arena setups) do not emit LIFT or ESCASTEP macros at all, so there is nothing for the relax filter to relax. The crash in B-228 comes from a **different** code path — likely a model / collision / pathfinding lookup that assumes the lift/escastep prop exists when the stage was authored as SP. The transport-prop loader gate is downstream of where the crash originates.

**Recommendation (revised):**
1. Re-trace the B-228 crash stack to identify which subsystem fails when an SP-authored stage is hosted as an MP arena. Candidates: `liftFindByPad` returning NULL when an AI script expects a registered lift; pathfinding waypoint resolution; portal traversal through a missing escastep portal.
2. Once root cause is known, the fix likely belongs in either (a) the AI/script side (fail soft when the prop is absent), or (b) a per-stage fix-up that injects the missing setup macros at MP-load time, rather than relying on the diffflag relax.
3. P5 may stay in place as defensive-in-depth structural insurance. Do not move it to `mplayer/setup.c`; that file is a menu file. Do not delete it either; the `LOG_NOTE` it emits is useful in playtest logs.
4. Do not close B-228 until repro is verified on the suspected stages with the next fix layered on.

#### AUDIT-24-H2 [HIGH | upgraded from MEDIUM | confirmed by dispatch-trace]
**`JBTN_BACK` → `ACTION_FORGE_TOGGLE` never fires; `ACTION_SCORECARD` always wins.**

`fireVk` in `port/src/actionmap.cpp:469` implements **single-winner-per-IMC dispatch**: it iterates every action in the active context, finds the one with the lowest trigger-slot index for the incoming VK (and on tie, the lowest action enum), then `goto next_player` — explicitly skipping any other action that also bound the same VK in the same context.

For `JBTN_BACK`:
- `ACTION_SCORECARD` (enum `56`, actionmap.h:131) — trigger 0 = TAB scancode 43, trigger 1 = `JBTN_BACK` (actionmap.cpp:1933-1934)
- `ACTION_FORGE_TOGGLE` (enum `57`, actionmap.h:134) — trigger 0 = `VKL_F7`, trigger 1 = `JBTN_BACK` (actionmap.cpp:1947-1948)

Both bind `JBTN_BACK` at trigger slot 1 — tie. Tie-break by lower action enum: SCORECARD (56) < FORGE_TOGGLE (57). **SCORECARD wins every press; FORGE_TOGGLE never fires on gamepad.** F7 on keyboard still works (no conflict).

The author's inline comment (actionmap.cpp:1936-1946) — "both actions edge-trigger on the same press, which is fine because scorecard in a solo Grid session is a no-op popup" — is factually wrong about the dispatch behaviour. Both do not fire; only SCORECARD does.

**Recommendation:**
1. **Short-term:** introduce a Forge-mode IMC (`g_ImcForge`) at higher priority than `g_ImcGameplay`, activate it inside `forgeSessionIsActive()`, and put the Forge-only bindings (FORGE_TOGGLE, FORGE_ASCEND, FORGE_DESCEND) there. The IMC stack already supports priority push, so this is mechanical. SCORECARD stays in gameplay.
2. **Alternative:** rebind `ACTION_FORGE_TOGGLE` to a different gamepad button (e.g. View+Menu chord, or a long-press on Back).
3. Verify the same dispatch model does not silently break **any other** dual-bound VK in the gameplay IMC. See AUDIT-24-H3.

#### AUDIT-24-H3 [HIGH | confirmed by dispatch-trace — new this pass]
**RT and LT also single-winner-lose: `ACTION_FORGE_ASCEND` / `ACTION_FORGE_DESCEND` never fire on gamepad.**

Same root cause as H2. The 2026-04-24 commit added Forge ascend/descend on the gamepad triggers, but they collide with the gameplay fire actions:

- `ACTION_FIRE_PRIMARY` (enum `20`) — trigger 0 = `VK_MOUSE_LEFT`, trigger 1 = `JOFS_RTRIG` (actionmap.cpp:1885-1886)
- `ACTION_FORGE_ASCEND` (enum `58`) — trigger 0 = `VKL_E`, trigger 1 = `JOFS_RTRIG` (actionmap.cpp:1949, 1957)
- `ACTION_FIRE_SECONDARY` (enum `21`) — trigger 0 = `VK_MOUSE_RIGHT`, trigger 1 = `JOFS_LTRIG`
- `ACTION_FORGE_DESCEND` (enum `59`) — trigger 0 = `VKL_Q`, trigger 1 = `JOFS_LTRIG` (actionmap.cpp:1950, 1958)

Both pairs tie at trigger slot 1; `FIRE_PRIMARY` (20) < `FORGE_ASCEND` (58), `FIRE_SECONDARY` (21) < `FORGE_DESCEND` (59). The Forge actions never fire on the trigger inputs. The author's comment ("they never trigger bwalk movement because the player movemode is MOVEMODE_CUTSCENE") rationalises a side-effect that doesn't apply because the Forge action never gets dispatched at all — the fire action wins and writes its own state.

**Result:** in Forge freefly, gamepad triggers fire weapons (which then no-op because the player is in cutscene mode and weapon dispatch is suppressed elsewhere) and **do not** raise/lower the camera.

**Recommendation:** identical to H2 — a Forge-mode IMC at higher priority is the clean fix. Keyboard E/Q are unaffected.

#### AUDIT-24-M1 [MEDIUM | confirmed]
**Comment-vs-code naming skew in P5.** `src/game/setup.c:1684` documents the mask variable as `mplift_diffflag`; the actual variable name (lines 1702, 1711, 1827, 1964) is `mptransport_diffflag`. The rename was correct (escasteps are not lifts) but the comment block didn't follow. Future readers searching for the documented identifier will not find it.

**Recommendation:** Single-line edit to `src/game/setup.c:1684` replacing `mplift_diffflag` with `mptransport_diffflag`.

#### AUDIT-24-M2 [MEDIUM | strong evidence, partial verification]
**Per-client RNG in `catalogPickRandomHeadIdForBody` is a desync vector if called outside a wire-broadcast post-pick.** `assetcatalog_api.c:608` calls `rngRandom() % count` with no seed coordination. Two clients independently invoking this function for the same bot slot pick different heads.

**Mitigated case:** match-setup writes the resolved `body_id` / `head_id` into `g_BotConfigsArray[slot].base.{body_id,head_id}` and the `mpchrconfig` struct is broadcast to peers — both clients then see the same head because the *result* is on the wire, not the *call*. Verified the two `pdgui_menu_room.cpp` sites (line 2269, line 3417) operate inside an `isLeader` context — only the leader picks; followers receive via `g_MatchConfig` broadcast.

**Risk case:** Any future call site that picks then *uses* the head locally without a broadcast (e.g. previewing a bot in the menu, or a server-side simulant config that the server then re-picks) will desync. The lobby-preview rendering path is the most likely future violator; track it explicitly.

**Recommendation:** Add a Doxygen-style header to `catalogPickRandomHeadIdForBody` warning callers it is *not* deterministic across clients and must be paired with a broadcast of the resolved ID.

#### AUDIT-24-M3 [MEDIUM | confirmed by code read]
**`s_ValidHeadBuf[256]` is non-reentrant, not just non-thread-safe.** `assetcatalog_api.c:494` declares a module-static buffer. `catalogGetBodyValidHeadIds` returns a pointer into it (`s_ValidHeadBuf`). The author's comment dismisses concerns by citing "single-threaded by design," which addresses threads, not nested calls.

**Risk:** Any caller iterating two bodies and remembering the first list will silently observe the second body's heads. E.g. `for (i in bodies) { ids = catalogGetBodyValidHeadIds(...); cache[i] = ids; }` — every `cache[i]` ends up pointing at the same buffer, holding the last body's data.

**Recommendation:** Either (a) document the reentrancy contract on the API (return pointer is invalidated by the next call), (b) make the caller pass the output buffer + capacity, or (c) duplicate IDs into a small caller-allocated array on return.

#### AUDIT-24-M5 [MEDIUM | confirmed]
**Grid submenu lives in `s_MenuView == 6`, not the menu pool.** `pdgui_menu_mainmenu.cpp` switches on a hand-rolled state-int rather than registering the submenu via the established `pdguiPushMenu` / pool dispatch. Implications:

- Input-authority handling (focus, modal stacking, ESC behaviour) does not benefit from menu-pool conventions
- Future "open Grid submenu from elsewhere" entrypoints have to learn `s_MenuView == 6` rather than push a registered dialog name
- Audit trail for menu state ownership is split (some menus pool-backed, this one not)

**Recommendation:** Track as a P1.5 polish item once the rest of the foundation lands; not blocking for the alpha cut, but should be reconciled before more submenus follow this pattern and ossify the divergence.

#### AUDIT-24-M6 [MEDIUM]
**`s_GridScenarios[]` is a parallel array to `s_BaseGameModes`.** `pdgui_menu_mainmenu.cpp:4011-4018` hardcodes the six base scenarios with a comment claiming match against `assetcatalog_base_extended.c`. Mod-authored scenarios will not appear in the Grid scenario picker without a code edit. Catalog SOT principle says this should be enumerated.

**Recommendation:** Replace the hardcoded array with an enumeration of `ASSET_GAMEMODE` (or whatever the type tag is) similar to `gridArenaCollect`. Until then, document the divergence in `context/known-issues.md` so it doesn't surprise a mod author trying to ship a new scenario.

#### AUDIT-24-M7 [MEDIUM | confirmed by code read — new this pass]
**`s_GridArenasBuilt` is set true once and never reset.** `pdgui_menu_mainmenu.cpp:3969` declares `static bool s_GridArenasBuilt = false`; `gridArenaListBuild` sets it true at line 4115; the gate at line 4215 (and the `gridArenaCollect` consumer) never resets it. Consequence: when a mod is loaded or unloaded mid-session, the catalog rebuilds but the Grid arena picker keeps showing the old list until the process restarts. Mod-authored arenas added at runtime are invisible to the picker.

The realloc lifecycle (`gridArenaListBuild` opens with `free(s_GridArenas)`) is correct — the bug is purely in the gate flag, not in the buffer.

**Recommendation:** Subscribe `s_GridArenasBuilt = false` to a catalog-rebuilt callback, OR clear it from the same code path that triggers a catalog reset (mod load/unload, hub reset). One-liner if a hook exists; small refactor if one needs to be added.

#### AUDIT-24-M8 [MEDIUM | confirmed by code read — new this pass]
**`n_bots += s_spawnBot(o)` decrements `n_bots` when the bot pool is full.** `forge_runtime.c:755` adds `s_spawnBot`'s return value into `n_bots`. `s_spawnBot` (line 211) returns the slot index (0..MAX_BOTS-1) on success and `-1` on `s_findFreeBotSlot` failure. The summing therefore yields nonsensical totals on partial spawn — and on the first failure, `n_bots` becomes negative.

`n_bots` is consumed by the Playtest HUD bot-count display and by the rebuild reporting log line — currently a presentation-only field, no gameplay effect — but the value is wrong from the moment a single spawn fails.

**Recommendation:** Replace with `if (s_spawnBot(o) >= 0) ++n_bots;`. One-liner.

#### AUDIT-24-L1 [LOW | confirmed]
**P7 bot HUD keybinds bypass `WantCaptureKeyboard`.** `pdgui_forge_hud.cpp:143-156` calls `ImGui::IsKeyPressed(ImGuiKey_{Insert,Delete,End,Home}, false)` without consulting `ImGui::GetIO().WantCaptureKeyboard`. The author's comment says these keys "are normally unbound during combat."

Mitigations present:
- Line 89: `if (pdguiIsActive()) return;` early-exits when *any* menu is open — covers the common case
- The HUD only renders / fires in `state == FORGE_SESSION_NORMAL` (Playtest), and only after `forgeSessionIsActive()` — so the keys are scoped to a session

Residual gap: any non-menu ImGui widget that wants keyboard (an in-game console widget rendered alongside the HUD, or a future text-input overlay) would still see the keys consumed by both.

**Recommendation:** Add `if (ImGui::GetIO().WantCaptureKeyboard) { /* fall through to render only */ } else { /* poll keys */ }`. One-line guard, matches the B-154 fix pattern.

#### AUDIT-24-L2 [LOW]
**P3 reduces `pickHeadIdForBody` in `matchsetup.c` to a one-line wrapper but leaves a parallel name in place.** Two layers of indirection (`matchsetup.c::pickHeadIdForBody` → `assetcatalog_api.c::catalogPickRandomHeadIdForBody`). Acceptable as a transitional shim; should collapse once call sites are migrated.

#### AUDIT-24-L3 [LOW]
**`gridArenaCollect` uses `realloc` on a `static GridArenaEntry *s_GridArenas`.** No `free` is called on rebuild — the realloc owns it. `gridArenaListBuild` opens with `free(s_GridArenas); s_GridArenas = NULL;` (mainmenu.cpp:4084), so the lifecycle is correct. But the buffer is never freed at process shutdown — a benign leak (the OS reclaims at exit; no per-frame growth). Note for hygiene only.

#### AUDIT-24-L4 [LOW | new this pass]
**`netmsgClcAuthWrite` compiles into `pd-server` and dereferences `g_NetLocalClient` unconditionally.** `port/src/net/netmsg.c:617` has no `#if !defined(PD_SERVER)` guard around the function body (only the `s_AuthCookie` static at line 603 is gated). Line 625 (`g_NetLocalClient->settings.name`) would crash if reached on a server build.

In practice it is unreachable on `pd-server`: the only call site is `netClientEvConnect` in `port/src/net/net.c:1736`, which is registered as a client-side connect handler. A dedicated server never connects to itself, so the function never executes. This is therefore a **latent** footgun, not a live crash — but the next time someone refactors the message-write paths into a generic dispatch, the deref will trip.

**Recommendation:** Either gate the function body with `#if !defined(PD_SERVER)`, or add an early-return guard `if (!g_NetLocalClient) return 0;` at the top. The same audit should sweep `netmsgClcSettingsWrite`, `netmsgClcMoveWrite`, and any other `Clc*Write` functions for the same pattern.

### Positives

- **`s_teleportBotNearPlayer` null-safety is comprehensive** (`forge_runtime.c:254-260`): range-checks `aibotnum`, `g_Vars.currentplayer`, `currentplayer->prop`, `g_MpBotChrPtrs[slot]`, and `bchr->prop` before dereferencing. Plus a 100..5000u radius clamp matching the HUD slider range.

## 4. Security / Trust

### 4.1 Wire surfaces

No new client-trusted surfaces introduced this pass. Grid submenu input is local only; scenario / variant data flows through `g_MatchConfig` which is authoritative on the host and broadcast via existing `SVC_*` paths.

### 4.2 Catalog ID handling

## 5. Cross-Cutting Risks

### 5.1 Phase 2.5 — Upstream-shape pattern scan

### 5.3 Mod / native asymmetry

`gridArenaCollect` filters via `challengeIsFeatureUnlocked((u8)e->ext.arena.requirefeature)`. This is the right gate, but a mod-authored arena sets `requirefeature` itself — meaning a mod can either (a) set 0 (always available) or (b) set a feature ID the player has not unlocked, and silently disappear from the picker. Acceptable behaviour, but worth surfacing in mod-authoring docs.

The `s_GridScenarios[]` hardcode (M6) is the most significant mod-asymmetry of this pass: arenas are catalog-driven (mod-equal), scenarios are not.
